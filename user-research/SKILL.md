# User Research

无需真实访谈，不等于无需证据。

这个 skill 的职责是：在信息不完整、用户样本稀缺时，先帮独立开发者判断“这是不是一个真实、足够痛、值得继续验证的用户需求”，而不是替产品想法找论据。

**Output language**: 跟随用户语言。框架术语保持 `JTBD`、`Observed`、`Reported`、`Inferred`、`Demand Diagnosis`、`Proceed / Probe / Narrow / Kill`。

## 核心职责

- 把模糊直觉拆成用户、场景、痛点、现有替代、切换动机五层需求假设
- 在没有真实访谈时，先给出证据强弱判断和下一步最小验证动作
- 输出时明确哪些是事实、哪些是用户陈述、哪些只是推断

不要把它扩展成：

- 市场规模或增长渠道分析
- 已有充分数据后的留存 / 转化分析
- 价值表达是否清晰的诊断（转 `product-value-validation`）
- 需求已确认后的功能 ROI / 流程优化审计（转 `product-guide` 或 `first-run-experience`）

## 适用边界

| 情境 | 适用？ | 处理方式 |
|------|--------|----------|
| 新产品 / 新功能 / 新用户细分是否真的有人要 | ✅ | 默认走 `Demand Diagnosis` |
| 只有创始人直觉、没做真实访谈 | ✅ | 允许分析，但所有结论默认是待验证假设 |
| 有评论、私信、社区讨论、销售对话等零散反馈 | ✅ | 走 `Feedback Synthesis` |
| 想模拟用户为什么会犹豫、为什么不切换 | ✅ | 走 `Role Simulation`，但只能作为辅助，不是证据 |
| 已有完整 cohort / A/B / 漏斗数据，需要解释增长或留存 | ❌ | 先做数据分析；本 skill 不替代数据工作 |
| 需求已确认，问题变成“价值说不清” | ❌ | 转 `product-value-validation` |
| 需求已确认，问题变成“流程太重 / ROI 是否值得” | ❌ | 转 `product-guide` 或 `first-run-experience` |

## 先守住证据纪律

### 1. 先把输入分成三层

| 层级 | 含义 | 例子 |
|------|------|------|
| `Observed` | 已发生的行为或可见事实 | 用户已经在用 Excel / Notion / 人工流程凑合；有人反复做同一步手工操作；出现明确付费或时间成本 |
| `Reported` | 用户直接说过的话或现成反馈 | 评论、私信、销售记录、支持工单、朋友转述 |
| `Inferred` | 基于现有信息做出的推断 | 角色扮演、类比竞品、对用户动机的推演 |

输出时遵守三条规则：

1. 没有 `Observed` 时，不要把结论写成“已经证明有需求”
2. `Role Simulation` 只能生成 `Inferred`，不能被包装成真实用户证据
3. 任何关键结论都要标注它主要依赖哪一层证据

### 2. 问行为，不问喜好

默认不要问：

- “你觉得用户会不会喜欢？”
- “这个功能是不是看起来不错？”
- “大家应不应该需要这个？”

优先问 1-3 个 open question，顺序如下：

1. `问题发生点`
   - “你怀疑哪类用户会在什么具体时刻卡住、焦虑或浪费时间？”
2. `当前 workaround`
   - “他们现在怎么凑合解决？最麻烦的是哪一步？”
3. `代价与紧迫性`
   - “如果不解决，这件事会带来什么损失，多久发生一次？”
4. `切换动机`
   - “为什么现有做法已经不够好？什么情况下他们才会愿意换？”
5. `现有证据`
   - “你已经看过哪些真实信号？行为、抱怨、手工 workaround、付费、搜索、反复提问都算”

从上到下只选当前最关键的 1-3 个，不要一次全问完。

如果能从上下文直接推断，就不要机械追问；但要在输出中标明推断依据。

## 最小输入契约

开始前，至少要搞清楚下面 4 件事：

- 你现在要判断的是什么：产品、功能，还是某个用户细分
- 你怀疑谁有问题
- 你目前掌握的证据是什么
- 你想做什么决策：继续做、先收窄、还是暂时别做

如果这 4 件事里有关键缺口，先补问题，不要直接进入分析。

## 工作流总览

### Step 1：先选路线

| 路线 | 何时使用 | 输出重点 |
|------|----------|----------|
| `A. Demand Diagnosis` | 用户在问“他们到底需不需要” | 判断问题是否真实、够痛、值得继续 |
| `B. Hypothesis Teardown` | 用户已经有方案，想验证“用户会不会要” | 把问题假设和方案假设拆开 |
| `C. Role Simulation` | 想暴露用户在决策节点的犹豫与阻力 | 发现切换阻力与缺失信息 |
| `D. Feedback Synthesis` | 手上已经有评论、私信、对话、工单 | 把零散反馈转成需求信号与 JTBD |

如果用户没有明确指定，默认先走 `Demand Diagnosis`。

### Step 2：给出决策，而不只是分析

所有路线的结尾都要落到这四类判定之一：

| 判定 | 含义 | 典型下一步 |
|------|------|------------|
| `Proceed` | 需求信号足够强，值得继续做更具体验证或方案设计 | 进入 `product-value-validation` 或具体验证实验 |
| `Probe` | 需求可能存在，但证据还薄 | 先补 1-3 个最低成本验证动作 |
| `Narrow` | 只有某个细分用户或某个触发场景有明显信号 | 收窄目标用户、场景或承诺 |
| `Kill` | 当前更像“看起来不错”，不是强需求 | 暂停投入，避免继续美化想法 |

默认判定口径：

- `Proceed`：`Trigger / Pain / Workaround` 至少 3 项有强信号，且不是纯 `Inferred`
- `Probe`：需求 plausible，但关键证据仍主要来自 `Reported / Inferred`
- `Narrow`：只有更窄的用户细分、时刻或问题版本有强信号
- `Kill`：没有具体触发时刻、没有高成本 workaround，也没有明确主动性信号

## A. Demand Diagnosis

### 目标

回答一个最底层的问题：

> 这个需求是不是在某个具体场景里真实存在，而且痛到足以让用户改变行为？

### SOP

**Step 1 — 写出候选 JTBD**

先把模糊想法压成一句话：

```text
当 [具体情境] 时，[哪类用户] 想要 [完成的任务 / 获得的能力]，这样他就能 [结果 / 避免的损失]
```

如果这句话里没有“具体情境”或“结果 / 损失”，说明需求还没被说清。

**Step 2 — 做五项需求诊断**

| 维度 | 要问什么 | 强信号 | 弱信号 |
|------|----------|--------|--------|
| `Trigger` | 痛点在什么时刻爆发？ | 有具体触发时刻、角色、上下文 | 只有抽象抱怨 |
| `Pain` | 不解决会怎样？ | 有时间、金钱、风险、情绪成本 | 只是“会更方便” |
| `Workaround` | 现在怎么解决？ | 有丑陋但稳定的替代流程 | 根本没人费力解决 |
| `Pull` | 用户是否已表现出主动性？ | 主动搜索、重复抱怨、愿意付费、手工绕过 | 只是口头说“挺有趣” |
| `Switch` | 为什么会从现状切换？ | 现有方案明显不够好，切换理由具体 | 看不到换的必要 |

**Step 3 — 标出最高风险假设**

优先找这三类风险：

- `Problem risk`：问题可能没那么痛
- `Segment risk`：不是这类用户最痛，而是另一个更窄的人群
- `Adoption risk`：问题真实，但他们不会用你这套解法

**Step 4 — 给最低成本验证动作**

在没有真实访谈时，优先推荐下面几类动作：

- `Fake door`：用一句极具体的价值承诺测试点击 / 留资 / 回复
- `Concierge`：手工替用户完成一次结果，看他是否愿意继续
- `Workaround audit`：把现有人工流程拆开，量化时间、错误率或协作成本
- `Signal mining`：整理现有评论、私信、搜索词、社群提问，验证是否反复指向同一情境
- `Narrowed landing copy`：只面向一个细分场景写文案，看是否有人被准确击中

### 输出格式

```md
## Demand Diagnosis: [产品 / 功能 / 需求假设]

### Candidate JTBD
- 当 [...]
- 我想要 [...]
- 这样我就能 [...]

### Evidence Ledger
- Observed:
- Reported:
- Inferred:

### Demand Check
| 维度 | 判定 | 证据 |
|------|------|------|
| Trigger | 强 / 中 / 弱 | ... |
| Pain | 强 / 中 / 弱 | ... |
| Workaround | 强 / 中 / 弱 | ... |
| Pull | 强 / 中 / 弱 | ... |
| Switch | 强 / 中 / 弱 | ... |

### Highest-Risk Assumption
- 类型:
- 内容:
- 为什么危险:

### Next Validation Moves
1. ...
2. ...
3. ...

### Decision
- Proceed / Probe / Narrow / Kill
- 原因:
```

## B. Hypothesis Teardown

### 目标

把“我觉得用户会需要 X”拆成可被反驳的假设，而不是把问题、方案和增长路径混成一句话。

### SOP

**Step 1 — 抽出完整假设**

格式：

```text
[哪类用户] 会在 [具体情境] 下因为 [问题 / 损失] 需要 [结果]，并愿意接受 [你的方案]
```

**Step 2 — 按层拆分**

至少拆成这四层：

1. `User existence`：这类用户真的存在，而且可识别
2. `Problem severity`：这个问题足够痛，不是边缘不便
3. `Workaround failure`：现有做法确实不够好
4. `Solution adoption`：他们会接受这类解决方式，而不是继续凑合

**Step 3 — 评风险**

每条假设评两个维度：

- `Importance`：错了会不会让方向失效
- `Evidence`：目前主要是 `Observed`、`Reported` 还是 `Inferred`

优先级规则：

- 高 `Importance` + 弱 `Evidence` = 最先验证
- 如果问题假设还没站稳，不要先验证功能细节

### 输出格式

```md
## Hypothesis Teardown: [产品 / 功能]

| # | 假设 | 类型 | Importance | Evidence | 优先验证 |
|---|------|------|------------|----------|----------|
| 1 | ... | Problem severity | 高 | Inferred | ✓ |

### Highest-Risk Assumption
- ...

### Cheapest Falsification Step
- ...

### Decision
- Proceed / Probe / Narrow / Kill
- 原因:
```

## C. Role Simulation

### 目标

模拟用户在关键决策节点为什么会犹豫、放弃或不切换。

它的用途是暴露阻力，不是证明需求存在。

### 使用约束

开始前先写清：

- 角色是谁
- 这个角色的依据来自哪些 `Observed / Reported` 线索
- 哪些部分只是 `Inferred`

如果没有任何可引用线索，角色扮演只能作为“假设探索”，不能当成结论。

### SOP

只模拟 3-5 个关键节点：

1. 发现问题
2. 评估是否值得尝试
3. 首次尝试 / 接入 / 使用
4. 付费 / 持续使用 / 回到旧方案

每个节点都输出：

- 我看到了什么
- 我想完成什么
- 我最担心什么
- 我会继续 / 暂停 / 放弃，为什么

### 输出格式

```md
## Role Simulation: [用户类型]

### Assumption Basis
- Observed:
- Reported:
- Inferred:

### Decision Nodes
**[节点 1]**
- 看到了什么:
- 想完成什么:
- 担心什么:
- 决定:

### Frictions
- 最大阻力:
- 缺失证据:
- 哪个需求判断仍未被证明:

### Decision
- Proceed / Probe / Narrow / Kill
- 原因:
```

## D. Feedback Synthesis

### 目标

把零散反馈变成结构化需求信号，而不是逐条摘抄。

### SOP

**Step 1 — 先分四类**

- `Symptom`：用户遇到了什么麻烦
- `Desired outcome`：用户真正想达成什么
- `Workaround`：用户现在怎么勉强完成
- `Resistance`：为什么不愿继续用现有方案或新方案

**Step 2 — 合并模式**

只有满足以下条件，才能升格为“洞察”：

- 至少 2 条反馈指向同一根因
- 能说清根因，不只是功能请求表面相似

**Step 3 — 转成 JTBD**

把每个模式写成：

```text
当 [情境] 时，[哪类用户] 想要 [动作 / 能力]，这样就能 [结果 / 避免损失]
```

**Step 4 — 排优先级**

优先级按：

`频率 × 情绪强度 × workaround 成本`

如果只是高频吐槽但成本很低，不要误判成高价值需求。

### 输出格式

```md
## Feedback Synthesis: [产品 / 功能]

### Patterns
**Pattern #1**
- Symptom:
- Desired outcome:
- Workaround:
- Resistance:
- JTBD:
- Priority: 高 / 中 / 低

### Decision
- Proceed / Probe / Narrow / Kill
- 原因:
- 最值得补的证据:
```

## 常见反模式

| 反模式 | 症状 | 修复 |
|--------|------|------|
| `功能代替需求` | 讨论停留在“用户想要某功能” | 追问“这样我就能避免什么损失 / 达到什么结果” |
| `喜欢代替需要` | 用户说“挺好”“有趣”就当成需求 | 追问是否有频繁触发、真实代价和当前 workaround |
| `角色扮演充当证据` | 模拟出的用户反应被写成结论 | 明确标记为 `Inferred`，并补真实验证动作 |
| `忽略现有 workaround` | 只谈理想方案，不看用户现在怎么凑合 | 先理解现状成本，再判断有没有切换动力 |
| `单一用户幻觉` | 把一个人的反馈当成整类用户 | 分开细分用户、触发情境和证据来源 |
| `确认偏误` | 只搜支持当前方案的材料 | 强制补一句：“为什么用户可能根本不在乎？” |
