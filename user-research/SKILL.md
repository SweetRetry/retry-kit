# User Research

无需真实访谈的用户需求挖掘框架。核心思路：把"我觉得用户想要 X"转化为"用户在 Y 场景下，因为 Z 原因，需要完成 W 任务"。

**Output language**: 跟随用户语言。框架术语（JTBD、Jobs、Pains、Gains、Assumption）保持英文。

---

## I. 三种工作模式

根据用户输入自动选择，无需用户指定：

| 模式 | 触发信号 | 核心产出 |
|------|----------|----------|
| **A. 假设拆解** | "我觉得用户会..."、不确定某功能是否值得做 | 暴露隐含假设 + 验证优先级排序 |
| **B. 角色扮演** | 想模拟用户决策、想测试产品流程 | 模拟目标用户的真实反应与阻力 |
| **C. 反馈分析** | 有现成用户反馈（评论/私信/对话） | 提炼痛点模式 + JTBD 转化 |

---

## II. 模式 A：假设拆解

### 目标

把产品构建者的直觉拆解成可验证的假设清单，识别哪些假设风险最高。

### SOP

**Step 1 — 提取假设**

从用户描述中提取所有隐含假设，格式：

```
假设 #N：[用户群体] 在 [场景] 下 [会做某事 / 有某需求 / 接受某方案]
```

**Step 2 — 风险评级**

每条假设评两个维度：

| 维度 | 问题 | 评级 |
|------|------|------|
| **重要性** | 如果这条假设是错的，产品核心价值还成立吗？ | 高 / 中 / 低 |
| **确定性** | 你现在有多少证据支持这条假设？ | 有证据 / 推测 / 无依据 |

**Step 3 — 验证优先级**

重要性高 + 确定性低 = 最优先验证。输出优先级排序 + 最小验证动作建议。

### 输出格式

```
## 假设拆解：[产品/功能名]

### 假设清单

| # | 假设 | 重要性 | 确定性 | 优先验证 |
|---|------|--------|--------|----------|
| 1 | ... | 高 | 推测 | ✓ |
| 2 | ... | 中 | 有证据 | |

### 最高风险假设
**假设 #N**：[内容]
**为什么危险**：[如果错了，影响是什么]
**最小验证动作**：[不需要真实访谈的最快验证方式]
```

## III. 模式 B：角色扮演

### 目标

模拟目标用户在使用产品时的真实思维过程，暴露产品流程中的摩擦点。

### SOP

**Step 1 — 用户角色构建**

从用户提供的信息推断目标用户画像：

- **身份背景**：职业、技能水平、使用场景
- **当前解决方案**：他现在怎么解决这个问题（替代品）
- **核心动机**：他真正想要的结果是什么（不是功能，是结果）
- **主要阻力**：什么会让他放弃使用

**Step 2 — 场景模拟**

扮演目标用户，走一遍产品流程，在每个关键节点说出：

1. **我看到了什么** — 第一印象
2. **我在想什么** — 内心独白
3. **我的疑虑** — 让我犹豫的点
4. **我的决定** — 继续 / 放弃 / 需要更多信息

**Step 3 — 洞察提炼**

模拟结束后，跳出角色，总结：最大摩擦点、最强动机、最关键缺失。

### 输出格式

```
## 角色扮演：[用户类型] 使用 [产品/功能]

**用户画像**：[2-3 句描述]
**当前替代方案**：[他现在怎么做]

### 流程模拟

**[节点 1]**
> 👤 "..." [内心独白]
阻力：[有/无，说明]

**[节点 2]**
> 👤 "..."
阻力：[...]

### 洞察
- **最大摩擦**：[...]
- **最强动机**：[...]
- **关键缺失**：[产品目前没有但用户需要的]
```

## IV. 模式 C：反馈分析

### 目标

从现有用户反馈中提炼结构化洞察，而不是逐条阅读。

### SOP

**Step 1 — 分类**

将反馈按性质分类：痛点 / 期望 / 困惑 / 正向反馈

**Step 2 — 模式识别**

在同类反馈中找重复模式，合并为洞察条目。一条洞察 = 至少 2 条反馈指向同一根因。

**Step 3 — JTBD 转化**

将痛点/期望转化为 Jobs to Be Done 格式：

```
当 [情境] 时，我想要 [动作/能力]，这样我就能 [结果/价值]
```

**Step 4 — 优先级**

按频率 × 情绪强度排序，高频 + 强负面情绪 = 最优先处理。

### 输出格式

```
## 反馈分析：[产品/功能]

### 洞察条目

**洞察 #1**：[一句话描述模式]
- 原始反馈：[引用 1-2 条]
- JTBD：当 [情境] 时，我想要 [动作]，这样我就能 [结果]
- 优先级：高 / 中 / 低

### 行动建议
[按优先级排列的 1-3 个产品改进方向]
```

## V. 反模式

| # | 反模式 | 症状 | 修复 |
|---|--------|------|------|
| 1 | **功能代替需求** | 分析停留在"用户想要某功能"而非"用户想实现某结果" | 每个需求都必须能回答"这样我就能___" |
| 2 | **确认偏误** | 只找支持现有方案的证据 | 主动寻找"为什么用户不用这个"的证据 |
| 3 | **单一用户幻觉** | 把一类用户当成所有用户 | 明确区分不同用户细分，分别分析 |
| 4 | **假设跳跃** | 从"用户有这个痛点"直接跳到"我们的方案能解决" | 中间必须有"用户会接受这种解决方式"的假设验证 |

---

## VI. 与其他 skill 的衔接

- **产出 → value-realization**：将挖掘出的 JTBD 和用户动机作为输入，用 value-realization 验证价值路径是否清晰
- **产出 → product-guide**：将验证后的需求作为输入，用 product-guide 审计功能实现方案的 ROI
