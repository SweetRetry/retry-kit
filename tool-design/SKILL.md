# AI Agent Tool Design

设计 agent tool 的目标，不是把已有 API 原样暴露出去，而是降低 agent 完成任务的总协调成本：

- 容易选对工具
- 容易生成合法参数
- 容易从结果里继续推理
- 容易在失败后恢复
- 不把 context window 浪费在无关数据上

## 先定边界

这个 skill 处理：
- MCP tools
- OpenAI function calling / Apps SDK tools
- 其他面向 LLM/agent 的工具 schema
- 工具粒度、参数结构、结果结构、错误语义、分页/长任务设计

这个 skill 不处理：
- 业务逻辑本身是否正确
- 后端内部实现细节
- UI 视觉设计
- 权限体系的全局架构重构

输出物默认是以下其一：
- 新工具方案
- 现有 tool schema 审查结论
- 从 CRUD API 到 agent-friendly tools 的重构建议

## 核心原则

### 1. 先按任务设计，再按接口实现

从用户要完成的任务出发，不要从数据库表或 REST 路由出发。

优先问：
- agent 真实要完成的任务是什么？
- 哪些步骤总是一起发生？
- 哪些步骤必须原子执行？
- 哪些步骤失败后需要单独重试？

反模式：

```text
create_node
update_node
list_nodes
delete_node
create_edge
update_edge
```

更好的方向：

```text
batch_edit_canvas
find_canvas_nodes
get_canvas_slice
```

如果一个工具名听起来像数据库操作，而不是任务动作，通常粒度太底层。

### 2. 默认设计“任务级工具”，不要两头极端

避免两种极端：
- 一个操作一个 tool，导致大量 round-trip
- 一个“万能 mega-tool”，输入 DSL 过大，模型难以稳定生成

使用这个判断规则：

适合合并为一个工具：
- 多个步骤几乎总是一起使用
- 需要原子性或共享校验
- 中间状态暴露出来没有意义
- 合并后能明显减少调用次数

适合拆成多个工具：
- 权限、风险或副作用不同
- 输入结构差异很大
- 返回结果类型差异很大
- 常见调用路径明显分叉
- 某一步经常需要单独重试或单独分页

默认目标不是“工具越少越好”，而是“完成常见任务所需的调用次数和认知负担都尽量低”。

### 3. Tool selection 成本和执行成本同样重要

模型先要选对工具，才能谈执行效率。

每个工具都要把以下信息写进 `name` / `description` / annotations：
- 这个工具解决什么任务
- 什么时候该用
- 什么时候不要用
- 是否只读
- 是否有副作用或破坏性
- 输入里哪些字段最关键
- 调用成功后通常下一步做什么

优先让工具名体现任务，而不是内部实现。

```text
差：run_operation
差：node_mutation
好：batch_edit_canvas
好：search_orders
好：start_export_report
```

如果平台支持，显式使用行为提示：
- `readOnlyHint`
- `destructiveHint`
- `idempotentHint`
- `openWorldHint`

不要把这些提示当成安全边界。真正的权限和校验必须由服务端执行。

### 4. 输入 schema 要严格，但不要逼模型写没必要的字

输入设计原则：
- 字段名直接表达业务语义
- 枚举优于自由文本
- `additionalProperties: false`
- 必填项尽量少但关键约束必须明确
- 对可推断值给安全默认值
- 不要求模型重复提供服务端已知上下文

当输入同时包含“结构化控制参数”和“大段自由文本”时，优先拆开思考：
- 结构化部分保留在 schema
- 高熵文本保留为自然语言或专门字段

如果任务本质是代码、查询语句、长提示词或其他自由文本输入，优先考虑允许自由文本的工具，而不是把文本硬塞进复杂 JSON 嵌套。

### 5. 返回结果要为“下一步推理”服务

tool result 不是日志，也不是原始数据库快照。

返回结果至少要帮助模型回答这 4 个问题：
- 这次成功了吗？
- 产生了哪些关键对象或状态变化？
- 如果失败了，失败在哪？
- 下一步应该继续什么动作？

优先返回：
- 紧凑的结构化结果
- 稳定 ID / handle / cursor / status
- 必要摘要，而不是全部原始数据

不要默认返回：
- 大块重复文本
- 无上限嵌套对象
- 调试字段洪水
- 只有人能读懂的自然语言说明

如果平台支持结构化输出，优先提供 `outputSchema` / `structuredContent`；把只给组件或前端用的额外数据放到隐藏元数据，而不是全部塞给模型。

### 6. 读取类工具必须原生支持控量

agent 读取数据不是“一次性 dump 全世界”，而是滑动窗口式地逐步探索。

读取类工具至少提供一类控量机制：
- `limit`
- `cursor`
- `fields`
- `depth`
- `sort`
- `filter`

默认优先 cursor 分页，而不是 offset 分页。只要结果集可能变化，offset 很容易漏读或重读。

推荐模式：

```json
{
  "query": "active enterprise customers",
  "cursor": "abc",
  "limit": 50,
  "fields": ["id", "name", "plan", "updatedAt"]
}
```

如果对象很大，优先拆成：
- `search_*`：返回轻量列表
- `get_*`：按 ID 取详情

不要把“搜索 + 全量详情 + 深层子树”绑死在同一个默认返回里。

### 7. 写操作要考虑原子性、幂等性和恢复

批量写入不是目的，减少脆弱中间状态才是目的。

写操作优先考虑：
- 是否需要原子执行
- 是否需要回滚
- 是否支持 `idempotencyKey`
- 是否支持只重试失败子集
- 是否要返回每一步的结果索引

适合 batch 的常见场景：
- 一个用户动作引发多个对象变更
- 需要共享校验上下文
- 中间状态无业务意义

不适合 batch 的常见场景：
- 单次操作成本很高，失败代价大
- 每步都可能触发独立审批
- 每步结果都要被模型单独判断后再继续

如果支持批处理，结果里要明确逐项状态，而不是只返回一句“partial failure”。

### 8. 长任务不要伪装成同步工具

如果操作可能超时、排队、异步生成或依赖外部系统，不要强行设计成同步一次完成。

优先模式：
- `start_*`：启动任务，返回 `jobId`
- `get_*_status`：查询状态/进度
- `cancel_*`：可选，允许取消

返回中明确：
- `jobId`
- `status`
- `pollAfterMs` 或等价提示
- 最终结果在哪里读取

不要让模型通过不断重试同一个写工具来“猜”任务有没有完成。

### 9. 错误必须机器可分流，不要靠 message 猜

错误返回要稳定、枚举化、可恢复。

至少包含：
- 稳定错误码
- `retryable`
- 定位信息：字段、路径、operation index
- 恢复建议：如减少 batch 大小、补权限、稍后重试

推荐区分：
- 不可重试：校验错误、权限缺失、资源不存在、schema 不匹配
- 可重试：限流、暂时不可用、冲突重试、超时

如果是批处理，允许局部失败时必须返回逐项结果，不要让模型重新做整批猜测。

### 10. 人类审批和服务端约束不能交给模型自觉

对于破坏性、不可逆、跨权限边界的操作：
- tool description 要明确风险
- 如果平台支持，标记 destructive 行为
- 服务端必须再次校验权限和前置条件
- 需要人工确认的动作就设计显式确认步骤

不要依赖“模型应该知道这很危险”。

## 设计流程

### Step 1: 先列真实任务，而不是 API 清单

先写出 3-5 个真实任务，例如：
- “找到符合条件的客户并读取必要详情”
- “对一个画布做一组原子编辑”
- “启动导出并轮询最终结果”

如果当前输入已经是接口列表，把它们反推回用户任务。

### Step 2: 为每个任务决定粒度

对每个任务判断：
- 单工具完成，还是多工具协作？
- 是否需要 batch？
- 是否需要分页/游标？
- 是否需要 start/status 两段式？

输出时明确说明为什么合并、为什么拆分。

### Step 3: 定义工具契约

每个工具至少写清：
- `name`
- `description`
- `input schema`
- 关键约束
- 返回结构
- 错误结构
- 是否只读 / destructive / idempotent

如果用户给的是现有 schema，优先指出：
- 工具太多还是太少
- 描述是否足够让模型选对
- 参数是否过于底层
- 返回是否过大或不可继续推理

### Step 4: 审查 agent loop

逐步模拟一次调用链：
1. 模型能否只靠 description 选到对的工具？
2. 能否稳定生成合法参数？
3. 返回结果是否足够支持下一步？
4. 失败后是否知道该重试、改参还是停止？

如果其中任一步需要“猜”，接口还没设计好。

## 常见反模式

| 反模式 | 问题 | 更好的做法 |
|---|---|---|
| 直接暴露 CRUD tool | 调用次数多，模型要自己拼工作流 | 暴露任务级工具 |
| 一个万能 mega-tool | 描述不清，参数难生成，失败难恢复 | 拆成少量高内聚工具 |
| 描述只有一句话 | 模型容易选错工具 | 写清使用时机、禁用时机、风险和返回 |
| schema 太松 | 模型生成歧义参数，服务端难校验 | 枚举化、严格 schema、禁止额外字段 |
| 结果全量 dump | 挤爆上下文，后续推理成本高 | 返回摘要、cursor、ID、可继续读取的句柄 |
| 所有操作都同步 | 长任务不稳定，模型只能盲重试 | `start_*` + `status_*` |
| 只返回自然语言错误 | 模型无法程序化恢复 | 稳定错误码 + retry hint + 定位信息 |
| 把安全寄托给提示词 | 模型可能误调用破坏性操作 | 服务端强校验 + 明确审批步骤 |

## 平台对齐提示

- MCP 场景：优先用工具注解表达只读/破坏性/幂等特征；结果要区分模型可见内容和隐藏元数据。
- OpenAI function calling：优先严格 schema；函数名和参数描述要足够清楚，必要时开启 strict mode。
- OpenAI Apps SDK：优先同时设计模型可见的 `structuredContent` 和组件专用 `_meta`，不要把 UI 所需大对象全部暴露给模型。
- Anthropic tool use：description 要写得足够具体，必要时明确并行调用、调用前提和参数构造方式。

## 使用时的语气和判断

- 不要机械地要求“必须 batch”。
- 不要为了追求优雅，把工具表面做成只有作者自己看得懂的 DSL。
- 当用户已经有现成接口时，优先给出最小重构路径，而不是要求整套推倒重来。
- 如果某条建议明显依赖具体平台能力，明确标注它是平台相关，而不是通用铁律。
