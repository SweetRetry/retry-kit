# Lark PRD

PRD 是让产品、设计、研发、测试对**同一个用户问题和完成标准**达成共识的决策文档，不是功能清单，也不是给已有方案补论证。每写一节，先问它对哪个决策有用。

## 1. 定读者与决策

动笔前明确：

- 谁读这份 PRD，据此要做什么决定（评审、排期、联调、验收；研发与测试侧由 Agent 取用需求内容时计入读者，信息完整度门槛随之提高）；
- 方向与投入是否已定：未定先收敛方向，本 skill 只把已定方向写成可交付需求；
- 已知证据（用户反馈、行为数据、工单、研究；提出人意图、当前优先级、研发技术边界这类内部背景，落到会议结论或沟通记录后才计入证据，仍只在口头或聊天里的标为假设）与关键未知；
- 会实质改变范围但缺失的信息：集中询问关键项；可继续起草的假设显式标出，阻塞范围或验收的未知项不得当作已定需求。

修订已有 PRD 时，先按第 6 步读取现状与改动范围，再定点编辑。

评审状态、提出人、负责人、排期和目标值均须有可追溯依据；未知项标待确认，并记录确认人与时点。生成文档不代表通过评审。

完成标准：能用一句话说清“让谁在什么范围内、就什么可观察结果形成共识”，且每个假设都能连到会改变哪项需求或范围；只存在于口头或人脑中的前提须写进正文或显式标为假设。

## 2. 按决策搭 section

新建或重排章节时，读取 [prd-sections.md](references/prd-sections.md)，按每节支撑的决策选择内容。定点修订只检查受影响章节，不加载完整章节矩阵。

完成标准：每节都有对应决策；范围、非目标、需求与验收可互相追踪。

## 3. 把需求写成可观察结果

术语与用词规范全文一致（正文、验收、画板、变更记录）：

- 同一对象全文只用一个词，并与 UI 文案一致；不换同义词，不用内部项目代号；
- 需求标强度：必须 / 应当 / 可选，并写明未满足时是否阻塞验收；不写“建议、可以考虑、最好”；
- 状态写成名词（待支付、已支付），触发与动作写成事件（提交、支付成功），两者不混用；
- 不出现不可验证的评价词与模糊量词（流畅、稳定、大量、尽快）和行业黑话（赋能、打通、闭环），改为可观察结果或标待确认；
- 全文表达须无歧义：明确指代对象、条件间的逻辑关系、适用范围及数量或时间边界。若存在会导致不同产品行为或验收结论的合理解释，须改写为明确规则；依据不足时列为待确认，不自行选定一种解释；
- 实现取舍（架构、接口）留给技术文档；验收验结果，可用 Given/When/Then，并逐条标明是可由程序或下游 Agent 核对，还是需人判断——可核对的给机器可判定的条件，需人判断的写清由谁依据什么判断；
- 大而不可测的需求拆到单条可验收粒度；
- 涉及界面交互时，关联原型、设计稿、既有组件库与 UI 规范或明确的交互约束，并对应到需求 ID；尚未确定且影响验收的交互列为开放问题。设计与正文冲突时先明确有效要求，再同步相关内容，流程画板不能代替交互依据；
- 无用户证据时收窄为显式假设加研究计划，并标出它会影响哪个决策。

完成标准：研发、测试及其下游 Agent 能只凭该节判断“做完了没有”，且无需猜测实现细节。

## 4. 业界实践（按需）

涉及方向选择、方案对比或行业惯例时写这节；纯内部流程可省略。

来源用可复核的一手材料（产品文档、公开案例、财报、标准）。要采用就回到第 3 步写成可验收需求。

完成标准：每条实践都能指出它改变了或校准了哪个需求或范围判断。

## 5. 用画板表达流程

先判断内容关系，再选表达：

- 有分支、回路、多角色协作、状态迁移、时序依赖时用画板（Mermaid）：关系本身就是信息，文字会把它藏住；
- 单线 3–5 步且无分支时用列表，不强行画板；
- 精确字段对比用表格。

一图一主题，多个独立流程拆多张画板。画板节点、状态、角色名与需求正文一致，正文引用节点而非复述箭头。图型选择与写法见 [references/lark-cli-recipes.md](references/lark-cli-recipes.md)。

完成标准：每张画板只回答一个“怎么流转/何时进入什么状态”的问题；不看正文也能读出主路径与主要失败路径。

## 6. 创建或修订飞书文档

命令、XML 骨架与校验方法见 [references/lark-cli-recipes.md](references/lark-cli-recipes.md)。按任务选择写入路径：

- **新建**：一次创建正文与所需画板；用 `<whiteboard type="mermaid">` 内联在对应需求章节。
- **修订**：先读取上游 `lark-doc` 及其 `references/lark-doc-update.md`，按原文定位受影响内容，定点更新需求、验收、范围、指标和交互引用；保留无关内容。涉及已有画板时读取上游画板工作流，复用原 token 更新，不另建一份 PRD。
- **验证**：写入后回读受影响正文；新增或改动画板须导出预览，检查实际渲染及图文一致性。确认有效改动后按第 7 步记录，并回读核对；未成功写入的改动不得记为已完成。

自定义 SVG、视觉精修与已有画板的编辑机制交给上游 `lark-whiteboard` / `lark-doc`，入口见操作参考。

## 7. 维护需求变更记录

正文只呈现当前有效需求，变更记录是**只追加的账本**：旧内容及变化原因留在记录中，不删除、不改写历史条目；记录有误时追加更正并指向原条目。

- 同一需求的修订保留 ID；新增需求分配新 ID，删除后的 ID 不复用；拆分、合并或替代时分配新 ID，并在记录中写明旧 ID → 新 ID 的关系。
- 每条记录写：日期 / 版本 / 需求 ID / 变更类型 / 变更内容 / 原因 / 影响面（范围·排期·指标·兼容）/ 提出人 / 状态。修改写清旧要求 → 新要求，删除保留旧要求，原因写判断情境（何时、哪次会议或哪份结论、为什么调整），足以让无上下文的人复原当时判断；影响面写实际变化或待确认项。
- 首次建文档就带该 section，首版记录覆盖全部实际需求 ID；修订没有历史记录的文档时，只记录本次观察到的基线与变更，不补造历史。后续定点追加，命令见 [references/lark-cli-recipes.md](references/lark-cli-recipes.md)。

完成标准：当前正文、验收及图示一致；需求能追到首版、本次基线或后续变更，拆分、合并及替代关系可追踪，历史条目完整未改写。

## 输出

交付文档 URL/token，并说明：基于哪些证据、哪些是假设、哪些需求待确认、画板对应哪些流程、变更记录新增了什么。缺口与阻塞显式列出。
