# PRD Sections

按“问题 → 旅程 → 目标 → 边界 → 场景 → 需求 → 异常 → 约束 → 切换 → 依赖”推进，不为凑完整感保留无对应决策的小节。

| Section | 必须回答 | 常见失败 |
| --- | --- | --- |
| 背景与问题 / 证据 | 哪类用户在什么情境下遇到什么问题，证据是什么 | 用功能或内部偏好冒充用户问题 |
| 用户旅程 | 用户为何在此刻产生这个需求：触发与动机、当前如何凑合、端到端接触点与关键摩擦、期望结果 | 写成功能流程图；只写用上产品之后，丢掉需求产生的原因和现有替代做法 |
| 目标与成功指标 | 哪个可观察结果变化，指标口径、来源、时间窗；数据是否可取得、由谁在何时复盘；取不到时列明获取方式与依赖，结论保持待验证；护栏指标：哪个既有结果不允许变差，越线时停止或收敛范围 | 目标写成“提升体验”，把功能验收通过当作效果达成 |
| 范围与非目标 | 这次做什么、明确不做什么及原因；涉及取舍或分期时，优先级、交付批次及依据，哪些需求必须一起交付 | 缺非目标；资源不足时无法判断先交付什么 |
| 场景 / 用户任务 | 本产品需支持的任务链及其正常路径 | 按功能罗列，而非按用户任务 |
| 业界实践 | 行业里谁在什么约束下怎么做、来源与时间、可迁移什么、关键差异 | 把竞品功能直接当需求 |
| 行为需求与验收 | actor + 触发/前置 + 可观察结果 + 失败边界，逐条可验收；配稳定需求 ID 供验收与变更追踪（语义见主文档的需求变更记录） | 需求暗藏实现，验收用形容词 |
| 异常与边界 | 失败、空、权限、并发、恢复后的最终状态 | 只写正常路径 |
| 质量约束 | 只在真实风险或标准要求时纳入，且给可验证门槛 | 机械填安全/性能模板 |
| 兼容与切换 | 存量数据、旧版本入口与既有行为的用户在切换期看到什么；切换失败或回滚后落到哪个最终状态（节奏与开关实现归技术方案） | 只写新用户的新行为，旧数据与旧版本行为未定义 |
| 依赖与开放问题 | 依赖方、阻塞项、owner、下一步 | 开放问题藏进脚注 |

完成标准：每节都能回答“删掉它哪个决策会受损”；范围、非目标、需求与验收之间可互相追踪。
