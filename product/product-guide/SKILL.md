# 产品诊断

从用户能否完整获得产品价值出发，处理两个问题：

1. **产品边界**：在什么用户、入口、状态或组合条件下，产品没有提供完整链路？
2. **产品价值**：这项功能是否值得它消耗的用户注意力与工程维护成本？

先判断用户能否走通，再判断这条链路是否值得复杂度。不要用代码正常运行代替产品链路成立，也不要把视觉风格偏好当成产品问题。

## 选择分析 branch

- 用户要求 product edge cases、用户链路、interaction flow、异常状态或体验断点时，只执行“产品边界分析”。
- 用户要求产品逻辑、功能价值、简化、取舍或 ROI 时，只执行“产品价值审计”。
- 用户要求宽泛的“产品审查”时，先执行产品边界分析，再基于已确认的用户链路执行产品价值审计。

产品边界 branch 只发现和报告缺口，不提供 redesign、实现方案或优先级。产品价值 branch 可以给出保留、简化、删除或加固建议。用户同时要求落地修改时，先完成诊断，再把修改作为独立任务。

## 共享起点：建立产品 contract

检查用户提供的页面、原型、PRD、路由、交互实现、状态文案、测试或真实产品。明确：

- 产品向谁承诺什么结果；
- 本次用户是谁，处于什么角色、资格和历史状态；
- 用户从哪里进入，当前想完成什么任务；
- 什么可观察结果才算成功；
- 哪些业务规则、权限或生命周期状态约束这条链路；
- 当前处于 MVP、增长期还是成熟期。

材料不足时，从实际界面与行为建立 provisional contract，并把可能改变结论的信息列为待确认。完成共享起点时，目标用户、任务起点、成功状态与关键约束都应明确。

# Branch A：产品边界分析

## 1. 画出用户任务闭环

不要只按页面顺序复述 UI。围绕一个用户目标画出完整链路：

**进入 → 识别当前位置与条件 → 找到行动入口 → 理解并执行 → 看见进行状态 → 得到明确结果 → 继续下一步或恢复**

同时标出：

- 主入口、导航入口、direct URL、deep link、通知、邮件、分享链接和浏览器返回；
- 首次用户、回访用户、游客、已登录用户、不同角色、不同套餐或资格；
- landing、注册、onboarding、首次获得价值、重复使用、协作、付费、流失、回访和 offboarding；
- empty、loading、ready、blocked、pending、partial、success、failed、cancelled、expired、archived、deleted；
- modal、drawer、表单、编辑器、上传、checkout 等局部 interaction flow；
- 页面、会话、设备、渠道和角色之间的 handoff。

完成本步时，每个目标用户都应有可进入的起点、可识别的成功终点，以及失败、退出或中断后的去向。

## 2. 逐层检查产品链路

对当前任务实际涉及的层面逐一检查：

- **发现与入口**：用户是否能找到入口；从外部链接或非理想入口进入时是否仍有上下文；
- **定位与理解**：用户是否知道自己在哪里、操作哪个对象、当前状态和前置条件；
- **行动与决策**：可执行动作是否可见；选项、默认值、限制和后果是否足以做决定；
- **过程与反馈**：点击后是否有 loading、progress、排队、处理中或 partial 状态；重复操作会被如何理解；
- **结果与下一步**：成功、失败、阻塞和空结果是否清楚；用户是否知道接下来能做什么；
- **恢复与退出**：是否能 retry、resume、undo、cancel、返回或安全退出；输入与进度是否保留；
- **连续性**：刷新、返回、多 tab、session 过期、重新登录、跨设备后是否恢复正确任务和上下文；
- **旅程阶段**：landing、注册、onboarding、activation、重复使用、协作、付费、流失与回访之间是否存在可达的下一步；
- **生命周期**：创建、编辑、提交、发布、暂停、完成、取消、删除、恢复、过期后是否都有产品表现；
- **角色与协作**：owner、成员、访客、被邀请者、权限变化和所有权转移后是否仍有合理路径；
- **商业状态**：trial、quota、paywall、升级、降级、续费失败、取消、退款和 entitlement 变化是否形成闭环；
- **跨渠道交接**：站内、邮件、通知、分享、外部支付或第三方授权返回后是否落在正确状态；
- **信任与后果**：付款、发布、删除、共享、授权和隐私变化前后，用户是否理解对象、范围、可逆性与最终结果；
- **内容与使用条件**：零条、单条、大量数据、长文本、本地化、时区、移动端、键盘和 assistive technology 是否改变任务可完成性。

每层都做适用性判断，不机械制造问题。完成本步时，所有适用层都应有明确结论，不能只检查主页面与 happy path。

## 3. 推演缺失和断裂

改变用户进入和完成任务的条件：

- 从首次使用切换到已有历史、被邀请、失去权限或重新获得权限；
- 从产品内导航切换到 deep link、通知、浏览器返回或登录后的 redirect；
- 在操作前、操作中、结果返回前和完成后刷新、离开、返回、重复点击或切换设备；
- 让数据从空到一条、多条、极长、过期、被他人修改或已删除；
- 让任务跨越 session、角色、套餐、quota、审批、付款或异步等待；
- 组合两个单独合理的条件，例如“session 过期 + 未保存输入”“降级 + 已有超额数据”“资源删除 + 旧通知”“退款 + 仍在履约”。

重点识别：

- **死路**：用户进入某状态后没有继续、退出或恢复路径；
- **孤儿状态**：业务状态真实存在，但产品没有展示、解释或可执行动作；
- **缺失转换**：两个合法状态都存在，用户却无法从一个到达另一个；
- **幽灵入口**：入口可见，但当前用户或状态永远无法完成其承诺；
- **结果歧义**：用户无法判断操作未开始、进行中、成功、失败还是部分完成；
- **恢复缺口**：失败后只能重来，或 retry、返回、重新登录会丢失上下文；
- **上下文断裂**：跨页面、渠道、设备、角色或时间后，产品忘记用户原本的对象与目标；
- **权限陷阱**：产品允许用户开始任务，却在中途因权限或归属阻断且无合理去向；
- **商业陷阱**：quota、paywall、降级或退款改变 entitlement 后，已有任务和数据没有可理解状态。

从断点继续追踪用户实际会看到什么、下一步最可能做什么，以及是否会形成重复提交、误操作、放弃、信任损失或无法获得核心价值。

完成本步时，每个候选项都应说明产品链在哪一环断裂，并覆盖断裂后的用户去向，而非停在“缺少某个页面或按钮”。

## 4. 建立证据链并反证

每个产品边界包含：

**用户与上下文 → 想完成的目标 → 进入方式与当前状态 → 产品应提供的下一环 → 实际缺失或矛盾的链路 → 用户可观察后果 → 证据**

按证据定级：

- **已确认**：页面、原型、路由、运行行为、测试或明确 contract 直接证明缺口存在；
- **高可信推断**：已知页面与状态足以推出断点，但尚未运行完整 journey；
- **待确认**：现有材料指向具体缺口，但另一个未检查入口、角色或 contract 可能改变结论。

尝试从其他入口、隐藏状态、既有页面和明确业务规则推翻候选项。单张截图中没看到某个入口，不足以证明整个产品没有该入口；纯审美偏好、一般可用性建议、工程实现风险和没有具体用户目标的理论可能性不形成产品边界。

## 5. 覆盖收口

结束前确认：

- 每个目标用户和角色都有入口、成功终点与失败去向；
- 每个适用产品状态都有可理解的表现和下一步；
- 每个关键动作都有开始、进行、成功、失败、取消与恢复语义；
- deep link、返回、刷新、重新登录和跨渠道交接不会遗失目标上下文；
- 权限、生命周期和商业状态变化已与主任务组合检查；
- 每个发现都来自具体用户链，不是页面 checklist；
- 同一根因和用户后果只保留一次，可信度与证据一致。

完成本 branch 时，所有适用层都有结论，所有发现都经受过反证，所有未知都具体到会改变哪条判断。

## 产品边界输出

使用自然语言，从最阻断核心用户目标的发现讲起。每个发现用一小段连贯说明讲清用户是谁、在什么上下文进入、链路断在哪里、最终看见什么、为什么无法完成目标，以及证据和必要的不确定性。

按用户目标和根因合并发现，不套固定表格或页面清单。范围内没有成立的产品边界时，直接说明“未发现有证据支持的产品链路缺口”，并确保结论来自完整 journey，而非只看 happy path。

# Branch B：产品价值审计

## 1. 判断用户价值

回答：用户完成这项功能后，工作、决策或结果发生了什么变化？如果无法用一句用户结果说明价值，标记为价值不明；如果价值成立但路径绕远，进入简化判断。

检查价值是否服务产品核心承诺，是否由真实需求、使用行为或明确业务约束支持，以及该价值在当前产品阶段是否必要。

## 2. 判断用户成本

检查用户为了获得价值承担的：

- **决策成本**：选择过多，缺少依据或默认值；
- **学习成本**：需要理解产品内部概念才能继续；
- **等待成本**：在获得价值前经历验证、审批、配置或阻塞；
- **重复成本**：反复输入、配置、确认或跨页面搬运信息；
- **切换成本**：任务被拆散到多个页面、渠道、角色或工具；
- **风险成本**：操作后果不清、不可逆或难以恢复。

不要把所有步骤都视为摩擦。只有不能降低风险、建立必要信任或交付用户价值的步骤，才是可删减成本。

## 3. 判断产品与工程成本

检查功能引入的状态数量、配置面、权限组合、数据与兼容性负担、支持与运营流程、故障面和后续变更阻力。以真实代码、事故、工单、变更频率或流程复杂度为证据；没有证据时标记为推断。

同时判断 opportunity cost：维护这项功能是否挤压更核心的产品承诺，而不是只问它有没有任何价值。

## 4. 给出产品判定

- **删除**：用户问题不成立，或能由更低成本的既有能力满足；
- **简化**：用户问题真实，但步骤、配置、概念或状态多于交付价值所需；
- **保留**：价值清晰，用户与维护成本合理；
- **加固**：价值高，但产品边界或实现脆弱已威胁核心承诺。

完成判定时，每项结论都应同时关联用户结果、产品阶段、用户成本和维护证据。不要用数字评分代替判断。

## 产品价值输出

先用一句话说明功能解决的用户问题，再说明关键用户成本与维护成本，最后给出删除、简化、保留或加固判定及其依据。只有“简化”或“加固”需要给出方向性建议；存在真实取舍时，明确不同选择牺牲什么。

不要用“用户可能喜欢”或“best practice”支撑结论。证据不足时说明缺少什么，不把假设包装为 ROI 事实。
