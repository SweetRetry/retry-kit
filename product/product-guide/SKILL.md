# Product Guide

判断一项 feature 是否值得它消耗的用户注意力与产品、工程维护成本。

以用户结果为价值单位，以产品阶段和真实证据约束判断。分析对象是“这项能力是否值得存在，以及应保留到什么复杂度”；用户任务链的可完成性、客户端交互边界、视觉质量和工程异常属于各自独立问题。

本 skill 可以给出删除、简化、保留或加固建议。用户同时要求落地修改时，完成价值诊断后继续完成原请求中已授权的实现和验证；仅在存在尚未授权的实质取舍时澄清。

## 1. 建立价值 contract

检查用户提供的 PRD、页面、原型、代码、指标、用户反馈、工单或商业规则，明确：

- 产品向哪类用户承诺什么结果；
- 用户完成该 feature 后，工作、决策或结果发生什么可观察变化；
- 该结果如何服务产品的核心承诺；
- 当前处于 MVP、增长期还是成熟期；
- 哪些角色、合规、商业或运营约束使复杂度不可省略；
- 有哪些使用、留存、收入、支持或维护证据。

无法用一句用户结果说明价值时，标记为价值不明。材料不足时建立 provisional contract，并把会改变判定的事实列为待确认。

完成本步时，目标用户、预期结果、产品阶段、必要约束与证据范围都应明确。

## 2. 判断用户价值

检查该 feature 是否：

- 解决真实、重复或高后果的问题，而非只增加可选项；
- 让用户更快、更准确或以更低风险获得核心结果；
- 由用户行为、反馈、业务规则或明确战略约束支持；
- 相比既有能力提供不可替代的增量，而不是换一种入口重复同一价值；
- 在当前产品阶段必要，而非把未来可能需要的能力提前转嫁给当前用户。

区分“有人能使用”“有人表达兴趣”和“产生可验证结果”。价值成立但路径或概念过重时，继续进入简化判断。

完成本步时，每项声称的价值都应关联具体用户结果和证据；证据不足的部分明确标记为推断。

## 3. 判断用户成本

检查用户为了获得价值承担的：

- **决策成本**：选项过多，缺少判断依据或安全默认值；
- **学习成本**：必须理解产品内部概念才能继续；
- **等待成本**：在获得价值前经历配置、验证、审批或阻塞；
- **重复成本**：反复输入、配置、确认或跨 surface 搬运信息；
- **切换成本**：任务被拆散到多个页面、渠道、角色或工具；
- **风险成本**：后果不清、不可逆或难以恢复；
- **持续成本**：一次启用后仍需频繁维护规则、数据或权限。

保留能降低真实风险、建立必要信任或直接交付价值的步骤。其余成本必须由增量价值解释。

完成本步时，每项用户成本都应说明由哪个产品决定产生、是否必要，以及去除后会牺牲什么。

## 4. 判断产品与工程成本

检查 feature 引入的：

- 新概念、状态、配置面和角色权限组合；
- 数据、兼容性、migration 与长期版本负担；
- 支持、运营、审批、结算或人工兜底流程；
- 故障面、可观测性需求和事故后果；
- 与相邻 feature 的职责重叠和未来变更阻力；
- opportunity cost：维护它是否挤压更核心的产品承诺。

以真实代码、事故、工单、变更频率、on-call 或运营流程为证据。没有证据时标记为推断，不把实现行数直接等同于维护成本。

完成本步时，主要持续成本均有 owner、证据或可验证假设，并能与用户价值进行同一时间尺度的比较。

## 5. 寻找更小的价值载体

围绕同一用户结果，检查既有能力、默认行为、组合方式或更窄 contract 能否提供大部分价值。比较时保持必要约束不变，避免通过删除真实需求制造虚假简化。

优先减少用户必须理解的概念、永久状态和长期维护面；只有真实用户差异需要持续独立行为时，才保留配置或分支。

完成本步时，至少明确当前方案是否已是满足真实需求的最小产品形态；若存在更小方案，说明保留了什么价值、移除了什么成本和牺牲了什么。

## 6. 给出产品判定

- **删除**：用户问题不成立，或能由成本更低的既有能力满足；
- **简化**：用户问题真实，但步骤、配置、概念或状态多于交付价值所需；
- **保留**：价值清晰，用户与维护成本合理，且没有更小的等价载体；
- **加固**：价值高，但产品或实现脆弱已威胁核心承诺，需要先降低失败成本。

逐条尝试用相反证据推翻判定：低使用是否来自难以发现，高维护是否只是一次性迁移，高复杂度是否由合规或高风险场景要求。不要用数字评分代替判断。

完成本步时，每项判定同时关联用户结果、产品阶段、用户成本、维护成本、替代方案与证据；关键未知具体到会改变哪项判定。

## 输出

先用一句话说明 feature 解决的用户问题，再说明关键用户成本与维护成本，最后给出删除、简化、保留或加固判定及依据。只有“简化”或“加固”需要给出方向性建议；存在真实取舍时，明确不同选择牺牲什么。

不要用“用户可能喜欢”或“best practice”支撑结论。证据不足时说明缺少什么，不把假设包装为 ROI 事实。
