# Simplify Code

这个 skill 的目标不是追求“更优雅”的主观风格，而是系统性判断：

1. 当前复杂度是否真的在解决问题
2. 如果不在解决问题，最小可行的简化方向是什么
3. 简化是否会改变行为边界、扩散改动半径或引入回归风险

核心产出是可落地的审查结论，不是架构口号。

## 适用场景

优先用于这些请求：

- “帮我简化这段代码 / 这个模块”
- “这里是不是过度抽象了”
- “这些 helper / service / factory / interface 该不该删”
- “review 一下这段代码有没有不必要的复杂度”
- “看看哪里可以减少层级、减少跳转、减少心智负担”
- “这个 generic / config / builder 值不值得保留”

高信号关键词：

- `simplify`
- `over-engineering`
- `abstraction`
- `wrapper`
- `factory`
- `builder`
- `orchestrator`
- `helper`
- `generic`
- `config`
- `flag argument`
- `thin layer`
- `样板代码`
- `跳转太多`
- `难读`
- `看不出主流程`

## 不适用场景

不要把这个 skill 用在下面这些问题上：

- 主要诉求是修 correctness bug、并发问题、安全问题
- 用户要的是“直接帮我重构实现”，而不是先做审查
- 主要问题是 UI 视觉规范、Tailwind/shadcn 约束
- 主要问题是项目目录布局、仓库结构、服务边界设计
- 代码之所以复杂，是因为产品逻辑本身复杂，而不是表达方式出了问题

如果目标是宏观架构减负，用 `pragmatic-architecture`。
如果目标是后端生产风险 review，用 `backend-code-quality`。

## 审查边界

这是一个“代码审查型” skill，不要默认越界到大重构。

默认边界：

1. 先判断复杂度是否多余，再谈怎么简化
2. 默认只给最小重构方向，不主动改动跨模块公开契约
3. 不因为“能抽象”就鼓励抽象，也不因为“看着重复”就立刻合并
4. 不把个人风格偏好包装成 finding
5. 不为了追求统一而牺牲局部可读性

出现这些情况前必须先与用户对齐，不要自行扩大范围：

- 需要修改公共 API / 对外 interface
- 需要合并多个模块或删除整层目录
- 需要改变异常处理、缓存、并发、事务等行为语义
- 需要为了简化而放弃向后兼容

## 核心判断原则

### 1. 简单不是“行数更少”，而是“理解路径更短”

优先看：

- 读主流程需要跳几次
- 要记住多少隐含状态
- 修改一个行为要碰几层
- 局部变更是否必须理解整套抽象

如果代码更短但更绕，不算简化。

### 2. 抽象必须服务当前变化，而不是想象中的未来

遇到这些说法，默认提高怀疑：

- “以后可能会有第二种实现”
- “先做成可配置”
- “先留一个扩展点”
- “这样更工程化”

判断问题改成：

- 现在有没有第二种真实变化
- 当前调用方是否真的需要这个能力面
- 删除这层后，今天会坏什么

### 3. 重复不是原罪，错误抽象才是

只有在下面条件成立时，抽象才值得保留：

- 重复已经稳定出现 3 次以上
- 这些重复的变化方向一致
- 抽象后调用方更容易理解，而不是更难

如果抽象内部已经堆 flag、分支、hook 点，优先怀疑它是错误抽象。

### 4. 优先暴露线性流程，减少“藏起来的逻辑”

下面这些情况通常值得简化：

- 主流程被拆进多个薄函数，必须来回跳转才能读懂
- 核心逻辑被包在 1 层又 1 层 pass-through wrapper 里
- 重要状态通过成员变量、闭包、context 隐式流动
- 只是为了“短函数”而把一个完整步骤拆碎

### 5. 局部最小化优先于体系化重写

优先给出：

- 删除一层 wrapper
- 内联一个只被用一次的 helper
- 合并两个始终一起变化的函数
- 把 3 个布尔参数改成两个清晰分支

谨慎给出：

- 整体模式迁移
- 大规模 folder 重组
- “把这一套都换成 X 架构”

## 审查前先确认的最小上下文

如果用户没说清，但代码里能直接看出来，就继续，不要为了提问而提问。

必要时先确认：

1. 审查范围是单文件、单模块还是某个 PR
2. 目标是找出“哪里复杂过头”，还是要给出可执行重构建议
3. 是否要求保持现有行为完全不变
4. 当前语言 / 框架是什么

如果用户只给一句“简化一下这段代码”，默认按“先做审查，再给最小重构方向”处理。

## 高价值复杂度信号

下面这些是信号，不是自动定罪。必须结合上下文判断“删掉会坏什么”。

### A. 无效抽象

- 只有一个实现的 interface / protocol / abstract base
- 只有一个产品路径的 factory / builder / strategy
- 没有运行时选择却仍保留 provider / resolver 层
- “通用 service” 只是转调另一个对象

### B. 薄中间层

- `controller -> service -> manager -> helper -> repo` 中多层只是在转发参数
- helper 只包了一层命名，却没有吸收复杂度
- 封装层没有缩小调用方责任，反而让追踪更难

### C. 错误抽象

- 一个抽象为了兼容多个场景不断加布尔参数、枚举参数、分支逻辑
- generic 看似复用，实则把不同语义硬塞进一个入口
- config 项越来越多，但大部分部署永远不会变

### D. 被隐藏的主流程

- 阅读主逻辑需要连续跳转 4 次以上
- 真正做事的代码淹没在 setup / wiring / adapter 中
- 顺序步骤 A/B/C 被拆散，导致排查时必须拼图

### E. 不成比例的概念数量

- 一个简单需求引入太多概念名词
- 文件数量、类数量、层级数量明显超过问题规模
- 修改一个行为需要同时理解多个“角色”但这些角色界限并不真实

## 低价值复杂度信号

下面这些不能单独作为 finding：

- 函数稍长，但线性且清楚
- 有少量重复，但各处语义并不完全一致
- 使用设计模式本身
- 代码不是你偏好的风格
- 文件多，但边界真实且各层确实承担不同职责

不要把“我不喜欢这种写法”写成“这里必须简化”。

## 审查工作流

### Step 1: 找主流程

先回答三个问题：

1. 真实业务动作从哪开始，到哪结束
2. 哪些层真的在做决策
3. 哪些层只是转发、改名或搬运参数

如果主流程都还没找到，不要急着评价抽象。

### Step 2: 数跳转和概念

审查时优先数：

- 读懂主逻辑需要的函数跳转次数
- 一个行为涉及的角色数量
- 同一份数据在几层之间传递
- 为支持“未来可能性”引入了多少结构

### Step 3: 判断复杂度来源

把复杂度分成三类：

1. `必要复杂度`
   - 业务规则本身复杂
   - 外部系统约束复杂
2. `表达复杂度`
   - 本来可以直接写清，却被层层包裹
3. `预支复杂度`
   - 不是当前需要，只是为了假想扩展提前建设

优先打击 `表达复杂度` 和 `预支复杂度`。

### Step 4: 给最小简化建议

每个 finding 都尽量落到下面这些动作之一：

- 删除
- 内联
- 合并
- 扁平化
- 去配置化
- 去泛化
- 改成更明确的命名

如果建议不能落到这些动作，通常说明结论还不够具体。

## 结论分级

- `High`: 明显的复杂度债务，已经影响理解、修改或排障；而且存在低风险的简化路径
- `Medium`: 复杂度开始失衡，但是否值得现在动手仍取决于变更频率或团队上下文
- `Low`: 有改进空间，但当前还没有形成实质性负担

不要把“只是还能更漂亮”标成 `High`。

## 标准输出

**默认保持克制。输出应该短到不需要滚动就能看完。**

默认格式（每个 finding 一行）：

```md
- [严重度] <位置>: <问题> → <最小动作>
```

例：

```md
- [High] user_service.go:42 UserFetcher 只有一个实现 → 删除 interface，内联到调用方
- [Medium] handler.go:88 三个布尔参数驱动分支 → 拆成两个命名函数
```

只有在以下情况才展开详细说明：

- 用户明确要求「详细解释」「展开说」
- 某个 finding 的「为什么现在值得改」不直观，需要解释取舍
- 简化会触及公共 API / 行为语义，必须说清风险

展开时才使用完整句式：

```md
1. [Medium] <标题>
   - 位置: <文件 / 调用路径>
   - 观察: <复杂度信号>
   - 最小简化方向: <删除 / 内联 / 合并 / 扁平化 / 去配置化>
```

**不要默认输出的内容**：

- 「审查工作流」中间过程（Step 1/2/3 的思考）
- 通用结论段落（"这段代码整体还不错"之类的总结）
- 重复解释 skill 自己的判断原则
- open questions 如果没有真实疑问就不要列

如果没有明确问题，只说一句：

```md
未发现明确的 simplify findings。
```

## 常用审查锚点

跨语言都可用的判断问题：

- 这层是否在吸收复杂度，还是只在转发复杂度？
- 把这层删掉，调用方会更难还是更容易理解？
- 这个抽象是否已经靠参数旗标维持统一？
- 如果今天要加一个小需求，必须改几层？
- 当前真实变化点有几个，而代码里准备了几个扩展点？

## 禁止行为

使用这个 skill 时，不要做这些事：

- 没看调用链就下结论说“这里过度抽象”
- 把“层次感”自动等同于“设计好”
- 看到重复就机械抽象
- 看到抽象就机械删除
- 用宏观架构观点覆盖局部代码可读性判断
- 在没有用户授权时，把审查直接升级成大规模重构计划
- 在用户没要求时输出审查过程说明、总结段落、或重复本 skill 的判断原则

## 一句话准则

简化代码的标准不是“更高级”，而是：
在保持行为边界清晰的前提下，让下一次阅读、修改、排查都更直接。
