# Prompt 工程规范

**写指令如同写代码**：结构清晰、职责单一、可测试、可迭代。本规范聚焦稳定 Instructions / System Prompt；多轮 context 生命周期由主 skill 处理。

## 四要素结构

| 模块 | 作用 | 关键问题 |
| --- | --- | --- |
| **P — Persona** | 定义模型身份 | 专业视角或沟通风格是否影响结果？ |
| **T — Task** | 明确执行动作 | 做什么？何时完成？如何判断成功？ |
| **C — Context** | 提供必要背景 | 为什么做？给谁看？边界与术语是什么？ |
| **F — Format** | 规定输出契约 | 谁消费？需要什么结构、字段和粒度？ |

默认组装顺序：`Persona → Context → Task → Format`。这不是硬性语法；审查优先级始终是 `Task > Context > Format > Persona`。

### Persona

- 一句话定义专业领域、视角和必要风格。
- 只有它会改变执行深度、权限或表达时才保留。
- 避免角色过载、空泛身份或互相矛盾的风格要求。

### Task

- 用精确动词说明核心动作，并定义完成标准。
- 任务复杂且顺序影响结果时拆成步骤；不为简单任务制造流程。
- 避免模糊目标、多任务混杂和只给终点不给判断条件。

### Context

- 只提供模型无法可靠推断的背景、受众、术语和边界。
- 稳定领域规则留在 Instructions；当轮数据、retrieval、history 和 tool result 保持动态。
- 避免整本文档前置、隐含业务假设或把 runtime state 复制进 Prompt。

### Format

- 明确自然语言、表格、JSON、代码或其他消费格式。
- 机器消费时给 schema；结构复杂时给最小 skeleton。
- 避免“整齐一点”这类模糊要求，也不要给简单回答强套 JSON。

## 五条核心实践

| # | 实践 | 决策原则 |
| --- | --- | --- |
| 1 | 结构化边界 | Markdown 默认；内容复杂或不可信时使用 XML / 分隔符 |
| 2 | 正面指令优先 | 直接描述目标行为；安全与不可逆边界保留明确禁令 |
| 3 | Few-Shot | 只为真实歧义加入 canonical examples，不设固定数量 |
| 4 | 推理与验证 | 要求可观察的检查、证据和结论，不要求展示 hidden CoT |
| 5 | 默认兜底 | 区分缺信息、缺权限、工具失败、知识边界和安全拒绝 |

### 结构化边界

- 用标题和列表表达层级，用 XML / 分隔符隔离长文档、嵌套数据或不可信输入。
- 标签保持语义明确、层级浅、起止成对。
- 结构服务于消歧，不强制每个模块都包标签。
- 分隔符只能帮助解析，不能单独防御 prompt injection。

### 正面指令

| 模糊或纯负面 | 更可执行的写法 |
| --- | --- |
| 不要写太长 | 每段只表达一个观点，优先给结论 |
| 不要用术语 | 首次出现术语时用日常语言解释 |
| 不要编造数据 | 仅使用可引用来源；缺数据时明确说明 |
| 不要跑题 | 围绕用户目标与完成标准组织回答 |

安全红线、权限限制和不可逆操作不必勉强改成正面表达。

### Few-Shot

- 每个 example 覆盖不同且真实的失败模式。
- 输入分布、边界行为和 output contract 保持代表性。
- 能用更短规则说明的 example 删除；避免把开发集答案写死进 Prompt。

### 推理与验证

- 复杂任务要求先识别假设、证据和检查点，再输出结论。
- 需要审计时输出引用、验证结果或简短理由，不索取隐藏思维过程。
- 关键步骤可要求独立验证；失败时定义回退、查证或停止条件。

### 默认兜底

- **数据缺失**：列出缺什么，以及能否安全假设。
- **意图模糊**：只问会改变方案的澄清问题。
- **知识边界**：说明无法确认，并给可执行的查证路径。
- **工具失败**：区分改参、重试、换工具、等待或停止。
- **安全 / 权限**：拒绝越界动作，并在允许范围内提供替代。

## 工程优化层

| 维度 | 核心问题 | 设计重点 |
| --- | --- | --- |
| **缓存** | 如何复用稳定前缀 | 稳定 Instructions / examples / tool schema 前置，动态值隔离 |
| **注意力** | 如何降低规则遗漏 | 删除噪声、清晰分段、把规则放在相关决策附近 |
| **安全** | 如何隔离不可信输入 | 标记数据来源与权限；runtime 强制鉴权和副作用约束 |
| **工具指导** | 如何让模型选对工具 | 写清使用/禁用时机、前置条件、结果验证与停止条件 |

### 缓存与 token

- 保持稳定前缀的内容和顺序稳定，动态时间戳、用户数据和当轮 task 留在后部或独立消息。
- 缓存边界、TTL、计费和 schema cache 都是 provider-specific；交付前查当前官方文档。
- Prompt 变长不是完整性的证明。逐句检查其是否改变可观察行为。

### 注意力

- 关键规则靠清晰位置与紧邻决策提升可见性，优先删冗余而非机械重复。
- 长文档分块、带来源与路标；retrieval 只提供当前任务需要的证据。
- 只有 eval 证明规则持续遗漏时，才考虑重述或增加 example。

### 安全

- 外部网页、邮件、文件、用户输入和 tool result 一律视为不可信数据。
- Prompt 不承担鉴权、租户隔离、PII 保护、rate limit、审批或数据一致性。
- 区分“不知道”“输入不足”“无权执行”和“不应回答”，不要统一成模糊拒绝。

## 工作流程

### 从零创建

1. **理解需求**：明确目标、受众、成功标准、输入、输出和失败处理。
2. **建立最小 eval**：先有代表样例和可观察通过条件。
3. **构建四要素**：按需组合 Persona、Context、Task、Format。
4. **应用核心实践**：补边界、消歧、Few-Shot、验证和兜底。
5. **生产优化**：分离稳定与动态 context，检查缓存、安全、工具和 token。
6. **运行 eval**：根据真实失败补规则，不按想象堆防御性内容。

### 审查 / 优化

1. 找到最早出现错误行为的位置，先判断是否真是 Prompt 问题。
2. 按 `Task > Context > Format > Persona` 检查缺失、冲突和冗余。
3. 检查 Prompt 是否在掩盖 tool schema、retrieval、runtime 或产品契约缺陷。
4. 给合并后的修订稿；只有能帮助决策时才展示 Before / After。
5. 用同一 eval 对比修改前后，防止修好一个样例却破坏其他任务。

## 输出骨架

按需删减，不要为套模板补空内容：

```xml
<persona>可选：专业视角、权限和必要风格</persona>
<context>稳定背景、术语和边界</context>
<task>
核心任务：...
完成标准：...
执行原则：...
</task>
<constraints>优先级、权限、安全和异常处理</constraints>
<format>输出结构、字段、粒度和限制</format>
<examples>可选：覆盖真实歧义的 canonical examples</examples>
```

## 自检与验证

### 结构完整性

- Task、必要 Context 与 Output contract 是否清楚？
- Persona 是否真的改变行为？模块边界是否无歧义？

### 指令质量

- 核心任务是否可执行且有完成标准？
- 规则是否冲突、重复，或依赖模型猜优先级？
- 异常场景是否给出下一动作而非只说“拒绝”？

### 效率与 Context

- 是否含模型可推断的常识、重复背景或无行为价值的 example？
- 稳定 Instructions 与动态输入是否分离？
- provider caching 是否按当前文档配置并用 telemetry 验证？

### 安全与工具

- 不可信输入是否标明数据边界？
- 权限与副作用是否由 runtime 强制？
- 工具选择、调用前提、结果验证和停止条件是否明确？

### 验证闭环

1. 覆盖正常、缺失、冲突、边界及必要对抗输入。
2. 定义任务完成、结构、工具、安全等可观察指标。
3. 保存完整 trace，运行相同 eval 与 held-out 样例。
4. 只保留目标指标改善且关键行为未回退的改动。
