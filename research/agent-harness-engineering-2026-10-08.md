# Agent harness engineering: first-party guidance

- Date: 2026-10-08
- Question: Which first-party Anthropic/Claude and OpenAI recommendations should guide a cleanup of `engineering/agent-engineering` across architecture choice, tool contracts, loops and recovery, context, sandboxing and permissions, delegation, and evaluation?
- Source scope: Anthropic engineering posts, Claude Platform documentation, claude.dev (its terms identify Anthropic, PBC as the site operator), and OpenAI official guides and API documentation. Sources were checked on 2026-10-08. Secondary commentary was excluded.

## Facts from sources

1. **Start with the simplest architecture.** Anthropic distinguishes code-orchestrated workflows from agents that dynamically direct their own tool use. It recommends using the simplest solution and increasing autonomy only where flexibility warrants its added latency and cost. Its 2024 article warns that some implementation details have since changed and points readers to Managed Agents for current product details. OpenAI likewise recommends starting with a single agent and adding specialization only when distinct instructions, tools, or decisions justify it. [Anthropic: Building effective agents](https://www.anthropic.com/engineering/building-effective-agents); [OpenAI: A practical guide to building agents](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)

2. **Keep the harness responsible for control flow and runtime boundaries.** OpenAI's SDK describes a run as a loop that invokes the model, executes tool calls, and continues through handoffs until completion or a defined interruption. Its run controls report turn-limit, tool, and guardrail failures. Anthropic's tool protocol likewise has an explicit `tool_use` / `tool_result` round trip, including an error result when a client tool fails. These are runtime behaviors, not guarantees that a prompt can enforce. [OpenAI: Running agents](https://developers.openai.com/api/docs/guides/agents/running-agents); [Anthropic: Handle tool calls](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)

3. **Approval is a suspended run, not a retry.** OpenAI's approval flow pauses for review and resumes from the same run state. Its practical guide recommends bounded actions and human review for high-impact or irreversible actions. Recovery guidance must distinguish retryable tool failures from approval pauses, and inspect completed side effects before retrying a failed run. [OpenAI: Guardrails and human review](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals); [OpenAI: A practical guide to building agents](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/); [OpenAI: Errors and recovery](https://developers.openai.com/api/docs/guides/agents-api/errors)

4. **Design tools as a small, legible contract.** Anthropic recommends a minimal set of distinct tools, clear and unambiguous inputs, useful and token-efficient results, and errors that explain how to recover. It recommends measuring tool use with realistic tasks and held-out cases. OpenAI recommends strict structured schemas for function inputs, while noting that the application still executes and authorizes tool calls. Schema validity does not grant permission to perform an action. [Anthropic: Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents); [OpenAI: Function calling](https://developers.openai.com/api/docs/guides/function-calling); [OpenAI: Programmatic tool calling](https://developers.openai.com/api/docs/guides/tools-programmatic-tool-calling)

5. **Treat context as finite and recoverable state as separate from the prompt window.** Anthropic recommends progressive disclosure and just-in-time retrieval to avoid loading irrelevant material. Compaction is useful, but lossy summaries should be tested against complex traces; structured notes or durable state help when work spans sessions. OpenAI documents several state strategies and warns against accidentally combining replayed history with server-managed state. [Anthropic: Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents); [OpenAI: Conversation state](https://developers.openai.com/api/docs/guides/conversation-state); [OpenAI: Compaction](https://developers.openai.com/api/docs/guides/compaction)

6. **Use sandboxing and approvals according to the threat and action.** OpenAI separates the trusted harness (control, auth, review, audit, and recovery) from the sandbox (code execution, files, and mounts); it recommends keeping credentials outside untrusted execution, limiting network access and mounted data, and using a sandbox only when a task needs execution or isolation. Anthropic warns that tool output may contain indirect prompt injection, recommends least privilege and sandboxed tools, and documents network and permission policies for managed agents. [OpenAI: Sandbox agents](https://developers.openai.com/api/docs/guides/agents/sandboxes); [OpenAI: Sandbox environment security](https://developers.openai.com/api/docs/guides/agents-api/environments/security); [Anthropic: Mitigate jailbreaks and prompt injections](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks); [Anthropic: Cloud environment setup](https://platform.claude.com/docs/en/managed-agents/environments); [Anthropic: Permission policies](https://platform.claude.com/docs/en/managed-agents/permission-policies)

7. **Delegate only where parallel work or context isolation pays for coordination.** Anthropic reports that its multi-agent research system helps with breadth-first work over independent directions, but costs substantially more tokens and is a poor fit when agents must share context or coordinate tightly. Delegation instructions should give each worker a distinct objective, output format, tools or source expectations, and scope. The parent should synthesize evidence and decide whether more work is needed. OpenAI distinguishes a handoff, where a specialist takes over, from an agent-as-tool call, where the manager retains final control. [Anthropic: How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system); [OpenAI: Orchestration and handoffs](https://developers.openai.com/api/docs/guides/agents/orchestration)

8. **Evaluate outcomes and inspect traces.** Anthropic recommends realistic tasks with verifiable outcomes, held-out cases, and metrics such as tool errors, tool count, tokens, and latency; for stateful tasks, evaluate end state and meaningful checkpoints instead of requiring one exact path. OpenAI recommends inspecting traces to diagnose tool choice, handoffs, guardrails, and latency, then using representative datasets to compare changes. [Anthropic: Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents); [Anthropic: Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents); [OpenAI: Agent evals](https://developers.openai.com/api/docs/guides/agent-evals); [OpenAI: Observability](https://developers.openai.com/api/docs/guides/agents/integrations-observability)

9. **Keep general instructions lean and re-evaluate them as models change.** Anthropic reports removing over 80% of Claude Code's system prompt for specific newer models without measurable loss on its coding evaluations, after finding overlapping instructions caused conflicts. This is a model- and product-specific result, but it supports testing whether a rule changes behavior rather than accumulating generic directives. `claude.dev` is first-party: its terms state that Anthropic, PBC operates the site. [claude.dev terms](https://claude.dev/terms/); [claude.dev: The new rules of context engineering for Claude 5 generation models](https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models/)

## Inferences for the skill structure

- Organize the guide as a decision path: decide whether an agent is needed; choose the smallest useful loop and stop/recovery rules; define tool contracts and runtime authority; manage state and isolation; delegate only for independent work; then inspect traces and evaluate outcomes.
- Keep cross-provider principles in `SKILL.md`; place provider-specific API shapes and implementation examples in focused references, with their runtime named. Do not turn a provider's SDK surface into a universal architecture requirement.
- Remove unsupported absolutes, invented failure anecdotes, fixed retry counts, mandatory lifecycle state machines, mandatory sandbox abstractions, and hard-coded memory/caching layouts. Replace them with conditional decisions tied to an identified threat, failure, state need, or measured performance issue.
- State stop conditions explicitly: final response or task completion; exhausted configured budget; unrecoverable error; denied permission; or a pending approval. Retry only when the error is plausibly transient or the input/action meaningfully changes, and account for side effects first.
- Put security enforcement at the runtime/tool boundary: validate identity, scope, schema, and operation there. Treat model instructions and input/output classifiers as additional defenses, not substitutes for access control.
- Keep evaluation claims proportional: use deterministic checks for invariants and state, calibrated model/human graders for judgment, held-out examples for generalization, and traces to locate failure causes. Avoid requiring one tool sequence when multiple valid paths exist, except where the sequence is itself a safety invariant.

These bullets are synthesis and recommendations, not direct quotations from either vendor.

## Limitations

- Anthropic posts include internal reports and model-specific results; those numbers are not universal guarantees. `claude.dev` terms also say its content is informational and may be incomplete or out of date. Use current platform docs for API behavior and evaluate model-specific prompt changes on the target system.
- Agent runtimes differ in who owns the loop, state, sandbox, and approval mechanism. The sources do not establish universal retry counts, tool-count limits, lifecycle states, or one required sandbox interface.
- The research compares vendor guidance; it does not benchmark the repository's skill behavior. Any rewrite should be checked against representative decision cases before claiming improved behavior.
