# Agent engineering scope: task fit, model, knowledge, and iteration

- Date: 2026-10-08
- Question: What first-party guidance should fill four general agent-engineering gaps: deciding whether and how autonomously to use an agent; selecting and optimizing models; separating external knowledge, conversation state, and long-term memory; and iterating from offline evaluation through production feedback?
- Source scope: OpenAI API and business guides, Anthropic engineering and research posts, Claude Platform documentation, and claude.dev. Sources were checked on 2026-10-08. claude.dev is operated by Anthropic, PBC, according to its [terms](https://claude.dev/terms/). This note covers the four named gaps; it does not repeat the prior harness recovery research.

## Facts from sources

### 1. Task fit, action space, acceptance, and autonomy

- OpenAI identifies nuanced decisions, brittle rule sets, and unstructured inputs as agent opportunities, while recommending a deterministic solution when the use case does not need those capabilities. It advises beginning with a small scope and one focused agent. [OpenAI: A practical guide to building agents](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/); [OpenAI: Agent definitions](https://developers.openai.com/api/docs/guides/agents/define-agents)
- Anthropic says an agent fits problems with an unpredictable number of steps or no fixed path. Strong fits combine conversation and action, measurable success criteria, environment feedback, and meaningful human oversight. Agent autonomy increases cost and can compound errors. [Anthropic: Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- OpenAI's agent definition treats instructions as the specialist's job and constraints; tools define its available capabilities; structured outputs, guardrails, and approval policies shape its interaction boundary. It recommends splitting agents only when ownership, instructions, tools, or approval policies differ materially. [OpenAI: Agent definitions](https://developers.openai.com/api/docs/guides/agents/define-agents); [OpenAI: Orchestration and handoffs](https://developers.openai.com/api/docs/guides/agents/orchestration)
- OpenAI recommends rating tools by read/write access, reversibility, required permissions, and financial impact, then using the risk level to decide whether to pause for checks or human review. [OpenAI: A practical guide to building agents](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)
- Anthropic describes autonomy as a deployment characteristic that emerges from model behavior, user oversight, and product design. Its article defines lower autonomy as executing an explicit human request and higher autonomy as choosing actions with little oversight; it does not present this as a precise universal scale. High-impact or irreversible actions should receive human oversight under OpenAI's practical guide. [Anthropic: Measuring AI agent autonomy in practice](https://www.anthropic.com/news/measuring-agent-autonomy); [OpenAI: A practical guide to building agents](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)

### 2. Model capability baseline, cost, routing, and fine-tuning

- OpenAI recommends establishing an eval baseline on representative production-like inputs before prompt or model optimization. Model behavior can differ across families and snapshots; its prompt guide recommends pinning production snapshots and evaluating changes or upgrades. [OpenAI: Model optimization](https://developers.openai.com/api/docs/guides/model-optimization); [OpenAI: Prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering)
- OpenAI's practical guide suggests prototyping against a capable model to establish a performance baseline, then testing smaller models against the same acceptance criteria. Its current deployment checklist also says to select by representative workload rather than route every request to the strongest model. [OpenAI: A practical guide to building agents](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/); [OpenAI: API deployment checklist](https://developers.openai.com/api/docs/guides/deployment-checklist)
- OpenAI's deployment checklist recommends choosing a model that performs well on representative tasks rather than routing every request to the most capable model. It calls for comparing task success, latency, token use, and cost per successful task. Its model guidance adjusts reasoning effort by task difficulty and says to use very high effort only when representative evals show a worthwhile quality gain. [OpenAI: API deployment checklist](https://developers.openai.com/api/docs/guides/deployment-checklist); [OpenAI: Model selection](https://developers.openai.com/api/docs/guides/model-selection)
- OpenAI's fine-tuning guidance says to create evals before fine-tuning and compare the tuned model with the base model on holdout data. Supervised fine-tuning is described for repeated behaviors such as classification, a specific output format, and instruction-following; reinforcement fine-tuning needs a well-defined task, expert agreement, and a grader with room to distinguish performance. The current SFT documentation says OpenAI is winding down its fine-tuning platform, so availability is provider- and date-dependent. [OpenAI: Supervised fine-tuning](https://developers.openai.com/api/docs/guides/supervised-fine-tuning); [OpenAI: Reinforcement fine-tuning use cases](https://developers.openai.com/api/docs/guides/rft-use-cases)
- Anthropic's current model guidance treats model and effort as task-dependent tradeoffs. Its Claude.dev model-specific article recommends re-running evals before carrying old workarounds or effort settings across model generations. [Claude.dev: Building with Claude Sonnet 5.5](https://claude.dev/blog/building-with-claude-sonnet-5-5/); [Claude.dev: Spending your effort](https://claude.dev/blog/spending-your-effort/)

### 3. External knowledge, conversation state, and persistent memory

- OpenAI Retrieval uses indexed files and semantic search to find external information; the Model Optimization guide says relevant context can supply private or current information outside the model's training data. Retrieval indexes are external data stores, so they must be refreshed when their source material changes. The last sentence is an implementation implication, not a vendor freshness guarantee. [OpenAI: Retrieval](https://developers.openai.com/api/docs/guides/retrieval); [OpenAI: Model optimization](https://developers.openai.com/api/docs/guides/model-optimization)
- OpenAI conversation state preserves items across turns; Conversations can persist across sessions, devices, or jobs. Conversation history records interaction context and tool activity, while retrieval searches a knowledge source. These have different purposes. [OpenAI: Conversation state](https://developers.openai.com/api/docs/guides/conversation-state)
- OpenAI's sandbox-agent guide explicitly separates SDK Session message history from sandbox memory, which distills useful preferences, corrections, project lessons, and task summaries into files. It also says snapshots and workspace resume preserve workspace state, while memory preserves reusable guidance. This is a runtime-specific example of the distinction, not a required storage design. [OpenAI: Sandbox agents](https://developers.openai.com/api/docs/guides/agents/sandboxes)
- Anthropic's memory tool gives the application a client-managed directory that the model can read and update across conversations. Managed Agents also support stores shared by sessions, with store descriptions and access modes. Anthropic recommends expiration for old memory files. [Anthropic: Memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool); [Anthropic: Using agent memory](https://platform.claude.com/docs/en/managed-agents/memory)
- Anthropic describes progressive disclosure and just-in-time retrieval as ways to keep only relevant information in active context. Its tool-combinations guidance distinguishes memory (persist state across conversations) from the other tools that perform current work. [Anthropic: Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents); [Anthropic: Tool combinations](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-combinations)

### 4. From offline evaluation to production feedback and rollback

- Anthropic defines an eval task by its inputs and success criteria; because agent output varies, it recommends multiple trials. A trace records the trial, and the environment's final state can be a stronger completion check than the agent's own claim. [Anthropic: Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- OpenAI recommends inspecting representative traces while debugging agent behavior, then moving to datasets and repeatable eval runs to compare prompts and workflow changes. Its observability guide records model calls, tools, handoffs, guardrails, and custom spans. [OpenAI: Evaluate agent workflows](https://developers.openai.com/api/docs/guides/agent-evals); [OpenAI: Integrations and observability](https://developers.openai.com/api/docs/guides/agents/integrations-observability)
- OpenAI's current prompting guide says to manage prompts as versioned application code, run representative fixtures and evaluation checks during deployment, and use pull requests, release tags, and feature flags to compare, ship, and roll back changes. [OpenAI: Prompting](https://developers.openai.com/api/docs/guides/prompting)
- Anthropic's eval guidance combines evals with production monitoring, A/B tests, and user research. Its recent Claude.dev eval workflow uses production-like tasks and a held-out set; it reverts a change when test performance is flat or regresses. A Claude.dev performance case describes watching each deployment against real-user monitoring. [Anthropic: Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents); [Claude.dev: Automating eval design and hillclimbing](https://claude.dev/blog/automating-eval-design-and-hillclimbing/); [Claude.dev: How we made claude.ai 3x faster](https://claude.dev/blog/how-we-made-claude-ai-faster/)

## Inferences

- An agent task contract should name the desired end state, allowed action surface, side-effect boundary, observable acceptance check, and escalation point. If the objective or acceptable outcome is unclear, clarify it or keep the model in an advisory role until the human decides.
- Choose autonomy from the deployment's actual action permissions and oversight, not the model's benchmark score alone. More model capability can improve task performance, but it does not itself authorize a broader action surface.
- Keep three data roles explicit: retrieval obtains facts from maintained external sources; conversation state preserves the current interaction; durable memory keeps selected information that is useful across sessions. Add source, scope, and freshness metadata where stale or untrusted information could change a decision.
- Select a baseline model and effort using representative task slices. Optimize only after measuring quality, latency, and cost per successful task. Add routing when task classes reliably need different capability or cost profiles and the routing cost is justified. Consider fine-tuning only for stable, repeated behavior when evals show the current model has a measurable, learnable gap; use retrieval for changing facts.
- Carry offline evidence into deployment: version the model identifier, prompt, tool contract, policy, and evaluator with each change; run a repeatable regression set; monitor real task outcomes, user corrections, errors, latency, and cost; roll back when a release regresses. These specific version fields and metric bundle are a synthesis, not a vendor-prescribed schema.

## Recommendations for the skill

- Add a short task-fit decision before architecture choice: Does the task require adaptive choices over unstructured input or variable environmental steps? Can the goal, permitted actions, and success check be stated? Can risky actions be reviewed or bounded? If not, reduce autonomy or choose a deterministic workflow.
- Add model choice as an eval-backed tradeoff rather than a catalog of model names. Use one capable baseline, representative cases, and per-task success/latency/cost. Route or fine-tune only when measurements show a specific benefit; mark provider-specific capabilities as time-sensitive.
- Replace one broad “memory” concept with three decision points: retrieve external facts, preserve active conversation state, or persist selected cross-session information. Include ownership, update/expiry, source trust, and sensitivity in the persistence decision.
- Add a compact lifecycle: define the eval and baseline; inspect traces to find failures; make one attributable change; run held-out regression checks; deploy with observation and a rollback path; feed verified user corrections or production failures into the next eval set.
- Keep operational thresholds task-specific. The sources do not justify universal retry, autonomy, tool-count, model-routing, memory-retention, or release-gating numbers.

## Limitations

- These sources describe vendor systems and examples. Anthropic's model and product guidance is specific to its models; OpenAI's API and fine-tuning availability can change. Check current provider docs before writing provider-specific instructions.
- Vendor case studies use internal workloads and evals. Their measured results do not establish universal returns for an unrelated product or task.
- The sources support the distinction between retrieval, conversation state, and durable memory, but do not define a common cross-vendor freshness, deletion, consent, or retention policy. Those policies depend on the application's data and obligations.
- No source supplies a universal autonomy scale or a universal threshold for when routing, fine-tuning, or online rollout pays off. Those thresholds require task-specific evaluation and risk analysis.
