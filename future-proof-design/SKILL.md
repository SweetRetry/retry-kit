# Future-Proof Design (面向未来设计)

这个 skill 的核心目标是**打破“遇到新需求就打个补丁”的恶性循环**，建立演进式设计的思维体系。我们不主张一次性建好“百年大计”的过度工程，但坚决抵制任何会让代码“更容易腐烂、改造成本呈指数级上升”的补丁行为。

我们追求的是：**在实现当前业务的同时，让下一次变更的成本更低，并及时扭转系统向错误轨道滑落的趋势。**

---

## 适用场景

优先在以下诉求和对话场景中触发：

- “帮我看看怎么给这个模块设计新功能扩展”
- “现在的代码很难加新逻辑了，帮忙重构一下”
- “review 一下这段修改，有没有坏味道或维护隐患”
- “这里是用 if-else 还是加个策略模式好？”
- “如何避免未来修改这部分代码时引发回归问题”
- “设计方案评审 / 架构合理性评估”

高信号关键词：

- `refactor` / `重构`
- `technical debt` / `技术债`
- `patch` / `打补丁` / `修补`
- `maintainability` / `可维护性`
- `scalability` / `扩展性`
- `blast radius` / `影响半径`
- `shotgun surgery` / `散弹式修改`
- `anti-pattern` / `反模式`
- `evolutionary design` / `演进式设计`

## 不适用场景

不要在以下情况生搬硬套本 skill 的高标准设计：

- **线上紧急故障热修复（Hotfix P0）**：此时速度和确定性高于一切，接受打补丁，但应在修复后记录技术债，提示后续重构。
- **一次性脚本 / 临时原型（POC / Prototype）**：生命周期极短，不需要考虑演进和维护。
- **极简流程的就地简化**：如果代码本身的逻辑就是线性的且足够简单，不要为了“面向未来”强行引入抽象层（这属于过度工程，应遵循 [simplify-code](file:///Users/zhangzimin/Documents/sweetRetry/skills/simplify-code/SKILL.md)）。

## 核心设计原则

### 1. 修改的局部性 (Locality of Change)
* **核心定义**：一个业务概念的变更或新规则的加入，改动范围应当收敛在极少数（最好是单个）高内聚的模块内。
* **反模式**：**散弹式修改 (Shotgun Surgery)**。加一个字段或新状态，需要同时修改 Controller、DTO、Service、Helper、SQL 以及前端的数个页面。
* **审查锚点**：这次修改涉及了几个不相关的类？它们之间是否有不合理的数据透传？

### 2. 演进式抽象 (Evolutionary Abstraction)
* **核心定义**：不为“想象中的未来需求”预留过度复杂的接口与泛化设计，但当前的编写方式必须**容易被重构**（即高模块化、职责单一、依赖清晰）。
* **黄金法则**：写“好删、好改、好替换”的代码，比写“通用但难以看懂”的抽象层更重要。
* **审查锚点**：如果未来这个业务下线了，我能否在 5 分钟内安全地把所有相关代码干净地删掉？

### 3. 显式契约与防御性边界 (Explicit Contract & Defensive Boundary)
* **核心定义**：模块之间的协作通过显式的类型、接口、或不可变对象（DTO/Value Object）进行，拒绝隐式传参；在边界处快速失败（Fail-fast），绝不让非法数据深入核心业务层。
* **反模式**：利用 `Map<String, Object>` 或全局 Context 隐式搬运新状态；直接吞掉异常返回 `null`，导致 NPE 在下游隐蔽爆发。
* **审查锚点**：新引入的数据字段是否具有强类型约束？输入边界（如 API 接入层、外部系统集成点）是否做了严格的校验？

### 4. 领域模型完整性 (Domain Integrity)
* **核心定义**：核心业务规则应由领域对象/实体（Domain Model/Entity）自治，应用服务层（Service）只负责编排。
* **反模式**：贫血模型。实体只有 Getter/Setter，复杂的判断逻辑散落在各种 Handler、Util 甚至 UI 渲染层中，导致规则不一致。
* **审查锚点**：新增的条件判断是否是该实体固有的业务规则？如果是，为什么不在实体类内部实现？

### 5. 路径纠偏与破窗治理 (Path Correction & Window Repairing)
* **核心定义**：面对已经处于“错误道路”（如架构错位、历史坏味道、设计反模式）上的既有代码，面向未来编程不等于“向烂代码妥协”或“继续垒垃圾”，而必须在变更时**主动刹车、小步纠偏**，阻止破窗效应扩散。
* **核心行动**：
  1. **拒绝盲从**：不以“既有代码就是这么写的”为由继续堆砌坏味道（例如不合理地拷贝粘贴糟糕的逻辑或滥用设计漏洞）。
  2. **引入隔离与防腐层 (Anti-Corruption Layer)**：如果历史债务过重无法一次性重构，至少在新增逻辑与遗留代码之间筑起防腐边界，确保新逻辑在正确的轨道上启动。
  3. **借机重构 (Opportunistic Refactoring)**：每一次需求变更或 Bug 修复都是对遗留代码进行局部纠偏的绝佳契机。
* **审查锚点**：这次修改是在顺着旧的“错误设计”继续下滑（加剧破窗），还是在设法切断债务的延续并扭转方向？

## 补丁式编程 vs 面向未来设计

| 维度 | 补丁式编程 (Patch-Style) | 面向未来设计 (Future-Oriented) |
| :--- | :--- | :--- |
| **增加新业务分支** | 随意增加布尔 Flag，嵌套 `if-else`，导致控制流日益混乱。 | 提取显式策略（Strategy/State 模式），或根据语义拆分独立的控制流，保持主流程呈线性阅读。 |
| **数据流动** | 哪里缺数据就去哪里查，或者通过全局共享状态（如 ThreadLocal/Context）传递，制造隐式耦合。 | 数据流向清晰，通过显式参数、只读 DTO 或精简的上下文接口进行参数传递。 |
| **面对错误路径/遗留缺陷** | 顺着已有的错误设计继续堆砌代码，在外围“包一层”过滤条件或纠偏逻辑以掩盖问题，导致破窗效应蔓延。 | 及时纠偏。若历史债务极重无法立刻重构，则引入防腐层（Anti-Corruption Layer）进行隔离，为后续重构留出清晰契约。 |
| **外部依赖** | 直接调用第三方 SDK 或外部底层服务，让核心逻辑深陷外部契约。 | 引入适配器（Adapter）和抽象网关（Gateway），隔离外部不稳定因素。 |
| **错误与边界** | “能跑通就行”，忽略极值、并发、事务边界与超时控制。 | 考虑幂等性、并发安全，并在核心调用链路设置合理的超时、降级与重试策略。 |

## 审查与重构工作流

当被激活时，按以下步骤对变更方案或既有代码进行深度扫描：

### Step 1: 扫描“补丁坏味道”与改动半径
统计当前修改方案的物理扩散情况：
1. **改动文件分布**：改动是否跨越了职责边界（例如：同时修改了数据库结构与表现层渲染逻辑）？
2. **Flag 蔓延度**：是否为了一个局部需求引入了新的全局控制开关/状态标识？
3. **控制流嵌套**：核心函数的圈复杂度（Cyclomatic Complexity）是否因为新加的分支而陡增？

### Step 2: 定位根源系统债务与“错误路径”
如果发现既有系统本身已偏离轨道或方案呈现“打补丁”特征，推导其根源：
- 错误路径是什么？是否是因为**现有模型无法适配新语义**（如：用 User 表硬塞 Enterprise 用户的属性）？
- 是因为**边界不清晰导致调用链路太长**？
- 是因为**缺乏测试保护，导致不敢动核心，只能在外围贴膏药，默认向错误路径妥协**？

### Step 3: 设计双轨对比方案 (Quick-Fix vs. Best-Practice)
在向用户输出时，严禁直接给出一份简单的修改建议。**必须同时提供以下两种选择的对比，重点展示如何打破已有的“错误路径”**：
* **方案 A (Quick-Fix / 临时补丁)**：
  - 简述实现路径（即用户原本倾向或最容易想到的就地修改方案）。
  - **债务评估**：说明这会带来什么短期负债（如：如何顺着错误设计继续滑坡，下一次修改时成本将增至多少）。
* **方案 B (Best-Practice / 面向未来设计 - 路径纠偏)**：
  - 阐明优雅的演进与纠偏设计（如：重构接口契约、提取策略类、引入防腐隔离解耦依赖）。
  - **演进优势**：说明该方案如何斩断技术债务的延续，收敛改动半径，为下一步业务扩展奠定正确方向。

### Step 4: 规划渐进式重构路径 (Progressive Refactoring Path)
为了降低方案 B 的执行风险，提供“小步快跑”的重构路线：
1. **第一步：铺平道路 (Prepare)**：在不改变行为的前提下，做小范围重构，为新功能腾出优雅的接入点（Refactor before feature）。
2. **第二步：合流引入 (Introduce)**：以干净的契约实现新功能。
3. **第三步：清理战场 (Cleanup)**：删除旧有权宜代码，完善单元测试。

## 常见设计反模式与改造对策

### 典型案列 A：标志参数雪崩 (Flag Avalanche)
* **表现**：一个核心函数被添加了 `isUrgent`、`skipAudit`、`useNewFlow` 等多个布尔开关。
* **面向未来改造**：
  * 如果分支逻辑差异极大，拆分为独立的处理器类或服务。
  * 如果只是部分步骤不同，使用**模板方法模式 (Template Method)** 或**策略模式 (Strategy)**。
  * 如果是可选配置，将控制行为封装进一个显式的契约对象（如配置上下文）中，而不是直接作为函数入参传递。

### 典型案例 B：绕过领域的穿透修改 (Domain Bypass)
* **表现**：直接在 Controller 或外部 Service 中使用 ORM 批量修改实体的内部状态，跳过了实体的内部约束和生命周期事件。
* **面向未来改造**：
  * 在实体内提供语义化的方法（如 `user.suspend(reason)`，而不是 `user.setStatus("suspended")` & `user.setUpdatedAt(now)`）。
  * 将所有约束逻辑守卫在实体方法内部，确保对象状态始终合法。

### 典型案例 C：硬编码的胶水逻辑 (Hardcoded Glue)
* **表现**：在代码中硬编码具体的环境 IP、特定租户 ID 的特殊 `if` 分支（如 `if (tenantId == 88) { ... }`）。
* **面向未来改造**：
  * 将环境信息与特定行为配置化，注入策略接口。
  * 引入租户特性的多租户行为定制器（Feature Toggle 或 Tenant Strategy Provider）。

## 审查结论分级与输出规范

### 严重度分级

- **[CRITICAL]**：严重的打补丁行为，直接破坏了系统核心架构，引入了显著的隐式耦合、数据一致性风险或高额的后期改造债。必须立即劝阻，进行 Best-Practice 重构。
- **[WARNING]**：局部的临时修补，虽然解决了当前问题，但会导致控制流恶化、内聚度降低。建议进行小步重构。
- **[OPTIMIZE]**：设计基本合理，但可通过微调（如强类型化、细化接口定义）使未来的扩展性更好。
