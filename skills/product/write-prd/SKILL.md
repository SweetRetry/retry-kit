# Write PRD

PRD 在动手前固定三件事：为谁解决什么问题、做到哪里算完成、什么不做。它有两类读者，任务不同：

- **人**做决定：批方向、取舍范围、排优先级、接受风险、最终验收。注意力有限，要先看到批什么、赌什么。
- **Agent** 执行与核对：设计、实现、写测试、判定验收。它没有会议和聊天里的上下文，遇到缺口会自信地猜，歧义直接变成错误行为。

所以一份 PRD 分两部分：**决策**（人看）与**执行契约**（Agent 看），末尾共用一份变更记录。Agent 读全文：决策部分是它取舍时的意图来源，执行契约是它的验收依据。每个事实只在一处成立，另一部分按 ID 引用，不复述。

## 1. 定读者、决策与权威源

动笔前明确：

- 哪些人据此做什么决定（评审、排期、验收），哪些 agent 据此做什么（实现、测试、验收核对）；
- 方向与投入是否已定：未定先收敛方向，本 skill 只把已定方向写成可交付需求；
- 已知证据（用户反馈、行为数据、工单、研究；提出人意图、当前优先级、研发技术边界这类内部背景，落到会议结论或沟通记录后才计入证据，仍只在口头或聊天里的标为假设）与关键未知；
- 会实质改变范围但缺失的信息：集中询问关键项；可继续起草的假设显式标出，阻塞范围或验收的未知项不得当作已定需求；
- **权威源**：PRD 只有一个权威源，其他位置都是副本。默认权威源是 Markdown 文件，放在项目约定的文档目录，没有约定时放进需求对应的代码仓库，让 agent 直接读到。已有 PRD 只存在于云文档时，云文档就是权威源。

修订已有 PRD 时，先从权威源读取现状，按受影响的 ID 定点编辑，保留无关内容，再按第 8 步记录。

评审状态、提出人、负责人、排期和目标值均须有可追溯依据；未知项标待确认，并记录确认人与时点。生成文档不代表通过评审。

完成标准：能用一句话说清“让谁在什么范围内、就什么可观察结果形成共识”；每个假设都连到它会改变的需求或范围；只存在于口头或人脑中的前提已写进正文或标为假设。

## 2. 搭两部分结构

新建或重排章节时，读取 [sections.md](references/sections.md)，按每节支撑的决定或执行任务选择内容；定点修订只检查受影响章节。

ID 连接两部分与变更记录：G 目标、NG 非目标、R 需求、AC 验收、INV 不变量、Q 开放问题。

完成标准：每节都对应一个人的决定或一项 agent 任务；每个 G 至少由一条 R 支撑，每条 R 都能追到 G 或范围条目，R 与 NG 不冲突。

## 3. 写决策部分（人看）

- 开头是决策摘要：要批准什么、问题与方案各一句、最大风险、待谁在何时拍板。评审者读完这几行就知道要决定什么。
- 写判断与取舍，规则细节只在执行契约写一次：方案概览描述用户可见的形态，并引用 R。
- 无用户证据时收窄为显式假设加研究计划，并标出它会影响哪个决定。
- 业界实践只在涉及方向选择、方案对比或行业惯例时写。来源用可复核的一手材料（产品文档、公开案例、财报、标准）；每条都指出它改变或校准了哪个判断，要采用就在执行契约写成 R。
- 开放问题统一放在这部分：每个 Q 写影响的 R、是否阻塞、非阻塞时的默认值、确认人与时点。人在这里拍板，agent 在这里查默认值。

完成标准：评审者只读决策部分，就能说出要批什么、赌的是什么假设、不做什么、什么结果算成功、哪些问题等人拍板。

## 4. 写执行契约（Agent 看）

术语表先行。每个对象、状态、事件全文只用一个词，与 UI 文案一致，两部分、流程图和变更记录沿用同一词表；不用内部项目代号。用户或旧文档里的别名记进术语表，正文只用正名。

每条需求一个条目：

```markdown
### R-3 取消待支付订单（必须，未满足阻塞验收）

- 规则：当买家在订单详情提交取消，且订单处于待支付时，系统应将订单置为已取消并回补库存。
- 失败与边界：订单处于已支付时不显示取消入口；取消与支付成功同时发生时，最终状态为已支付，买家看到取消失败提示。
- 验收：
  - AC-3.1 Given 待支付订单 When 买家提交取消 Then 订单状态为已取消，库存回补 1。核对：程序。
  - AC-3.2 取消确认弹窗与设计稿 F-12 一致。核对：人，设计负责人对照设计稿。
- 依据：G-1；设计稿 F-12
```

写法：

- 规则用 EARS 句式（当……时 / 处于……时，系统应……），一条只写一个可观察结果；大而不可测的需求拆到单条可验收粒度。
- 强度只用必须 / 应当 / 可选，并写明未满足时是否阻塞验收。
- 状态写成名词（待支付、已支付），触发与动作写成事件（提交、支付成功），两者不混用。
- 评价词、模糊量词和行业黑话（流畅、稳定、大量、尽快、赋能、闭环）改写成可观察结果；依据不足时列为 Q。
- 指代对象、条件间的逻辑关系、适用范围、数量与时间边界都写明。一句话存在会导致不同行为或验收结论的合理解释时，改写为明确规则；依据不足时列为 Q，不自行选定一种解释。
- 每条 AC 标核对方式：程序可判定的写成机器可判定的条件（状态值、接口返回、页面元素、埋点事件）；需人判断的写清由谁依据什么判断。
- 实现取舍（架构、接口、数据结构）留给技术方案；契约只约束可观察行为。
- 现状基线写改动前的行为；INV 列出本次必须保持不变的相邻行为，每条可回归核对。Agent 会顺手“改进”相邻功能，INV 是它的护栏。
- 涉及界面时，关联原型、设计稿、组件库或交互约束并对应到 R。设计与正文冲突时先明确有效要求再同步两边；流程图不能代替交互依据；尚未确定且影响验收的交互列为 Q。
- 决策权限写明契约未覆盖时 agent 怎么做：不影响可观察行为的实现细节自主决定；非阻塞 Q 按默认值执行并在交付时报告；触及 NG、改变未约定的可观察行为、遇到阻塞 Q、AC 无法满足、设计与正文冲突时停下上报。

完成标准：第 6 步冷读通过。

## 5. 用流程图表达关系

先判断内容关系，再选表达：

- 有分支、回路、多角色协作、状态迁移、时序依赖时用 Mermaid 代码块：关系本身就是信息，文字会把它藏住；
- 单线 3–5 步且无分支时用列表；
- 精确字段对比用表格。

一图只回答一个“怎么流转 / 何时进入什么状态”的问题，多个独立流程拆多张；分支边写条件标签。用户旅程与方案主流程放决策部分，状态机与时序放执行契约。节点、状态、角色名与术语表一致，正文引用节点而非复述箭头。

完成标准：不看正文也能从图中读出主路径与主要失败路径。

## 6. 冷读

**冷读**是让没有本次会话上下文的读者只凭 PRD 工作，暴露作者脑中默认、纸面缺失的信息。有子 agent 能力时派发一个，只给它 PRD 全文，要求它：

1. 对每条 R 说出要实现的可观察行为，以及每条 AC 的核对方法与执行者；
2. 列出每一处必须猜的地方：词义、条件、边界、默认值、权限；
3. 只读决策部分，复述要批的决定、所赌假设、非目标、成功标准与待拍板问题。

没有子 agent 能力时，自己按这份清单逐条冷读。每个猜测点二选一处理：改写正文关闭它，或登记为 Q 并写明是否阻塞与默认值；第 3 项复述与作者意图不符的段落重写。改动后对受影响的 R 重跑冷读。

完成标准：冷读输出中没有未处理的猜测点；每条 AC 都有核对方式与执行者；决策部分的复述与作者意图一致。

## 7. 发布与同步

先写完权威源并通过冷读，再同步副本。

- 同步到飞书：读取 [lark.md](references/lark.md)。
- 任何副本：开头注明权威源位置与对应版本，权威源头部反向记录副本链接。评审意见与他人在副本上的改动，先合入权威源，再从权威源重新同步；两边不各自修改。

完成标准：回读副本，受影响章节与权威源一致；未成功写入的改动不记为已完成。

## 8. 维护需求变更记录

正文只呈现当前有效需求，变更记录是**只追加的账本**：旧内容及变化原因留在记录中，不删除、不改写历史条目；记录有误时追加更正并指向原条目。

- 同一需求的修订保留 ID；新增需求分配新 ID，删除后的 ID 不复用；拆分、合并或替代时分配新 ID，并写明旧 ID → 新 ID 的关系。
- 每条记录写：日期 / 版本 / ID / 变更类型 / 变更内容 / 原因 / 影响面 / 需重验的 AC / 提出人 / 状态。修改写清旧要求 → 新要求，删除保留旧要求；原因写判断情境（何时、哪次会议或哪份结论、为什么调整），足以让无上下文的人复原当时判断；影响面写范围、排期、指标、兼容的实际变化或待确认项。需重验的 AC 让下游 agent 只对变化部分增量实现与回归。
- 首次建文档就带该 section，首版记录覆盖全部实际需求 ID；修订没有历史记录的文档时，只记录本次观察到的基线与变更，不补造历史。

完成标准：当前正文、验收及流程图一致；每条需求能追到首版、本次基线或后续变更，拆分、合并及替代关系可追踪，历史条目完整未改写。

## 输出

交付权威源路径与副本链接，并说明：基于哪些证据、哪些是假设、哪些 Q 阻塞、冷读发现并处理了什么、流程图对应哪些流程、变更记录新增了什么。缺口与阻塞显式列出。
