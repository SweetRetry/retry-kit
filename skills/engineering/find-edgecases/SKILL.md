# Find Edgecases

一条 finding 由三件事同时成立构成：

1. **可达触发**：重复点击、超时重试、发布、并发、乱序这类真实会发生的条件；
2. **终态**：系统停下来时数据的样子违反一条不变量，例如重复扣款、两份数据不一致、任务永远停在 `processing`、界面显示上一次请求的结果；
3. **无自愈**：没有幂等重试、对账、过期清理或用户看得见的重试入口把它修回来。

缺一件就不是 finding。正常输入下就出错的普通 bug、复杂度和交互问题记为转交项。

顺着代码问“如果……会怎样”，只能想到作者也想到过的情况。漏掉的恰恰是代码里没写的东西：没写下来的规则、范围外的另一个写入方、没人处理的故障。所以先建模，再按故障模型系统生成场景，最后回到代码反证。

默认只报告。用户要建议时，按根因给方向。用户要修改时，先用测试复现，只改已确认问题涉及的代码，改完重跑该测试。

## 范围

- 审用户指定的代码、diff、设计或调用路径。用户说 `changes` 时审当前改动；都没有时先问。
- **审查单元**是包住范围的最小闭合流程，加上全仓库里读写同一份状态的代码。竞态常常来自范围外的写入方，所以它属于单元。
- 审设计文档时，用章节或流程节点代替 `文件:行号`。

## 1. 建模

**不变量**是无论发生什么都必须成立的事。先从业务和观察者推，再补上代码里已经在检查的。只从代码里收集，会漏掉作者没想到的那几条。

- 后端：一个订单只扣一次款；库存不为负；状态只能 `pending → paid → shipped`；每条消息的效果只生效一次。
- 前端：界面显示用户最新一次操作的结果；一次提交只产生一条记录；登出后看不到上一个用户的数据；未保存的输入不会被悄悄丢掉。
- 跨端：客户端与服务端对同一字段的含义和格式理解一致。

**撤不回的动作**是不变量最容易被破坏的地方：写库、调外部接口、发消息、扣款、发通知、删除、离开有未保存内容的页面。

**状态转移**。共享状态包括表里的行、缓存、队列、外部系统里的记录、客户端 store、URL、浏览器存储。每次转移写成“读 → 判断 → 写”，标出哪几步不在同一个原子操作里。

**写入方**是所有能读写这些状态的参与者，在全仓库里搜。常被漏掉的有：同一用户的两个标签页、重复点击、各层的重试（客户端、网关、SDK、队列重投）、并行的 worker、定时任务、补偿与对账任务、外部回调、运维脚本与数据迁移、滚动发布时并存的新旧版本、浏览器里缓存的旧前端。

**完成标准：**每个撤不回的动作都对应至少一条不变量，并写明由什么机制保证（唯一约束、事务、锁、条件更新、幂等键、对账任务、请求取消），没有就写“无”；每次转移都列出了能插进它读与写之间的写入方。范围小时，这一步自然只有一两次转移。

## 2. 推演

对每次转移，用下面五种算子生成场景。每种算子在各类边界上的具体样子查 [references/faults.md](references/faults.md)。

1. **切点**：在每两个非原子步骤之间放进崩溃、超时、响应丢失（实际做成了，调用方以为失败）。
2. **交错**：把第 1 步列出的每个其他写入方插到读和写之间。
3. **重复与乱序**：输入来两次、同时来两个、顺序颠倒、旧响应比新响应晚到。
4. **取值**：判断依赖的输入取边界值和旧格式。
5. **环境**：途中权限、配置或身份变了，锁、令牌、缓存、会话过期，新旧版本同时在跑，数据量放大。

风险最高的几次转移，再叠加两种故障，例如“超时后重试，旧请求也最终成功了”。

每个场景追到**终态**：数据最后是什么样，违反哪条不变量，有没有自愈机制。终态是数据停下的样子。抛出的异常、返回的错误、打出的日志是途中的一站，要接着追是谁接住了它。

**完成标准：**每次转移在每种适用算子下都有结论，结论只有三种：“安全”并写出起作用的机制；“违反”即成为候选；“未知”并写出缺哪项事实。这张表是你的底稿，用户要求时才放进输出。

## 3. 反证与定级

对每个候选找反证：上游是否已校验？数据库有没有唯一约束？框架或队列是否自带去重？部署方式是否让触发条件根本不会出现？有没有测试覆盖？一个函数里没有保护，不代表整个系统没有保护。

高严重度候选能用现有测试框架或一段脚本复现时，先复现再定级。用确定性方式注入故障：在切点处抛错或杀进程，用屏障或延迟强制交错顺序，用重放制造重复。只报告时，临时文件放在仓库外，或跑完删掉。

- **已确认**：代码、测试、日志、数据或复现直接证明，上下游约束也已核实；
- **高可信推断**：调用链足以推出后果，但没有实际运行；
- **待确认**：有具体线索，但缺一项会改变结论的事实，例如线上配置、部署拓扑或真实数据。

**完成标准：**留下的每条都经过反证；每条待确认项写明缺哪项事实。

## 4. 归因与排序

几个候选缺的是同一个机制时（例如支付边界没有幂等键），合成一条。根因写成缺失的机制，各候选作为触发路径挂在下面。

先按严重度排：数据错误与安全 → 撤不回的业务损失 → 服务不可用 → 用户看到错误结果。同档内按触发频率排。重复点击、超时重试、每周发布天天都在发生；几个罕见条件同时成立的排在后面。

**完成标准：**同一根因只占一条；每条写明严重度和触发频率的依据。

## 输出

每条 finding 写一段：触发条件、在哪一行走上岔路、已经发生了什么撤不回的事、终态、影响到谁、缺失的机制、证据与等级。缺任何一项，回去继续查或丢掉这条。

> **[高] 支付边界缺幂等键**。`order/pay.ts:42` 调用支付接口之后、把订单写成 `paid` 之前，如果进程重启，钱已经扣了，订单还是 `pending`。`jobs/retry.ts:18` 会重新发起扣款，而请求不带幂等键，用户被扣两次。另一条触发路径是 `web/checkout/Submit.tsx:30`：提交超时后按钮恢复可点，用户再点一次，同样二次扣款。证据：`pay.ts:40-48` 先调支付再写库，支付调用没有传 `idempotencyKey`；提交按钮只在请求进行中禁用。等级：高可信推断，未复现。

finding 之后依次写：

1. **未知项**：可能改变结论的事实，写明去哪里确认。
2. **范围外线索**与**转交项**：每条一行，写位置和原因。

没有成立的 finding 时，写“未发现可达条件下的系统失效”，再逐行列出已查的转移和保护它的机制。
