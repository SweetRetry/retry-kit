# Create a design.md

设计语言有两个载体，同一事实只住一处：取值归 Token 与组件代码，代码自己执行；代码表达不了、agent 按默认会做错的判断归 design.md。每条规则过删除测试：删掉它，agent 生成的界面会变，才写进 design.md。规则正向在先：先写产品用什么完成一件事，再写它因此不用什么；只做减法的 design.md 产出的界面比默认更空。具体流程和页面留在 PRD 与原型。

决策归用户，事实归你：能从项目查到的不问用户。

## 决策维度

下表是访谈清单，也是文件的章节顺序。每个维度写角色、预算与使用条件，取值留给 Token。

| 层 | 章节 | 要定的判断 |
| --- | --- | --- |
| 品牌 | Overview | 性格、受众、期望感受、不能像谁；辨识点，即哪几条用法让产品区别于最近的邻居；冲突优先级，即需求竞争时依次保护什么 |
| 规范 | Colors | 明暗主题及两者关系、中性色冷暖、强调色及其面积预算；主操作、状态、分类各由哪个角色承担 |
| 规范 | Typography | 正文与标题字体（同族或对比）、字阶与阅读角色的对应、数字字形 |
| 规范 | Layout | 密度、间距档位、内容宽度、窄屏时先让出什么 |
| 规范 | Elevation & Depth | 层级靠描边、阴影还是明度差；浮层如何区别于下层 |
| 规范 | Shapes | 圆角语言与嵌套 |
| 规范 | Motion | 高频操作与内容过渡各自的节奏；哪些变化值得动 |
| 品牌 | Voice & Content Strategy | voice 是产品以谁的身份、用什么人称说话；tone 按用户此刻的情绪利害分档，有温度的时刻（开始、空态、首次成功）与必须平实的时刻（报错、权限、计费、删除）各附一句本产品的真实文案；术语表，即每个产品概念的唯一叫法与禁用的同义词；数字、日期、时间与单位的格式 |
| 规范 | Components | 封闭词表：只用已发布的组件、变体与 Token 名，写明扩展口；悬停、焦点、禁用、加载、空、错误各靠什么区分 |
| 规范 | Illustration | 图标、插画与空态图形的语法（无、单色或彩色，静止或微动）、专用色、允许出现的时刻 |
| 应用 | Surfaces | 产品有哪几类界面，各自的首要任务、使用条件与覆盖的默认值 |
| 应用 | Do's and Don'ts | 封杀清单与无障碍下限；去掉套路后本产品靠什么建立张力 |

每条规则归入底线或默认值：

- **底线**换到任何一类界面都成立，决定产品像不像自己。通常是性格、不能像谁、辨识点、voice、冲突优先级、封杀清单、无障碍下限与封闭词表。
- **默认值**随界面任务变化，连同它依赖的使用条件一起写：操作频率、出错代价、输入方式、主角是界面还是内容、用户此刻的情绪。规范层的取值与 tone 通常是默认值；界面的使用条件不同才覆盖。

每个性格形容词落到至少一条规范层或应用层的可观测规则，说明它在界面上做什么，再配一条排除；没有落点的形容词是未决分支。

## 1. 查事实

读 Token、样式、组件变体、已上线页面、品牌素材与现有 design.md；局部更新只读受影响的部分。已上线代码优先于草稿，来源之间的冲突转为访谈问题。

## 2. 逐轮访谈

请求或现有 design.md 已给出的决定直接记录，只问没覆盖的维度。

按层推进：品牌、规范、应用。每轮提出所有前置已定的问题：编号，每题附基于事实的推荐答案，措辞让回答“yes”即采纳推荐。封杀清单一轮从下方候选里挑与产品界面相关的问。

规范层各维度与 tone 同样按轮提问，每个推荐答案对得上已定的性格、受众或界面任务；“不用”说得通时也是一个选项。项目没有 Token 来源时，推荐答案附具体取值，确认后即写入文件头的 Token。

用户的修正只在超出当前页面仍成立时写成规则。

### 封杀候选

每条是“套路，它想完成的事”。问用户产品靠什么完成这件事：答案写成正向规则，套路挂在它后面进 Do's and Don'ts。品牌明确选用的手法不问，用户点名的反例一并确认。

- 居中 Hero 加三张图标卡片，说明产品是什么。
- 卡片套卡片、层层描边，表达分组。
- 渐变文字、光斑、网格背景、毛玻璃、大面积投影，显得精致。
- 普通元数据套进徽章，标出状态。
- 标题前的装饰图标与图标底块，帮助识别。
- 页面上叙述创作过程的生成者口吻，没有要完成的事，直接封。

产品有数据与报告类界面时加问：

- 摘要、建议、结论重复同一主张，强调重点。
- 表格塞进窄栏、表头与单元格对齐不一，呈现证据。
- 不共享刻度或零基线的图表，显得有数据。
- 数字向好就标绿，表达好坏。

表中每个维度已定或明确省略、每个形容词有落点、用户逐条确认产品与邻居的每处差别且双方理解一致，访谈才结束；此前不写文件。

## 3. 写文件

新建文件命名为 `DESIGN.md`，已有同类文件沿用其名。章节名与文件头遵循 Google 的 [DESIGN.md 规范](https://github.com/google-labs-code/design.md/blob/main/docs/spec.md)：YAML 文件头承载 Token（`colors`、`typography`、`rounded`、`spacing`、`motion`、`components`），正文按上表顺序只写已定的章节，未讨论的章节不写；取值在别处的 Token 分组以分组名与理由记入文件头 `omitted`，`omitted` 只收 Token 分组名；已定为“不用”的维度是答案，照常写成规则。

- 规则写成可观测行为，容易误用处附理由。底线集中列在 Overview，其余即默认值。
- Overview 点名最近的邻居并列出辨识点，辨识点写产品做什么。
- 取值只有一个来源：项目已有 Token 来源（如 `globals.css`）时，正文点名公开 Token，并以行内代码 `` `@<路径>` `` 引用来源文件（从 DESIGN.md 所在目录解析，不得越出该目录），文件头省略该来源覆盖的全部分组；没有时文件头就是来源。Token 取值与组件内置样式由代码执行，正文只写它们的用法。
- 能机械检查的规则（溢出、对比度、未登记类名）交给脚本或 CI。

默认写一个文件。某类界面与默认值冲突时才拆分：根文件放品牌、共用规范与底线；界面文件开头写明继承哪个根文件、覆盖哪几条及理由，根文件以 `` `@<路径>` `` 引用每个界面文件。底线禁止的恰是某类界面的核心信息时，写成限定范围并配补偿约束的显式例外。同一条覆盖在两类以上界面都成立时，改根文件的默认值。

## 4. 验证与交付

先运行 `npx @google/design.md lint DESIGN.md`：error 清零，warning 逐条修正或在交付时说明理由。再逐条对照访谈答案与项目证据。新增行为原则时，用同一个真实页面和同一提示，两次都加载 Token，分别在不加载与加载 design.md 的条件下生成，并排呈现给用户；差别应正好是辨识点：加载后仍缺的辨识点是 design.md 漏写，两边都有的规则是空操作，删掉。加载后的页面还须更好：两页不标来源交给用户挑，输了说明 design.md 只做了减法，回访谈补正向规则。措辞修改不需重新生成。

交付 design.md、`omitted` 中的 Token 分组，以及未写章节和理由。用户要求接入时，在 AGENTS.md 或 CLAUDE.md 加一行指针。
