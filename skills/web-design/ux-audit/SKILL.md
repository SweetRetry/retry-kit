# UX Audit

要找的是用户心智模型与产品实际行为的落差：用户在这里犹豫、看错、点错、找不到，或出错后回不去。每条发现都要落到「某类用户做某个任务的某一步」上；只说得出「不好看」「不高级」的意见不在范围内，正常操作就报错的代码 bug 也不在范围内。

默认只报告。用户要修改时，按发现的根因改，改完重走触发它的任务步骤。

## 0. 定范围

- 审用户指定的页面、流程、设计稿或截图；用户说 `changes` 时，审当前改动触及的界面及与它同类的界面。都没有时先问。
- 写下**用户画像**（角色、熟练度、使用频率）与 2–5 个**核心任务**（用户来这里要完成的事，写成动宾短语）。需求文档、路由与导航能推出时直接推，推不出时问。
- 证据来源按可信度：运行中的产品 > 设计稿与原型 > 截图 > 只读代码。能运行就运行；启动受阻时先排除依赖、端口、环境变量，缺后端或登录时用临时 mock，交付前移除。只能读代码时，结论一律降为推断。

**完成标准：**每个核心任务都有起点页面与完成判据。

## 1. 走任务：最小惊讶走查

以画像里的用户身份，在真实渲染上逐个走完核心任务。每一步**先写预测，再操作**：

1. **预测**：只凭屏幕上可见的意符（signifier：文案、图标、位置、样式）写下「用户会点哪里、点了会发生什么」。
2. **操作**并截图。
3. **对照**：实际结果与预测不一致就是一处**惊讶**（Principle of least astonishment）。找不到入口、看不懂状态、走错分支、出现没声明的副作用（跳转、清空、提交、权限变化），都记下来。

每个任务至少再走一条异常路径：空数据、加载慢、校验失败、网络失败、取消到一半、重复提交、返回上一步。窄屏（375px）与纯键盘各走一遍主任务。

**完成标准：**每个任务的每一步都有「预测 / 实际 / 截图」三项；每个任务至少一条异常路径走到用户能继续或明确失败为止。

## 2. 盘点同类：设计漂移

**设计漂移**（design drift）是同一种东西在产品不同地方长成了不同的样子，各自看都没错，放在一起用户就得重新学。盘点它不能靠逐页看，要横向比：

1. 列出范围内的**同类物**：同一业务对象的名称、主操作按钮、破坏性操作与其确认方式、空状态、加载与报错反馈、表单校验时机、日期数字与单位格式、列表行操作的位置、页头结构、同级标题、成功提示。
2. 在走查经过的每个页面、每个视口执行 [scripts/drift-census.js](scripts/drift-census.js)（整个文件是一个无参函数，用浏览器工具的 evaluate 执行）。它按角色输出视觉签名的分布与界面用词；把各页结果按角色合并，同一角色出现多个签名、同一对象出现多个叫法的，都是候选。
3. 每个候选回答：这个差异在表达语义差异吗？表达的（危险操作更醒目、主次按钮不同）保留；不表达的就是漂移。

**完成标准：**每类出现两次以上的同类物都列出了全部变体与出现位置，每个变体判为「有语义」或「漂移」。

## 3. 逐条套用原则

对照 [references/heuristics.md](references/heuristics.md)，用第 1、2 步的记录逐条检验十条原则及其附带的透镜（信噪比、外部一致性、费茨定律等）。一处问题违反多条时，记在最直接的那条下，其余作为旁注。

**完成标准：**十条原则每条都有结论：通过（写出依据）、发现（进入候选）或不适用（写出原因）。

## 4. 反证与定级

对每个候选找反证：这是平台或行业惯例吗（外部一致性优先于内部偏好）？差异是否承载语义？用户画像真的会走到这一步吗？熟练用户的效率需求是否正好需要它？

按 Nielsen 严重度定级，同时写出三个依据：**频率**（多少用户、多常遇到）、**影响**（绕得过去还是卡住）、**持续性**（学一次就好，还是每次都踩）。

| 级别 | 含义 |
| --- | --- |
| 4 灾难 | 阻断核心任务、造成数据或金钱损失、无法恢复 |
| 3 严重 | 核心任务明显受阻或频繁出错，需要优先修 |
| 2 次要 | 造成犹豫或绕路，能自行恢复 |
| 1 外观 | 不影响完成任务，有余力再修 |

证据等级：**已观察**（走查中实际发生并有截图）、**推断**（由设计稿、代码或单张截图推出）、**待验证**（依赖真实用户行为，需要可用性测试或数据确认，写明要测什么）。

**完成标准：**留下来的每条都经过反证，严重度三个依据齐全。

## 5. 归因

多条发现缺的是同一个东西时合成一条，根因写成缺失的那个东西，各处表现挂在下面：漂移常来自没有共享组件或没有词表；状态不可见常来自没有统一的请求反馈层。

修复方向先改结构，再改文字：调整分组、顺序、控件类型、默认值与约束，让问题无从发生；结构解决不了时才加说明、提示或确认。

## 输出

先写一段总评：哪个核心任务最难完成、卡在哪里。然后按严重度从高到低列发现，每条一段：

> **[3 严重] 删除操作的确认方式漂移**（4 一致性与标准）。项目列表行内删除直接生效并给撤销 toast（`/projects`），成员列表删除弹确认框（`/members`），API Key 删除既不确认也不能撤销（`/settings/keys`）。用户在前两处学到的预期在第三处失效，误删 Key 立刻中断线上调用。频率：管理员每周操作；影响：不可恢复；持续性：每次都踩。根因：删除没有共享的确认组件。方向：不可逆删除统一走输入名称确认，可恢复删除统一走撤销 toast。证据：已观察，截图 `audit/keys-delete.png`。

发现之后依次写：

1. **覆盖表**：核心任务 × 十条原则，每格写通过、发现编号或不适用。
2. **漂移盘点表**：同类物、变体、出现位置、判定。
3. **待验证项**：需要用户测试或数据才能定论的问题，写明验证方法。
4. **范围外线索**：每条一行，写位置和原因。

没有成立的问题时，写「未发现有证据支持的可用性问题」，再附覆盖表与漂移盘点表。
