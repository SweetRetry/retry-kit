# UX Audit

要找两类问题：

- **体验落差**：用户在某一步犹豫、看错、点错、找不到，或出错后回不去。落在「某类用户做某个任务的某一步」上。
- **设计漂移**：同一种东西在产品里有了多种做法。每处单看都说得通，是长期迭代、每次只参照离得最近的代码累积出来的；用户要在每处重新学，维护者要改 N 处。落在「某类同类物的全部变体」上。

只说得出「不好看」「不高级」的意见不在范围内，正常操作就报错的代码 bug 与完整的 WCAG 合规审计也不在范围内。默认只报告；用户要修改时，先补护栏再按规范变体收敛，改完重跑盘点与触发问题的任务步骤。

## 0. 定范围

- 审用户指定的产品、页面、流程或设计稿；用户说 `changes` 时，审改动触及的界面及与它同类的全部界面（漂移在新旧之间产生）。都没有时先问。
- 用户只问一致性或漂移时，做第 1 步，第 2 步只走验证漂移所需的路径，第 3 步只看「一致」维度；其余情况全做。
- 写下**用户画像**（角色、熟练度、使用频率）与 2–5 个**核心任务**（动宾短语，带起点页面与完成判据）。需求文档、路由与导航能推出时直接推，推不出时问。
- 证据来源按可信度：运行中的产品 > 设计稿与原型 > 截图 > 只读代码。能运行就运行；启动受阻时先排除依赖、端口、环境变量，缺后端或登录时用临时 mock，交付前移除。

**完成标准：**有源码路径或明确无源码；有可运行入口或明确无法运行；核心任务各有起点与完成判据。

## 1. 盘点漂移

读 [references/consistency.md](references/consistency.md)，按其中的六层（取值、组件、模式、结构、语言、行为）盘点：

1. **代码盘点**：有源码时运行：

   ```bash
   node <skill 目录>/scripts/code-census.mjs <项目路径>
   ```

   输出按层列出每类同类物的全部变体、次数与位置，是候选清单。脚本覆盖不到的同类物（页头结构、空状态、新建入口、列表行操作、保存模型）按该文件的分层表在代码里搜。
2. **渲染盘点**：在第 2 步经过的每个页面、每个视口，用浏览器工具的 evaluate 执行 [scripts/drift-census.js](scripts/drift-census.js)（整个文件是一个无参函数）。把各页结果按角色合并，同一角色多个签名、同一对象多个叫法的列为候选。代码里同一份组件在渲染中出现多个签名，说明调用点覆盖了外观。
3. **判定**：每组候选按语义判据分成「有语义」与「漂移」；漂移组选出规范变体并写依据，列出收敛清单（偏离位置与数量）。

**完成标准：**六层每层都有结论；每类出现两次以上的同类物列出了全部变体，每个变体判为「有语义」「漂移」或「规范」；每组漂移有规范变体与收敛清单。

## 2. 走任务：最小惊讶走查

以画像里的用户身份，在真实渲染上逐个走完核心任务。每一步**先写预测，再操作**：

1. **预测**：只凭屏幕上可见的意符（signifier：文案、图标、位置、样式）写下「用户会点哪里、点了会发生什么」。在别处学到的预期也算：第 1 步盘点出的同类物，在这里应该与在别处一样。
2. **操作**并截图。
3. **对照**：实际与预测不一致就是一处**惊讶**（Principle of least astonishment）。找不到入口、看不懂状态、走错分支、出现未声明的副作用（跳转、清空、提交、通知他人、产生费用），以及同类物在这里的行为与别处不同，都记下。

每个任务至少再走一条异常路径：空数据、加载慢、校验失败、网络失败、取消到一半、重复提交、返回上一步。窄屏（375px）与纯键盘各走一遍主任务。第 1 步「行为」层的候选（Esc、点击外部、焦点回归、返回键、URL 状态）在这里逐一实测。

**完成标准：**每个任务的每一步都有「预测 / 实际 / 截图」三项；每个任务至少一条异常路径走到用户能继续或明确失败为止；行为层候选都有实测结论。

## 3. 逐维检验

对照 [references/principles.md](references/principles.md)，用第 1、2 步的记录逐个检验八个维度：理解、行动、反馈、恢复、专注、一致、信任、可达。每个维度下的透镜（概念模型、费茨定律、信噪比、格式塔、暗黑模式等）都过一遍。一处问题违反多个维度时，记在最直接的那个下，其余作为旁注。

**完成标准：**每个核心任务在八个维度上都有结论：通过（写出依据）、发现（进入候选）或不适用（写出原因）。

## 4. 反证与定级

对每个候选找反证：这是平台或行业惯例吗（外部一致性优先于内部偏好）？差异是否承载语义？用户画像真的会走到这一步吗？熟练用户的效率需求是否正好需要它？

按 Nielsen 严重度定级，写出三个依据：**频率**（多少用户、多常遇到）、**影响**（绕得过去还是卡住）、**持续性**（学一次就好，还是每次都踩）。

| 级别 | 含义 |
| --- | --- |
| 4 灾难 | 阻断核心任务、造成数据或金钱损失、无法恢复 |
| 3 严重 | 核心任务明显受阻或频繁出错，需要优先修 |
| 2 次要 | 造成犹豫或绕路，能自行恢复 |
| 1 外观 | 不影响完成任务，有余力再修 |

漂移按它造成的最坏后果定级：在一处学到的预期到另一处导致误操作（一处删除可撤销，另一处立即永久删除）至少是 3；只是视觉不齐是 1–2。漂移还要写出**扩散度**（涉及多少处）：扩散度不改变对用户的严重度，但决定修复的批量方式。

证据等级：**已观察**（走查中实际发生并有截图）、**代码确认**（盘点脚本或源码直接证明）、**推断**（由设计稿、单张截图或调用链推出）、**待验证**（依赖真实用户行为，写明要测什么）。

**完成标准：**留下来的每条都经过反证，严重度三个依据齐全，漂移条目写出扩散度。

## 5. 归因与护栏

多条发现缺的是同一个东西时合成一条，根因写成缺失的那个东西，各处表现挂在下面。漂移的根因是缺少让一致成为默认的结构；按 consistency.md 的护栏表给出对应护栏（lint 规则、共享组件、模式 hook、词表、唯一格式化函数）。只收敛不补护栏，漂移会在下一轮迭代中长回来。

修复方向先改结构，再改文字：调整分组、顺序、控件类型、默认值与约束，让问题无从发生；结构解决不了时才加说明、提示或确认。

## 输出

先写总评：最难完成的核心任务卡在哪里；漂移最严重的层与它的根因。然后按严重度从高到低列发现，每条一段：

> **[3 严重] 删除的确认与撤销漂移**（一致 · 恢复）。项目列表删除直接生效并给撤销 toast（`/projects`），成员删除弹确认框（`/members`），API Key 删除既不确认也不能撤销（`/settings/keys`）。用户在前两处学到的预期在第三处失效，误删 Key 立刻中断线上调用。频率：管理员每周操作；影响：不可恢复；持续性：每次都踩。扩散度：3 种做法、11 处（代码盘点「模式：确认」）。根因：删除没有共享的确认组件。规范变体：不可逆删除输入名称确认，可恢复删除给撤销 toast。护栏：抽出 `useConfirmDelete`，lint 禁止直接调用 `confirm(`。证据：已观察，截图 `audit/keys-delete.png`；代码确认。

发现之后依次写：

1. **漂移盘点表**：层、同类物、变体与次数、判定、规范变体、收敛清单、护栏。
2. **覆盖表**：核心任务 × 八个维度，每格写通过、发现编号或不适用。
3. **待验证项**：需要用户测试或数据才能定论的问题，写明验证方法。
4. **范围外线索**：每条一行，写位置和原因。

没有成立的问题时，写「未发现有证据支持的体验问题或设计漂移」，再附漂移盘点表与覆盖表。
