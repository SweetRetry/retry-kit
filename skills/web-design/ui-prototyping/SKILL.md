# UI prototyping

把尚未定案的交互模型或视觉取值做成同一页里可操作的候选，让用户在相同条件下体验，逐轮收敛到一个。

## 原则

- **先改需求**。界面感觉糟糕时根因多在任务定义：多塞的维度、多出的步骤、揉进一屏的两种目标。对照用户要完成的任务，先写明现有流程里哪些步骤、字段或分支被删除、合并或推迟及其理由，改不动的部分才进入候选比较。改既有界面时把现状作为基线候选放进第一轮。
- **押注而非变体**。每个候选代表一种交互模型，是对发现性与效率、信息量与可扫读、速度与防错这类拉扯的一次押注，能说出它在哪种使用情境下胜出，且是愿意交付的方案。只换颜色、圆角或间距的近亲只留一个。
- **公平**。所有候选用同一任务、内容、数据、viewport 和起始状态。比单一决策时其他条件一致；比整体方向时可一起改变相互依赖的布局、层级与交互。
- **可操作**。会影响决定的行为做出来：点击、输入、取消、返回、重试。loading、empty、error、success 只在改变取舍时做。mock 数据的数量与形态足以触发待判断的行为。
- **库只用于非决策部分**。模板自带 Basecoat（shadcn 风格组件）与 Alpine（状态与渲染）。被比较的决策点手写；不在比较范围内的控件、列表与状态交给库，省下的精力用来加深候选。
- **画布只放候选**。画布上只有候选和完成任务所需的 UI，含必需的 label、help text 与 error message。方案介绍、假设、取舍、操作教程与评价写在交付消息里。
- **隔离**。数据与 side effect 本地模拟，不连真实账号、密钥或可写服务；只剩一个候选并获用户确认前，仓库与外部服务不改动。
- **只收不发**。每轮候选数不超过上一轮。用户认可多个候选时，优点能在同一交互模型里共存就合并；优点互相冲突才分别细化，让冲突点更容易体验。新方向只替换被淘汰的候选。

## 流程

1. **定义决策**。一句话写清用户要完成的任务、改掉的需求，以及这次在哪些做法之间选。有现有产品或代码时只查候选会用到的真实内容、viewport、token、组件与约束；没有证据的产品规则作为假设在交付时说明。比较的是视觉取值而非交互模型时改走[取值模式](reference/value-mode.md)。
2. **第一轮**。`mktemp -d` 在仓库外建目录，`cp` [assets/template.html](assets/template.html) 为 `index.html`；用户要求保留时写入指定位置。模板头部注释说明候选 section、sidebar、库与取值变量的用法。做 2 到 4 个押注；说得通的只有两个就做两个。
3. **交付第一轮**。`index.html` 的可点击绝对路径；需要在每个候选中完成的同一任务；候选的核心差异、各自胜出的情境与本轮的决策问题；用户可能预期却没做成候选的做法，各附一句理由。文件直接打开无法工作时才给本地 static server 命令。
4. **逐轮收敛**。在同一文件里做下一轮：`grep -n data-prototype-component` 定位，只读改本轮涉及的 section；淘汰候选删整个 section，认可的特性合入保留者，再补真实内容与影响取舍的状态。每轮只交付本轮的删除、合并或细化及理由，和新的决策问题。用户报告显示问题时才截图。
5. **定案**。只剩一个候选且用户确认后才改实际代码。原请求含正式实现则在仓库中实现并验证；否则交付原型后结束。

完成标准：每轮候选数不超过上一轮，且只在优点互相冲突时保持不变；多个候选时每个 sidebar 入口都到达一个能完成同一核心任务的候选；原型可直接打开或附带 static server 命令；定案前仓库与外部服务无改动。
