# 微交互与交互反馈

微交互是“触发、规则与状态、反馈、焦点收尾”的完整闭环。将过渡时长设为 `0ms` 后，语义与可操作性必须依然完整。

## 1. 控件级微交互

- **热区**：独立控件的热区至少 `24×24px`，窄屏主操作扩至 `40–44px`。视觉需保持紧凑时，用伪元素（`relative before:absolute before:-inset-2`）扩区。段落内的行内链接除外。
- **即时与短循环**：独立开关与轻量切换点击即生效，不配保存按钮。短时确认动作（复制、同步）在触发控件原地切换约 `1.5–2s` 后复原，复原前再点重置计时，不额外弹 toast。相邻 Tooltip 跳过开启延迟即时切换。
- **校验时机（晚报错、早消错）**：失焦或提交时触发报错。字段进入报错态后，随输入实时复检并在合法时立即清除。提交校验失败时，聚焦首个报错字段。
- **禁用态可解释**：需要告知解锁条件时，在控件旁写可见前提，或用 `aria-disabled="true"` 保持可聚焦并就近提示。
- **焦点闭环**：打开浮层时，焦点落到首个输入项或安全项，破坏性弹窗绝不自动聚焦破坏性按钮。按 `Escape` 只退出最内层，关闭后回焦到原触发控件。删除当前聚焦项后，焦点顺移到相邻项或空态入口，不掉回 `body`。
- **可打断**：连续操作与浮层开关随时从当前状态衔接新意图。业务逻辑绝不等待动效结束。

## 2. 反馈形态

用两个问题确定反馈载体，不看消息严重程度：

1. **用户需要在原处修改输入吗？** 需要时，用就地 inline 反馈。字段报错放在字段旁并配 `role="alert"`，弹窗内的提交失败留在弹窗内。toast 自动消失会带走修正入口，这类失败不用 toast。
2. **状态会持续多久？**
   - 一次性结果（保存、删除、导出）用自动消失的 toast（`toast.success` / `toast.error`），成功不弹弹窗。
   - 持续状态保持可见直到解除。局部持续状态（无数据、加载失败）落在所在区域，按成因（首次使用、筛选无结果、无权限、加载失败）给出下一步操作。全局持续状态（连接中断）用固定 `id` 的驻留 toast，恢复时调用 `toast.dismiss(id)`。

遵守以下反馈约束：

- 同一动作只给一种反馈。
- toast 只写一句话，细节留在原处。
- 批量部分失败用一条 `toast.warning`，写明成功与失败数量。
- 局部提交的等待态放在触发按钮内。只有跨页面或原上下文已消失的长任务，才用 `toast.loading` 获取 `id`，结束时用同一 `id` 转为 success 或 error。

## 3. 等待与恢复

- **更新策略**：结果可撤销且极少失败时，用乐观更新（optimistic update）。提交前先按成功渲染并保存快照，失败时回滚并就近说明，不用刷新页面代替恢复。结果不可逆或常失败时，用悲观更新（pessimistic update），等待服务端确认后再变更界面，反馈留在触发控件上。

| 等待时长 | 反馈 |
| :--- | :--- |
| < 100ms | 直接完成，不加 Loader |
| 100ms–1s | 触发控件内局部反馈，不遮蔽上下文 |
| 1s–10s | 展示真实执行状态，进度与步骤来自真实数据 |
| > 10s 或持续数据流 | 提供取消或离开后重入，区分停止客户端等待与取消服务端任务 |

- **防重**：会造成重复扣款、重复创建或写冲突的操作，按下即防重。可安全重复或持续输入的操作不禁用。
- **竞态**：切换、分页与筛选时，丢弃不属于最新意图的响应。
- **保留输入**：提交、校验或网络失败后，保留用户已填内容与选项。
- **不可逆操作**：在不可逆时点前确认影响范围，或提供有效撤销。
- **破坏性操作隔离**：破坏性按钮不与正向主按钮紧挨并列。弹窗与表单底部正向主按钮放在端侧，破坏性按钮用弱样式并拉开间距。菜单中的破坏性条目置于最底部，用 `DropdownMenuSeparator` 隔开并设 `variant="destructive"`。
