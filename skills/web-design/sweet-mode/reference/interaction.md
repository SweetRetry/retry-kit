# 交互反馈

## 1. 反馈形态

由两个问题决定，不看消息严重程度：

1. **用户要在原处修改输入吗？** 要 → 就地 inline：字段错误在字段旁（配 `role="alert"`），对话框内的提交失败留在对话框内。toast 消失会带走修正入口，这类错误不用 toast。
2. **状态持续多久？** 一次性结果（保存、删除、导出）→ 自动消失的 toast（`toast.success` / `error`），成功不弹 Dialog。持续状态保持可见直到解除：局部的（无数据、加载失败）落在所在区域，按成因（首次使用、筛选无结果、无权限、加载失败）给出下一步操作；全局的（连接中断）用固定 `id` 的驻留 toast，恢复时 `toast.dismiss(id)`。

- 同一动作只给一种反馈。
- toast 只写一句话，细节留在原处。
- 批量部分失败用一条 `toast.warning`，带成功与失败数。
- 局部提交的等待放在触发按钮内；只有跨页面或原上下文已消失的长任务用 `toast.loading` 取 `id`，结束时用同一 `id` 转为 success / error。

## 2. 等待与恢复

结果可撤销且极少失败 → 先呈现结果，失败时回滚到真实状态并就近说明，不以刷新代替恢复。不可逆或常失败 → 等服务端确认，反馈放在触发控件上。

| 等待时长 | 反馈 |
| :--- | :--- |
| < 100ms | 直接完成，不加 Loader |
| 100ms–1s | 触发控件内局部反馈，不遮蔽上下文 |
| 1s–10s | 展示真实执行状态，进度与步骤有真实来源 |
| > 10s 或持续数据流 | 提供取消或离开后重入；区分停止客户端等待与取消服务端工作 |

- **防重**：会重复扣款、创建或写冲突的操作按下即防重；可安全重复或持续输入的操作不禁用。
- **竞态**：切换、分页、筛选时丢弃不属于最新意图的响应。
- **保留输入**：提交、校验或网络失败后保留已填内容与选项。
- **不可逆**：在不可逆时点前确认影响范围，或提供有效撤销。
