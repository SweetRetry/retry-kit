# design.md 闭环验证与评估指南 (Eval & Verification)

这份指南用于验证生成的 `design.md` 是否真正改变了模型的决策，以及如何持续维护它。

---

## 一、 验证的核心哲学：检验结构，而非仅看字体

Vercel 探索过程最重要的经验是：
**一份起效的 `design.md`，带来的改变是“结构性”的，绝不仅仅是“换了好看的字体”**。

如果 Guided 页面只是在 Baseline（无 design.md）的基础上美化了颜色或字号，说明 `design.md` 失败了。
当出现以下结构变化时，说明设计指引真正起效：
1. **首屏诉求重塑**：从“泛用 SaaS 居中标题 + 3张卡片”，重塑为“直接呈现核心结论与决定性证据”。
2. **论据呈现方式改变**：证据表格从局部狭窄的侧栏扩展为 12 栏全宽；离散数据被整合为共享刻度的清晰视图。
3. **噪音消除**：删除了互斥重复的“背景”、“总结”与纯装饰性图表；普通元数据不再被滥加药丸徽章。

---

## 二、 极简 A/B 对比验证法 (Matched Comparison)

无需复杂的自动化评测系统，通过一次对照测试即可直观验证：

### 1. 选取一个真实高频场景 (One Realistic Scenario)
* 避免抽象的“生成一个现代化页面”，挑选一个团队真实需要输出的页面（例如：客户续约提议、性能基准报告、ROI 计算器或发布说明）。
* 准备真实的输入数据与读者角色设定。

### 2. 运行 Baseline (对照组)
* 保持提示词和数据完全一致，**不加载 `design.md`**，直接让模型生成页面代码。
* 保存首个生成结果（哪怕很难看），作为对照基准。

### 3. 运行 Guided (实验组)
* 同样的环境、模型、提示词和数据，**加载生成的 `design.md`**。
* 生成页面代码。

### 4. 盲审或对照打分 (Checklist)

| 检查维度 | Baseline 常见败笔 | Guided 预期达标表现 |
| :--- | :--- | :--- |
| **首屏 (First Viewport)** | 居中大 Hero Banner，空洞口号 | 直接呈现关键结论、计算工具或决定性图表 |
| **表格排布 (Tables)** | 被困在窄分栏内，表头多处换行挤压 | 占满全宽 12 栏，数值右对齐，表头单元格严格对齐 |
| **AI 味 (Slop Index)** | 充斥渐变光斑、每条文字套 Card、Pill 泛滥 | 干净单色底，靠排版与留白建立层级，无多余边框 |
| **词表封闭性 (Vocabulary)** | 模型自由发挥类名（如 `my-custom-cool-card`） | 仅使用已发布的规范类名或标准的语义化 HTML |

---

## 三、 确定性机械检查 (Layer 3: Deterministic Checks)

属于物理或语法维度的规则，应尽可能通过脚本或自动化检查完成，而不是在提示词中空耗篇幅：

1. **类名白名单断言**：
   * 提取生成 HTML 中所有的 `class` 属性，断言其必须落在已发布的 Bounded Vocabulary 或 `<prefix>-custom-*` 逃逸阀内。
2. **表格宽度检查**：
   * 检查证据表格未被嵌套在窄栅格容器中。
3. **元数据标签滥用检查**：
   * 检查是否出现超过 2 个带有 Badge/Pill 样式的非状态文本。
4. **无障碍底线**：
   * 单一 `h1`，包含 `<main id="main">`，包含跳过链接（Skip Link）。

---

## 四、 纠偏分流法 (Triage Tree)

日常收到的各种修改反馈，按此决策树精准归位，绝不把所有东西都塞进 `design.md`：

```
收到一条具体的纠偏或修改意见：
├── 能否用自动化脚本或正则在 HTML/CSS 上直接校验？（如溢出、非法类名、标签嵌套）
│       → 归入 Layer 3: 确定性检查代码 / CI 校验
├── 是否为具体数值、色彩值、间距尺度、字号大小或类名？
│       → 归入 Layer 2: 样式表与 Token 词表（Bounded Vocabulary）
└── 是否属于受众预期、论据呈现逻辑、层级取舍或审美封杀？
        → 归入 Layer 1: design.md 的正文规范（必须写成可观测行为）
```
