# UI prototyping

## 1. 定义决策

开始写 HTML 前，用一句话写清用户要完成的任务，以及这次要在哪些做法之间选择。

有现有产品或代码时，只查候选会用到的真实内容、viewport、design token、组件和约束。没有证据的产品规则作为假设，在交付时说明。

选候选前先穷举设计空间：列出这个决策的每个维度及各维度上的可行做法，组合成所有可区分的交互模型，直到再想不出与已列做法本质不同的新做法。第一轮从中选 2 到 4 个彼此差异最大、合起来覆盖整个空间的候选，每个候选代表一种不同的交互模型。只换颜色、圆角或间距的近亲方案只留一个。

比较的是视觉取值而非交互模型时，改用下面的取值模式，跳过第 2、3 节。

### 取值模式

比较对象是色彩、字体、圆角、密度、层级表达或动效参数。细微差异本身就是要判断的东西，近亲取值不合并。

1. 穷举每个维度的取值空间：逐维度列出可区分的取值，直到再细分已看不出差别。
2. 只做一个画面：复制模板后只保留一个 section，放一张 Foundations 样张（色彩配比、表面层级、圆角、字阶、状态、按钮与输入）和一到两张真实页面，用真实内容。
3. 每个维度做成一组选项控件，写入根节点的 data 属性或 CSS 变量；各维度自由组合切换，整个画面同步变化。控件固定在画面一角，是这个模式下画布唯一允许的非候选 UI。
4. 每轮交付路径、各维度当前的选项，以及需要用户判断的组合问题。用户反馈后缩减各维度的选项；选定的维度删除控件，取值写死。
5. 所有控件删除后剩下的画面就是设计版，记录全部选定取值，供 design.md 与 Token 引用。是否留存、留在哪里由用户决定。

## 2. 构建第一轮

1. 用 `mktemp -d` 在仓库外创建目录，用 `cp` 把 [assets/template.html](assets/template.html) 复制为 `index.html`。用户要求保留时，写入用户指定的位置。
2. 每个候选写成一个 `section[data-prototype-component]`，带唯一的 `id` 和具体组件名的 `data-label`。模板按这些 section 自动生成 sidebar。
3. 模拟数据和共用逻辑只写一份，供所有候选使用。
4. 动画的时序、进入方式或中断行为会影响选择时，把 `body` 的 `data-motion` 设为 `true`。自定义动画遵守 `prefers-reduced-motion`。

构建时遵守以下规则：

- **公平**：所有候选使用同一个任务、内容、数据、viewport 和起始状态。比较单一决策时，其他条件保持一致；比较整体方向时，可以一起改变相互依赖的布局、层级和交互。
- **可操作**：把会影响决定的行为做出来，用户能点击、输入、取消、返回和重试。loading、empty、error 或 success 会改变取舍时，才做这些状态。模拟数据的数量和形态要足以触发待判断的行为。
- **画布**：只放候选组件和完成交互所需的 UI，包括组件必需的 label、help text 与 error message。方案介绍、hypothesis、trade-off、操作教程和评价写在交付消息中。
- **隔离**：数据和 side effect 都在本地模拟，不连接真实账号、密钥或可写服务。文件直接打开无法工作时，才提供本地 static server 命令。

## 3. 逐轮收敛

第一轮发散，之后每一轮都收敛：候选数不超过上一轮，并尽量减少，直到只剩一个候选。

第一轮交付：

- `index.html` 的可点击绝对路径；
- 需要在每个组件中完成的同一任务；
- 候选的核心差异，以及本轮保留哪个候选的决策问题；
- 穷举出但没做成候选的做法，各附一句落选理由。

之后每轮只交付本轮的删除、合并或细化及理由，以及新的决策问题。

用户反馈后，在同一文件中做下一轮。用 `grep -n data-prototype-component` 定位 section，只读取和编辑本轮涉及的 section；淘汰候选时删除整个 section。

1. 删除用户淘汰的候选，把用户认可的特性合入保留的候选。
2. 反馈认可多个候选、没有淘汰任何一个时，先分析各候选的优缺点，再按以下顺序选择：
   - 优点能在同一个交互模型里共存时，合并为更少的候选。
   - 优点互相冲突时，分别细化各候选，让冲突点更容易体验和判断，候选数保持不变。
3. 加深保留的候选：补真实内容、会影响取舍的状态和细节。

用户要求新方向时，先从设计空间里未做成候选的做法中选取，新候选只替换被淘汰的候选，候选数不超过上一轮。用户报告显示问题时，才截图定位。

只剩一个候选时，模板自动移除 sidebar，候选占满页面。继续在原型中打磨，直到用户确认。

## 4. 进入实现

实际代码只在只剩一个候选且用户确认后改动。在此之前，所有改动只写入临时原型目录。原请求包含正式实现时，在仓库中实现这个候选并验证；否则交付原型后结束。

完成标准：每轮候选数不超过上一轮，且只在优点互相冲突时保持不变；多个候选时，每个 sidebar 入口都到达一个可完成同一核心任务的候选；原型可直接打开或附带必要的 static server 命令；只剩一个候选并获确认前，仓库与外部服务没有任何改动。取值模式下，每轮各维度的选项数不增加，所有控件删除并获用户确认才算完成。
