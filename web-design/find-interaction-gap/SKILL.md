# Find Interaction Gap

## 1. 核心心智模型 (Mental Model)

交互的本质是**系统与用户在时间轴上的有限状态机（Finite State Machine）对话与连续可控性**。
在代码层面“输入能拿到输出”绝不等于“交互成立”。Agent 在编码和设计交互时最普遍的痼疾是**“头尾综合症（Head-and-Tail Syndrome）”**：
- **只写了“头”（触发入口）**：放一个按钮或表单；
- **只写了“尾”（最终数据写入或页面跳转）**：拿到响应直接 render 最终态；
- **“中间过程”彻底裸奔与黑盒**：
  - 点击后没有任何即时反馈（假死 1-2 秒，用户以为没点着疯狂连击）；
  - 异步处理中途没有任何进度或状态感知（不知道是卡死了还是在处理）；
  - 失败了直接抛一串报错甚至直接静默，用户辛辛苦苦填的表单被瞬间清空；
  - 破坏性操作没有二次确认或撤销机会；
  - 长任务无法中断、离开后找不到进度入口；
  - 弹窗关闭后键盘焦点迷失，屏幕阅读器断流。

本技能检查指定交互中有实际任务后果的过程缺口。审查时报告证据和建议；只有已授权修补时才修改实现，不因检查维度或示例存在就新增产品能力。

## 2. 交互有限状态机 (FSM) 全生命周期审查

按实际存在且影响任务结果的状态检查**逻辑实现与用户感知**，无需为每个交互补齐所有阶段：

```text
[Idle 就绪] ──> [Armed 预备/校验] ──> [In-Flight 执行中] ──> [Settled 结算] ──> [Recovery/Cleanup 恢复]
                         │                    │                    │
                   (前置限制提示)      (防重/阶段进展/流式)   (成功高亮 / 人话报错)
```

### 1. Idle ➔ Armed（触发前与意图呈现）
- **具体动词 Affordance**：操作文案必须是具象动词（如“立即扣费生成”、“导出为 CSV”），而非模糊的“确定”。
- **Disabled 原因显式化**：按钮若处于禁用状态，**必须就近告知差什么条件才能点**（如鼠标悬浮提示“需先上传至少 1 张图片”），严禁无由来的静默置灰。

### 2. Armed ➔ In-Flight（触发瞬间与防重防并发）
- **0ms 本地感知**：点击的瞬间（第 0 毫秒），按钮必须呈现按下态（Active/Pressed）或局部 Spinner 动效，确认系统已受理。
- **并发与防重拦截**：重复触发会导致重复扣款、重复创建或写冲突时，检查既有防重机制；不对可安全重复或需要持续输入的交互一律禁用。

### 3. In-Flight 执行中（感知性能时间法则）
根据耗时提供分级感知，杜绝假死体验：
- **瞬时操作（< 100ms）**：直接完成，无需任何加载器。
- **微等待（100ms – 1s）**：按钮内 Spinner 或微动效，**严禁弹全屏 Loading 遮蔽上下文**。
- **中长等待（1s – 10s）**：反馈已知的执行状态；有真实进度来源时展示步骤或进度，不为填满界面虚构阶段和百分比。
- **长任务与持续数据流（> 10s / SSE / 批处理 / 分块传输）**：
  - **可中止性**：用户需要停止且运行机制支持时，检查取消契约；区分终止客户端等待与取消服务端工作。`AbortController` 仅是适用客户端请求的一种实现。
  - **可重入性**：任务已支持后台运行，或用户明确需要离开后继续跟踪时，检查进度重入路径。新增后台执行、持久进度或取消能力须在授权范围内，否则作为建议交付。

### 4. 竞态与乐观更新处理 (Race Conditions & Optimistic UI)
- **竞态条件防范**：快速切换 Tab、分页或搜索筛选时，必须追踪请求序号/Token，**防止旧请求慢于新请求返回而覆盖最新意图**。
- **乐观更新平滑回滚**：乐观更新若在服务端失败，恢复真实状态并就近说明失败；仅在可安全重试时提供重试入口，不用全屏报错或强制刷新重置替代恢复。

### 5. Settled 结算（成功明确，失败说人话）
- **成功态**：让用户能识别操作结果；结果本身已清楚可见时，不再强制叠加高亮、Toast 或下一步引导。
- **失败态**：**绝对禁止只弹一句“操作失败”或一串系统错误码**！必须满足两要素：
  1. **已知且可理解的原因**；原因尚未确定时说明当前限制，不编造诊断；
  2. **说明可用的恢复方式或当前限制**；仅在操作可安全重试且已有相应能力时提供“重试”，不虚构恢复路径。

### 6. Recovery 异常挽救与草稿韧性 (Resilient Recovery)
- **草稿保护原则**：当提交失败、表单校验未通过、或网络突发中断时，**严禁重置/清空用户已输入的内容**！必须完整保留所有已填字段与选定项。
- **破坏性操作防线**：删除、覆盖、批量解绑等不可逆高风险操作，必须在不可逆时点前提供清晰的确认弹窗（明确说明影响范围），或在操作后提供数秒内的 **撤销（Undo）机制**。
- **焦点与无障碍闭环 (Focus Management)**：模态框关闭后焦点必须原路返回触发点，动态列表内容变更需通过 `aria-live` 向屏幕阅读器播报。

## 3. Agent 典型“头尾综合症”排查清单

| 常见交互断裂（Gap） | 典型翻车场景 | 正确的补全方案 |
| :--- | :--- | :--- |
| **点击后“假死”** | 点击保存后界面无任何变化，1.5 秒后突然跳转。用户误以为没反应连续点击了 3 次。 | 按钮立即进入 Loading + 禁用态，提交中阻止重复点击。 |
| **失败“一刀切清空”** | 填了 20 个字段的表单，因验证码填错提交失败，页面刷新后所有内容全部清空。 | 拦截错误，仅将验证码标红提示，保留其他 19 个已填字段。 |
| **黑盒长任务** | 点击“批量处理/导出大文件”后，弹出一个全屏转圈圈，转了 30 秒用户不知道进行到哪了，也不敢关页面。 | 局部展示分步进展（`处理分块 1/5...`），并提示“您可安全离开此页面，完成后在历史列表查看”。 |
| **耗时操作不可中止** | 正在执行耗时数据处理或流式传输，用户发现参数选错了，但页面上没有任何“取消/停止”按钮。 | 引入 `AbortController`，执行中途将操作按钮切换为“取消 / 中止”状态。 |
| **竞态覆盖** | 用户快速从 Tab A 切换到 Tab B，Tab A 的慢请求在 2 秒后返回，把 Tab B 的内容刷成了 Tab A。 | 在组件内维护最新的 `requestId` 或使用 `AbortController` 在切换时取消上一个请求。 |
| **天书式报错** | 接口报错直接把 `TypeError: Cannot read properties of undefined` 或 `500 Internal Error` 弹给用户。 | 捕获底层异常，转译为“服务响应异常，请稍后重试”，并在控制台保留详细日志。 |
| **无声成功** | 点击“添加到收藏”后没有任何提示或图标变色，用户不知道到底添加上了没有。 | 收藏图标瞬间填充实心并带有微弹动动效，底部弹出轻量 Toast。 |

## 4. 审查与输出交付规范

审查交互过程时，按以下格式输出 findings：

```text
- [FSM 阶段] [交互过程断裂]: [简明问题描述]
  - 交互场景：[用户在什么界面试图执行什么操作]
  - 缺失的过程/感知：[指出 Agent 在中间遗漏了什么：如无即时反馈、等待无进展、失败清空输入、无停止按钮等]
  - 用户体验后果：[用户在此处会产生何种困惑、焦虑、重复误操作、数据丢失或状态错乱]
  - 最小补全建议：[仅针对已证实缺口说明所需行为；用户已授权实现时才交付代码与验证]
```
