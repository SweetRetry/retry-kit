# SaaS UX Writing

SaaS 界面是多人协作、带状态流转、受权限与配额约束的专业生产器物。界面文案存在的唯一目的，是把系统的**领域模型、状态转移与操作边界**无损映射到用户心智，让用户在扫视瞬间明确三件事：**这是什么对象与状态、点下去会发生什么结果、代价与影响边界在哪里**。

顺着原文案逐句“润色”，只会把机器腔换成口头语，或把错位的领域概念修饰得更通顺。因此必须从第一性原理出发，按**核心原则 → 语境与封闭词表 → 操作边界与信息增量 → 器物书面语与组件规范 → 交付验收**的顺序推进。页面布局重构、纯视觉样式与长篇营销文章不在本 skill 范围。

## 核心原则（First Principles）

1. **语境同构（Context Isomorphism）**
   文案中的每个称谓都在定义人与组织、人与资产的权责关系。称谓必须与产品的**组织治理模型**严格同构（如平权团队协作称“成员 / 工作区”，企业行政管控称“员工 / 部门 / 审批”），绝不跨模型借词。信息的详略由**场景扫视频率与出错代价**决定：每日扫视上百次的高频作业面极简安静；低频但影响全空间或账单的治理与商业操作则把边界一次说透。

2. **封闭词表与动作单义（Closed Lexicon & Bijective Verbs）**
   SaaS 用户靠名词识别业务对象、靠动词预判状态变化。全局遵循**一物一名、一动一义**：同一实体在导航、表头、表单、弹窗、通知中只用一个标准名词；不同数据后果的操作（如创建 vs 添加 vs 邀请，移出 vs 归档 vs 移至回收站 vs 永久删除 vs 吊销）各有唯一动词，绝不混用。

3. **信息增量与边界完备（Information Delta & Boundary Completeness）**
   界面上的每句文字都必须提供**同屏其余元素尚未表达的增量事实**。能从标题、上层容器、字段名或控件状态直接推知的同义复述一律删除；而跨越**影响半径、资产去向、生效与可逆性、权限与配额**四条边界的操作，必须在决定前把后果与出路交代清楚。

4. **器物书面语（Instrument Written Voice）**
   SaaS 工作台是专业工具，不是聊天室，也不是系统日志或行政公文。文字保持**无我、克制、高信息密度**：以产品、模块或业务对象为主语客观直陈事实，彻底剥离口头语（语气助词、熟稔套近乎、口语动词、是非问句）、机器腔（翻译腔虚词、被动句、底层实现词）与官僚客服套话（客套寒暄、感叹号、暗黑挽留）。

## 1. 建立语境与封闭词表

动笔前先读取代码（数据 schema、角色枚举、路由结构、i18n 与组件文案、`design.md`）与用户材料，锁定以下四项前提：

### A. 判别组织与治理模型

| 组织模型 | 产品形态特征 | 容器标准称谓 | 人员与身份称谓 | 关系与权限流转动作 | 严禁混入的错位词 |
| --- | --- | --- | --- | --- | --- |
| **团队协作型**<br>（Team / Workspace） | 平权协作、自发组建、项目驱动（协作文档、设计、研发、项目管理） | 工作区、团队、项目、空间 | 成员、访客、协作者、所有者、管理员 | 邀请、加入、移出、分配、共享、转让所有权 | 员工、下属、上级、工号、部门录入、离职、调岗 |
| **企业管控型**<br>（Enterprise / Org） | 组织架构映射、合规审计、分级行政审批（HR、财务、OA、IAM、ERP） | 组织、企业、部门、分支机构、主体 | 员工、部门负责人、审批人、组织管理员、外部联系人 | 录入、入职、调岗、离职交接、授权、审批、归档 | 搞定、小伙伴、玩家、战队等松散或娱乐称谓 |
| **多租户商户型**<br>（Merchant / Tenant） | 经营主体配置业务并服务终端客户（电商后台、CRM、工单客服台） | 店铺、站点、商户、应用、环境（生产 / 测试） | 运营、客服、子账号（内部）；客户、买家、订阅者（外部） | 上架、发布、派单、接待、分群、触达、封禁 | 把内部成员与外部终端客户笼统混称为“用户” |
| **个人专业工具型**<br>（Personal / Solo） | 单人高频创作、分析或效率工具 | 账户、个人空间、作品集、库 | 直接称呼具体业务资产，必要时用“你 / 你的” | 创建、导入、导出、发布、分享链接、备份 | 暴露多余的“工作区管理员 / 席位 / 部门”层级 |

### B. 明确操作者视角与影响圈层
- **操作者身份**：区分当前界面面向普通成员、项目负责人、工作区/组织管理员、账单管理员还是外部访客。
- **影响圈层**：
  1. **个人圈层**：个人资料、通知偏好、个人视图筛选与排序、个人访问令牌（显式或通过上下文表明“仅对你生效”）。
  2. **项目 / 资源圈层**：单个项目成员、单篇文档共享、单条自动化规则（指明当前作用对象）。
  3. **工作区 / 组织全局圈层**：安全策略、SSO、域名验证、套餐变更、全员默认权限（必须显式写明“对工作区所有成员生效”）。

### C. 定位业务场景与信息密度
- **高频作业面（数据表格、看板、画布、编辑器、筛选栏、命令面板）**：只留 2–6 字精准名词或“动词 + 对象”，零解释、零寒暄。
- **协同与权限面（邀请、共享面板、角色权限矩阵、公开链接）**：讲清“谁能访问、具备什么权限、如何收回”。
- **商业与配额面（定价、升级/降级、席位管理、账单、用量预警与超限拦截）**：透明披露计费口径（按席位 / 按用量）、折算与生效时机（立即按比例折算 vs 下周期生效）及超限后果（只读 vs 暂停服务）。
- **集成与开发者面（API 密钥、Webhook、OAuth、导入导出、审计日志）**：交代凭证安全边界（密钥仅显示一次、吊销后调用立即中断）、格式约束与异步处理状态。
- **冷启动与引导面（Onboarding、空状态、配置向导）**：交代“管理什么业务对象 + 产生什么业务价值 + 唯一主操作入口”。
- **阻断、破坏与异常面（危险确认弹窗、表单校验、权限/配额拦截、网络与服务报错）**：交代“客观事实或后果 + 关联资产去向 + 此刻可执行的动作”。

### D. 锁定封闭词表（一物一名，一动一义）
盘点范围内的容器、角色、资源、计费单元与状态枚举，建立唯一名词映射；同时严格按状态机语义选择动词：

| 动作类别 | 标准动词与精确语义边界 | 禁止混用的写法 |
| --- | --- | --- |
| **新建与引入** | `创建`（从零生成新资源） · `添加`（将已有项纳入当前集合） · `导入`（从外部文件或系统批量迁入） · `邀请`（发通知请成员加入） | 把邀请成员写成“添加员工 / 新建用户”；把新建项目写成“添加项目” |
| **解除与销毁** | `移出`（解除成员与工作区/项目的归属，账号本身保留） · `移除 / 取消关联`（从集合拿掉引用，原对象保留） · `归档`（冻结并隐藏，数据保留且可恢复） · `移至回收站`（软删除，限期可恢复） · `永久删除`（物理销毁，不可恢复） | 不分软删、硬删与解除关联，一律笼统写成“删除” |
| **凭证与状态** | `启用 / 停用`（开关功能、集成、规则或账号） · `吊销 / 撤销`（使 API 密钥、令牌、已发出的邀请或授权立即失效） · `重置`（恢复默认值或重新生成凭证） | 把吊销密钥写成“删除密钥”；同一模块内混用“停用 / 禁用 / 关闭” |
| **流转与交付** | `保存`（持久化当前修改） · `发布 / 应用`（使配置或内容正式生效） · `提交审批`（进入审核流） · `导出`（生成文件下载） · `同步`（与外部源拉齐数据） | 用无业务语义的“确定 / 提交 / 完成 / 执行操作”替代具体动词 |

**完成标准**：组织模型、操作者与影响圈层、业务场景，以及核心名词与动词的封闭词表已全部锁定；代码与材料不足以判断组织模型或业务语义时，先列问题向用户确认，确认前不改写文案。

## 2. 推导操作边界与信息增量

对范围内每处文案，先决定**写什么事实、删什么废话**，再决定措辞：

1. **同屏零增量裁减（删净复读与自嗨解释）**
   逐条追问：“删掉这句话，用户仅凭页面标题、上层容器、字段标签、按钮文案与当前状态，会不会做错判断或不敢操作？”
   - 不会影响判断的**同义复述一律删除**（如在 `API 密钥` 标题下写 `管理你的 API 密钥`；在 `修改密码` 弹窗写 `在这里修改你的登录密码`；在已有明确表头的列上加重复解释的 Tooltip）。
   - 不向用户解释界面布局或系统内部动作（删去“点击下方按钮即可…”“系统将自动为您…”）。

2. **四条操作边界补齐（点击前消除不确定性）**
   凡涉及权限变更、席位与计费、资源移除/删除、集成断开或操作受阻，必须核查并补齐缺失的边界事实：
   - **影响半径**：仅当前个人生效、当前项目生效，还是全工作区/全组织生效？
   - **资产归属与连带后果**：移出成员后，其创建的文档、负责的任务、配置的集成归谁（保留在工作区、转为未分配，还是同步销毁）？删除父容器或吊销密钥后，子资源与线上调用是否立即中断？
   - **生效时机与可逆性**：立即生效还是下个计费周期生效？能否撤销或从回收站恢复（保留多少天）？不可逆操作必须显式写明“无法恢复”或“立即失效”。
   - **受阻原因与自救路径**：按钮禁用、权限不足或触发配额上限时，写明具体限制（缺哪个角色权限、达到哪个套餐的哪项上限）及紧邻的解决入口（如“请联系工作区管理员开通”或“清理历史归档 / 升级至专业版”）。

3. **主副文案严格分工**
   - **主文案（标题 / 按钮 / Tab / 表头 / 菜单项）**：2–6 字，只写**业务对象名**或**具体动词 + 业务对象**，承载 1 秒扫视定位。
   - **副文案（辅助说明 / 弹窗正文 / 字段下方说明）**：只写主文案未能表达的**四条边界增量**或**输入格式/计费口径约束**；主文案已自明的，副文案留空。

**完成标准**：范围内每处文案均已明确主文案的对象/动作，以及副文案需承载的边界增量（无增量则标记为删除）；代码逻辑与现有文案冲突或边界后果未定义的，记入待确认。

## 3. 按器物书面语与组件规范落字

### A. 器物书面语准则（去口头语、去机器腔、去官僚腔）

1. **彻底去除口头语（零闲聊感）**
   - **客观主语与平视人称**：以产品、模块或业务对象为主语陈述事实（如“支持导入 CSV 与 XLSX 文件，单文件上限 50 MB”）；指代当前操作者及其私有设置时用平视的 `你 / 你的`（企业级合同要求全站尊称时全局统一用 `您`，绝不混用），严禁使用套近乎的 `咱们 / 小伙伴 / 大家 / 亲`。
   - **书面产品词替代口语动词**：表达能力、范围、配额与规则时，用准确的书面产品词（`支持 / 包含 / 可用 / 适用 / 上限 / 仅限 / 生效`），不用转述用户随口一问的口语词（`能放 / 能用 / 能不能 / 搞定 / 玩转 / 看看 / 瞧瞧 / 别担心 / 空空如也 / 还没…呢`）。
   - **零语气助词与零感叹号**：标题、正文、按钮、空态、Toast 与报错中绝不出现 `吧 / 呢 / 哦 / 啦 / 呀 / 哈`，不使用感叹号（`!`）。
   - **清单式规则标题替代口语是非问句**：帮助说明、引导卡片与常见问题标题直接点明业务对象，并用 `哪些 / 如何 / 何时` 引导出具体规则、清单或步骤（如 `支持导入哪些文件格式`、`如何配置 SAML 单点登录`）；重写所有靠 `都 / 全部 / 现在` 圈范围、答案只有“是 / 否”的口语是非问句（如“现在都支持哪些格式？”“删掉的项目能不能找回？”）。

2. **彻底去除机器腔与官僚客服腔（零阅读阻抗）**
   - **直取及物动词，剥离虚词外壳**：删去 `进行 / 实施 / 对…执行…操作 / 已被成功… / 已成功为您… / 正在为您…`：
     - `已保存`（替代 `已成功为您保存修改`）
     - `导出记录`（替代 `对记录进行导出操作`）
     - `已移至回收站`（替代 `该记录已被成功删除`）
   - **业务结果替代底层实现**：把数据库表名、代码字段、同步机制与内部错误转为用户可感知的业务事实（用 `实时更新筛选结果` 替代 `重建查询索引`；用 `登录状态已过期，请重新登录` 替代 `Token 校验失败 (401)`）。
   - **删净公文套话与暗黑挽留**：删去 `温馨提示 / 敬请知悉 / 尊敬的用户 / 抱歉给您带来不便 / 为了给您提供更优质的服务`；次要与取消按钮保持中立克制（写 `取消`、`暂不升级`、`稍后配置`），严禁使用羞辱或情绪施压文案（不用 `残忍拒绝`、`放弃提升效率`）。

### B. SaaS 全组件落字规范

| 组件类型 | 落字规范 | 反例 → 正例 |
| --- | --- | --- |
| **导航、Tab 与表头** | 2–4 字名词短语，同级词性与颗粒度严格一致，相邻项首字可区分 | `成员列表 / 权限管理 / 去配置账单` → `成员 / 权限 / 账单` |
| **操作按钮（CTA）** | 具体`动词 + 业务对象`（容器上下文已唯一锁定对象时可单用具体动词），不用无语义词 | `确定 / 提交 / 新增 / 操作` → `邀请成员 / 创建密钥 / 导出账单` |
| **危险与变更确认弹窗** | 标题写`具体动词 + 对象`；正文交代`不可逆后果 + 关联资产去向`；主按钮原样复刻标题动词短语 | 标题 `温馨提示` + 正文 `确定要删除该员工吗？` + 按钮 `[确定]` → 标题 `移出工作区？` + 正文 `移出后林夏将立即失去访问权限，其创建的文档保留在工作区。` + 按钮 `[移出工作区]` |
| **空状态与首次引导** | 第一句客观陈述`尚未创建的业务对象`，第二句说明`创建后的业务价值`，下方接唯一主操作按钮 | `这里还空空如也哦，快来创建吧！` → `尚未添加 Webhook。添加后可在工作区事件触发时自动推送通知至外部服务。` + `[添加 Webhook]` |
| **表单标签、提示与占位符** | 标签写简洁业务属性；占位符给`真实格式示例`或`可检索字段`；固定校验规则直接写在输入框旁，不藏进占位符 | 标签 `邮箱` + 占位符 `请输入您的邮箱地址` → 标签 `工作邮箱` + 占位符 `name@company.com`；搜索框 `搜索成员姓名、邮箱` |
| **操作反馈（Toast / Banner）** | Toast 用 3–8 字陈述已完成结果，可逆操作附 `[撤销]`；驻留 Banner 交代全局状态原因与处理入口 | `系统已成功为您将文档移入回收站！` → `已移至回收站` `[撤销]` |
| **校验、报错与权限/配额拦截** | 陈述`客观受阻原因 + 此刻可执行的恢复路径`；字段错误就近内联指明具体达标条件 | `操作失败 (Error 403)` → `当前角色无权修改安全设置，请联系工作区管理员开通。`；`超出人数限制` → `免费版最多包含 5 名成员，升级至专业版可无限邀请成员。` |
| **状态枚举与计费口径** | 状态标签用 2–4 字对称短语（`运行中 / 已停用 / 待审批 / 已逾期`）；计费与配额写清单位、周期与折算规则 | `正常 / 关了 / 审核 / 超期了` → `运行中 / 已停用 / 待审批 / 已逾期`；`¥99/人` → `¥99 / 成员 / 月，按年付折算` |

### C. 原样保留边界
品牌名、产品与套餐专有名词、行业通用协议与标准技术缩写（`SSO`、`SAML`、`OAuth`、`SCIM`、`Webhook`、`API`、`SDK`、`CSV`、`JSON`、`Cron`）、法律合规条款原文，以及用户输入内容，保持原样，不强行汉化或改写。

## 4. 待确认、交付与验收门

存在以下情况时，在输出改写结果前编号列出，附代码线索与默认建议，一次性向用户确认：
- 代码与现有材料无法判定产品属于团队协作、企业管控还是多租户商户模型。
- 现有文案与代码实际逻辑、权限边界或计费规则冲突。
- 关键操作的影响半径、关联资产去向或恢复机制在代码中未定义。

按以下两部分交付：

1. **语境与封闭词表**：
   - 产品组织模型、当前业务场景、操作者角色与影响圈层。
   - 核心名词与动词的 `旧称/混用词 → 统一标准词` 对照表。
2. **文案改写对照表**：

```markdown
| 位置 / 组件 | 原文案 | 新文案（主文案 / 副文案） | 改写依据（校准的词表、补齐的操作边界或剔除的口语/机器腔） |
| --- | --- | --- | --- |
```

- 删掉冗余副文案或提示的条目，副文案标明“删除”，依据写明同屏已由哪处承载。
- 无需改动的条目，新文案写“保留”。

**验收门（交付前逐项核对）**：
- **语境同构**：人员、容器与流转称谓是否严格契合组织模型（如团队协作产品零“员工 / 下属 / 部门 / 工号”）？
- **词表闭合**：同一业务对象与状态是否全局唯一命名？`创建 / 添加 / 邀请`、`移出 / 归档 / 移至回收站 / 永久删除 / 吊销` 等动词是否严格按数据后果区分？
- **边界与增量**：权限变更、成员移出、资源删除与计费配额操作是否交代了影响半径、资产去向、生效时机与可逆性？无信息增量的同义复述副文案是否已全部删除？
- **器物书面语**：是否彻底清除了口头语、助词（吧/呢/哦/啦）、感叹号、是非问句，以及“对…进行操作 / 成功为您 / 温馨提示”等机器腔与官僚套话？
- **组件同构**：按钮是否全为具体“动词 + 对象”？确认弹窗主按钮是否与标题动词一致？同级导航、Tab 与状态标签句式是否对称？
- 默认只交付词表与对照表；经用户明确授权后，再替换代码中的文案字符串（保留 key、路由、字段名与枚举值等代码标识符不变）。
