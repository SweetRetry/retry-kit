# 信息架构

让界面按照用户理解信息的方式组织，而不是按照代码和数据的结构组织。最终产出是展示模型：它定义用户看到哪些信息单元、它们如何关联、先看到什么，以及深入后新增什么。

默认只分析和设计。用户明确要求修改时，先确定展示模型和验收标准，再改实现。

## 1. 建立展示模型

先明确目标用户、使用情境和任务，再按优先级列出用户进入界面后需要回答的问题。每个问题都要对应一次判断或下一步行动。

从这些问题中识别：

- 用户认为持续存在的对象；
- 用户已经作出或需要作出的决策；
- 任务产生的结果及影响范围；
- 会改变判断或可用操作的状态；
- 用于解释、核验或建立信任的依据；
- 用户认为属于同一段工作的连续事件。

确定它们的名称、身份、关系、生命周期和信息归属。接口响应、数据库记录、消息片段、工具调用和组件实例只是信息来源；只有与用户认识的信息单元一一对应时，才能直接成为界面结构。

**完成标准：**每个可见信息单元都能回答一个用户问题；展示模型与源数据结构的边界明确，没有用技术记录边界代替用户任务边界。

## 2. 组织信息

依次确定分组、顺序、命名、导航和层级：

- 优先按对象、任务或因果关系分组，再考虑时间、类型和数据来源；
- 顺序服从用户问题的重要性、任务阶段或决策价值；
- 同一对象的身份、状态、结果和操作保持邻近；
- 名称表达用户认识的对象或结果，不用内部术语和实现动作代替；
- 同一事实只有一个权威位置，其他位置只承担明确不同的问题；
- 导航名称应让用户预测目的地、范围和返回关系。

层级遵守以下分工：

- 默认层负责识别对象并支持相关性判断；
- 详情层补充原因、关系、依据、历史和次要操作；
- 原始记录只在确有诊断价值时出现。

摘要应做语义压缩：减少篇幅，同时保留核心含义。状态、类型、时间和数量只有在对象及其含义已经明确，并且这些信息会改变用户判断时，才是有效摘要。

渐进披露延后细节，不延后含义。对每个折叠区、列表摘要、通知、预览和详情入口检查：

1. 默认状态能否说明这是什么、发生了什么、是否与用户有关？
2. 用户能否在操作前判断继续深入是否值得？
3. 深入后是否只增加解释、依据或操作？
4. 收纳是否真正降低理解成本，而不只是减少占用空间？

如果用户必须展开、悬停、跳转或试操作后，才知道信息是什么或为何重要，这就是无效收纳。

**完成标准：**用户不经过额外交互也能识别信息并判断相关性；每次深入只增加信息深度，不承担首次解释。

## 3. 定位根因

逐项检查：

- 信息单元是否错误地沿用了记录、调用或组件边界；
- 同一任务是否被技术边界切碎，不同对象是否因来源相同而混在一起；
- 元数据、状态或数量是否占据上层，核心含义却被放进详情；
- 名称是否只说明系统做了什么，没有说明用户得到什么；
- 同一事实是否在多处竞争权威，或判断所需的信息是否没有明确归属。

判断根因属于产品约束、信息架构、交互模型、组件行为还是视觉表达。上层根因造成的标题、图标、间距和折叠方式问题应合并处理。用户仍然看不懂内容、必须操作后才知道含义，或觉得局部都对但整体奇怪时，回到信息单元和层级，不继续修补文案与样式。

**完成标准：**每个问题只有一个最高且有证据支持的根因，并说明它如何增加理解成本、误导判断或破坏任务连续性。

## 4. 明确要求实现时

1. 固定用户问题、信息单元、关系、层级和各层职责；
2. 用明确的展示类型或纯映射函数，把源数据转换成用户语义；
3. 再选择列表、表格、树、标签页、折叠区或详情页；
4. 用真实长度、真实数量、重复名称、空态、失败态和权限差异验证结构；
5. 同时验证应该出现和不该出现的内容：核心含义默认可见，内部字段和次要细节没有越级出现。

组件库只提供交互能力，不决定产品的信息模型。不能为了迁就组件默认结构而改变已经确认的信息单元和层级。

**完成标准：**实现中明确区分展示模型和源数据结构；真实内容下，默认状态仍能回答用户的首要问题；原问题有可观察的回归验证。

## 输出

先说明目标用户、界面和首要问题，并给出“信息架构成立”“存在信息架构问题”或“证据不足”。

审查时按影响排序说明问题、用户需要回答的问题、当前结构、实际后果、根因和证据。相同根因合并，不按组件或文案数量拆分。

设计或重构时交付：

1. 用户问题和内容清单；
2. 展示模型及其与源数据的映射；
3. 分组、顺序、命名和导航；
4. 默认层与详情层的职责；
5. 会改变架构的未知项和可验证的验收标准。

用户只要求审查时不修改；明确要求实现时按第 4 节执行并回归。
