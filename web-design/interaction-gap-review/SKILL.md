# Interaction Gap Review

发现用户在既有网页或 App 中无法开始、理解、继续、确认结果或恢复任务的交互缺口。以用户目标和实际可见行为为准：先检查主链路是否闭合，再用入口、状态和中断变化验证缺口，不把罕见条件本身当作 finding。

默认只读。用户同时要求修改时，先交付缺口分析，再将实现作为后续任务。

## 1. 锁定任务与证据

从用户指定的页面、flow、代码、diff 或运行中的产品开始，检查 route、组件、client state、API 响应处理、测试、文案和实际行为。明确：

- 谁在什么入口和对象状态下，要完成什么目标；
- 用户完成后应看到什么，哪些状态属于明确阻塞或安全退出；
- 开始、继续和提交任务所需的资源、权限、历史状态与输入；
- route、server response、cache、local state、form draft 中各状态的 authority；
- 哪些 product 或 service contract 缺失会实质改变结论。

用户只说 `changes` 时，从当前交互变更出发，沿 route、state、API 消费者和用户动作追到稳定 contract 或无因果关系的边界。

**完成标准：**用户、目标、起点、成功状态、前置条件、状态 authority 和可用证据均已明确；未知事实具体记录为信息缺口。

## 2. 还原交互链路

以用户可识别的状态为节点，以可发现的 action、自动变化或 handoff 为边，画出从进入到结束的主链路：

- **发现与开始：**用户如何知道任务存在、理解其目的并进入正确对象；
- **执行与推进：**每一步需要的输入、validation、默认值、next action 与前置依赖；
- **反馈与确认：**loading、saving、pending、success、failed、partial、blocked 等状态如何可见、可理解、可行动；
- **转场与连续性：**列表到详情、modal 到页面、创建到使用、外部授权返回、展开／收起／切换 view 是否保留仍有效的上下文、输入、focus、scroll 和进度；
- **退出与恢复：**cancel、back、refresh、retry、重新登录、重新进入、undo 和安全放弃后如何继续或结束。

每个 action 标出它服务的任务、semantic owner、出现条件、提交条件与结果落点。每条前置依赖 `A 依赖 B` 必须形成“理解 B → 到达／完成 B → 带着原意图回到 A”的回路。

**完成标准：**主链路上的每一步都有下一步或明确终点；每个关键 action 都有可见的进入条件、进行中反馈和可理解的结果。

## 3. 用闭环覆盖常见断裂

对每个关键任务逐项检查以下闭环。它们是用户面常见断裂的最小覆盖面；不适用时说明原因，不因页面能完成 happy path 而跳过。

| 闭环 | 必须确认 | 常见断裂信号 |
| --- | --- | --- |
| **发现** | 用户能找到 action、理解目标、前置条件和不可用原因 | action 隐藏／错放；disabled 无原因；空状态、首次使用或权限不足没有下一步 |
| **执行** | 输入规则、validation、提交时机和对象范围可理解，用户能避免误操作与重复提交 | 错误未定位到可修正处；提交条件突变；重复点击、切换对象或 mode 造成错误提交 |
| **反馈** | 处理中、排队、离线、后台继续、失败和部分完成均有及时且可行动的状态 | 点击后无响应；loading 遮蔽上下文；成功／失败 toast 不说明对象、结果或下一步 |
| **确认** | 用户能确认最终状态、实际影响与结果所在位置 | optimistic state 与服务端结果冲突；完成后仍停在旧状态；跳转后丢失结果或操作对象 |
| **连续** | navigation、handoff、刷新、返回、登录、tab／view 切换后仍保留有效意图与输入 | 丢失 draft、focus、scroll、筛选、进度或错误；依赖任务完成后不能带着原意图返回 |
| **恢复** | empty、error、permission、session 过期、冲突、对象删除与网络变化后有修正、retry、重入或安全退出 | 只显示技术错误；retry 无效或造成重复；用户被困在不可行动状态 |
| **控制** | cancel、undo、确认和 final feedback 与 action 后果相称 | 发布、删除、付款、共享或授权的范围／可逆性不清；无法中断或确认是否生效 |
| **可用** | keyboard、screen reader、touch、窄屏、长内容、本地化与时区不改变完成任务所需的顺序、反馈或 action | focus 无处落点；视觉反馈未被辅助技术感知；移动端或翻译后关键 action 消失 |

沿主链路优先检查 `发现 → 执行 → 反馈 → 确认`，再检查 `连续 → 恢复 → 控制 → 可用`。每个闭环都从用户可见的状态出发，而非只检查 API 是否返回、组件是否存在或测试是否覆盖。

对每个候选缺口问四个问题：用户原本要完成什么、在哪个可达状态缺少什么交互、缺失后看见什么／还能做什么、是否存在其他可见路径已经闭合这条链路。只保留改变用户任务结果的项。

**完成标准：**每个闭环都有“成立／不成立／不适用”的结论；每个保留项指向任务图中的具体断边，而非抽象的“体验不好”或单个 UI 元素缺失。

## 4. 验证缺口与恢复能力

从候选断点继续追踪用户实际看到什么、最可能如何重入，以及重入后的结果。只施加能验证该断点的最小变化：

- 用主导航、direct URL、deep link、通知、浏览器返回与登录后 redirect 重新进入；
- 在提交前、请求中、响应后但渲染前刷新、返回、重复 action 或切换 tab；
- 让输入、当前对象、前置资源、权限或 session 在任务中途变化；
- 让 API 返回慢、empty、partial、stale、冲突、认证失效或客户端未知状态；
- 只改变 presentation state，检查仍有效的输入、focus、scroll、上传进度和错误是否被保留；
- 组合与该任务相关的两个条件，例如未保存输入与 session 过期、optimistic success 与服务端拒绝。

API 返回错误不等于链路已闭合；只有错误被映射为用户能理解且能行动的状态，才算提供反馈。单张截图或单个组件未显示 action，也不足以证明整条链路缺失：检查其他入口、route guard、状态恢复和 error mapping 后再下结论。

**完成标准：**每个保留 finding 都已追到可观察的稳定后果，或精确说明缺失哪项证据会改变判断。

## 5. 收敛 findings

每个 interaction gap 形成一条链：

**用户与上下文 → 目标与入口 → 缺失前的可见状态和 authority → 缺少的交互／反馈／转场 → 用户最终状态与可执行 action → 影响 → 证据**。

按证据定级：

- **已确认：**运行行为、代码、测试、route 或明确 contract 直接证明；
- **高可信推断：**交互实现和状态转换足以推出后果，但未运行完整链路；
- **待确认：**缺少的入口、角色、feature flag 或 service contract 可能改变结论。

按根因与用户后果合并，避免把同一个“无反馈”拆成 loading、success、failure 的重复 finding；分别保留造成不同任务断裂的缺口。

**完成标准：**每个 finding 均有完整链路、证据等级和单一主要根因，且已检查可见的替代路径。

## 输出

从最阻断核心任务的 finding 开始。每项用一小段说明用户是谁、从哪里进入、缺少哪项交互、最终看到什么、还能做什么、影响、证据与可信度。

用户只要求分析时，以现状、影响、证据和待确认 contract 收口；只有用户明确要求建议时，才在所有 findings 后提出恢复方向。范围内没有成立的缺口时，说明“未发现有证据支持的用户交互缺口”，并说明已复核的主链路与状态。
