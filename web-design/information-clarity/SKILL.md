# Information Clarity

信息清晰度成立时，对指定用户、情境和目标，当前呈现能以合适的信噪比支持用户回答问题。问题包含两个方向：必要信息缺失、不可发现、不可区分、含义模糊、关系错误或取得过晚；无关、重复、过早、过细的信息竞争注意力，使必要信号难以识别或被赋予错误优先级。信息清晰度不等同于字段少或内容短，补充与剪枝都可能使其成立。

用静态成立性划定边界：保持所审查状态，不执行下一次 action、navigation 或 system update 时，用户已经无法识别对象、理解必要关系、判断相关性或预测深入价值，就属于信息清晰度问题。当前信息足以判断、问题只在后续反馈、时序、状态转换或恢复中出现时，不属于本 skill。信息结构使用户错误预测或选择 action 时，信息结构仍是根因，任务后果是影响证据。

默认只读。用户要求建议、设计或重构时，先固定 findings、展示模型和验收标准；只有明确要求修改实现时才改代码并回归。

## 1. 固定信息需求 contract

先明确 actor、情境、目标、信息载体和当前状态，再列出用户此刻必须回答的问题：

1. 这是什么对象、结果或范围，现在处于什么状态？
2. 它与哪些对象相关，关系是归属、并列、条件、因果、先后还是引用？
3. 哪些状态、时间、权限、来源或影响范围会改变我的判断？
4. 哪个入口、分组或详情可能满足当前目的，是否值得深入？
5. 作出判断需要哪些依据，依据的时效和 authority 是什么？

每个问题必须对应一次识别、比较、选择、核验或下一步决策，并写明答错、漏答或回答过晚的用户后果。记录当前可见内容、可访问语义、目标用户已有知识、真实数据来源和仍未知的产品约束；不把设计者熟悉系统当作用户已经理解。

再反向检查每个现有信息单元：它回答哪个当前用户问题，是否改变判断、解释异常、建立必要信任或提供下一步所需条件？不能说明独立责任，或只重复其他位置已经表达的含义时，标为 noise candidate；不要因内容已经存在就推定它应该保留。

**完成标准：**每个候选问题都绑定一个具体用户问题、所需信息、判断时点和可观察后果；每个现有信息单元都有独立责任或被列为 noise candidate。没有问题或后果的内容差异不进入 finding。

## 2. 重建展示模型

从用户问题识别：

- 用户认为持续存在的对象及其身份；
- 对象之间的归属、并列、条件、因果、时间和引用关系；
- 会改变判断的状态、范围、权限、时效和来源；
- 任务产生的结果、影响对象与核验依据；
- 用户认为属于同一段工作的连续事件。

确定每个信息单元的名称、身份、关系、生命周期、authority 和归属，再映射到接口响应、数据库记录、事件、消息、工具调用和组件。技术记录只是信息来源；只有与用户认识的信息单元一一对应时，才能直接成为展示边界。

同一事实只设一个权威位置。其他位置只有在回答不同用户问题时才保留，并明确它是摘要、引用还是历史快照。

**完成标准：**每个所需信息都有明确的用户语义、关系、authority 和呈现责任；展示模型与源数据结构的边界清楚，没有用技术记录或组件边界代替用户理解边界。

## 3. 追踪信息获取路径

对每个用户问题追踪：

**当前线索与上下文 → 用户对价值和成本的预期 → 选择的入口或分组 → 到达后的信息 → 是否能回答问题或判断下一层是否值得深入**。

检查：

- 名称、摘要、图像和邻近上下文是否准确预告内容，而不是只诱导点击；
- 用户能否看出当前位置、当前范围、上级关系、并列选项和目的地；
- 已知目标能否找到，尚未明确目标的用户能否看出有哪些内容和选择；
- 入口承诺与到达内容是否一致，用户是否被迫反复进入、返回或记忆多个详情才能比较；
- 关系类型是否先于组件选择：并列、层级、线性顺序和细节收纳不能因使用同一组件而混为一谈。

渐进披露延后细节，不延后首次解释。默认层负责对象身份、核心含义、相关性和深入价值；详情层增加依据、条件、历史、例外和次要操作。点击次数或层级数量本身不是质量指标，判断标准是每一步是否提供足够且真实的信息线索。

**完成标准：**每个入口都能让目标用户预测会获得什么以及是否值得深入；到达后兑现该预期，并只增加信息深度，不承担首次解释。

## 4. 检查信息呈现 invariant

对每个必需信息逐项判断“成立／不成立／不适用”：

| invariant | 必须确认 | 常见问题信号 |
| --- | --- | --- |
| **完备** | 当前判断所需的对象、关系、条件和依据都存在 | 只有状态或数量，没有对象与含义；关键范围或条件缺失 |
| **可发现** | 信息在需要的时点能被察觉，不依赖偶然探索 | 核心含义藏在 hover、折叠、tab 或详情；重要信息被噪声压过 |
| **可区分** | 不同对象、状态、来源和范围不会被误认成相同 | 重复名称；只靠颜色、位置或轻微样式区分；摘要同质化 |
| **可解释** | 名称、单位、术语、状态和摘要对目标用户含义明确 | 内部术语；模糊标签；状态有值但不知道意味着什么 |
| **关系与顺序** | 分组、邻近、层级和阅读顺序准确表达真实关系 | 技术边界切碎同一对象；无关内容并列；顺序改变后含义丢失 |
| **信噪与优先** | 首要问题先得到回答，每个次要信息都承担独立责任且不竞争注意力 | 铺垫先于结论；重复解释；内部过程、低价值元数据或过早例外淹没当前判断 |
| **定向与信息气味** | 入口、范围、当前位置和深入价值可以预测 | 标签不能预告目的地；入口很多但无法判断差异；到达内容不兑现承诺 |
| **一致与权威** | 同一概念稳定命名，同一事实有明确 authority 和时效 | 同物异名、异物同名；列表与详情竞争真相；过期摘要没有标识 |
| **模态等价** | 去掉颜色、位置、卡片外观或切换为线性／辅助技术呈现后，身份、关系和顺序仍成立 | 关系只靠视觉暗示；朗读或窄屏重排后对象归属与阅读顺序丢失 |

信息噪声只相对 actor、情境、当前任务和判断时点成立：信息、选择、关系或呈现方式没有帮助用户识别对象、理解关系、作出正确决定、准备下一步或履行安全／法规义务，却竞争注意力、工作记忆或信息权威。典型候选包括：

| 类型 | 可观察信号 | 不能据此删除的边界 |
| --- | --- | --- |
| **无关或抢占注意力** | 辅助内容、装饰、动效或打断与当前对象和决定无关，却比首要信息更显著 | 风险、资格、成本、任务条件或下一步资源即使增加长度也可能必要 |
| **重复或冲突** | 同一事实多处出现而没有权威位置，或不同版本导出不同判断 | 为回答不同即时问题而重复对象身份、当前状态或关键风险可以成立 |
| **过早的深层细节** | 内部字段、过程、罕见例外或高级选项先于对象、目的、结果和相关性 | 会立即改变资格、费用、风险或是否继续的细节应提前呈现 |
| **分裂的必要关系** | 用户必须跨卡片、tab、页面或不同名称拼合对象、条件、含义和结果 | 并列比较、审计或历史资料可以分区，但关系、摘要和回溯入口必须明确 |
| **空泛或不可解释** | 标签、标题、图标、状态或术语不提供信息增量，只要求猜测目的或记忆内部模型 | 用户熟悉、法规定义或精确区分所需的领域术语应保留并提供必要解释 |
| **陈旧或失去归属** | 内容不再满足当前需要、只反映内部组织，或旧信息未标明时效却与当前事实竞争 | 审计、法律或历史资料应作为有明确状态和归属的记录保留 |

组件存在不证明 invariant 成立，缺少惯用组件也不证明信息清晰度存在问题。字数、元素数量、密度和视觉风格只是风险线索；只有内容不承担独立责任，或呈现关系实际遮蔽、打断、分裂或误导判断时，才构成噪声。相互依赖的条件、例外、证据、风险和合规事实属于必要复杂度时，应通过就近整合、分组、排序、摘要和分层降低负担，不能通过删除含义伪造简单。

对每个 noise candidate 按以下顺序决定处置：

1. **删除**：不回答当前或后续必要问题，不提供独有依据、约束或风险；
2. **合并**：与其他信息表达同一事实、结论或解释，保留一个权威版本；
3. **压缩**：责任成立，但铺垫、过程或例子超过当前判断所需；
4. **延后**：只对部分用户、例外情境或核验阶段有用，移到与其问题相邻的详情层；
5. **保留**：它独立改变判断、避免误解、建立必要信任或支持下一步。

处置对象必须具体到信息单元及其责任，不能用“精简文案”“减少信息”代替判断。

**完成标准：**每项不成立都映射到一个用户问题、当前呈现和可观察后果；不能只写“层级不清”“信息太多”或“组件不合适”。

## 5. 验证、反证与定位根因

优先观察真实内容和真实任务；根据候选根因选择最小验证方法：

- 用 content inventory / audit 核实信息是否存在、准确、重复和由谁负责；
- 用 card sorting 或 question sorting 探索目标用户如何分组、命名和排序；
- 用 tree testing 验证既定分类与标签能否支持查找；
- 用任务观察、think-aloud、搜索／导航日志或客服问题验证用户如何解释线索并选择路径；
- 用线性化、keyboard、screen reader、zoom、窄屏和长文案检查结构与关系是否跨模态保留。

同时检查真实长度、零／一／多条、重复名称、相似对象、空值、失败态、权限差异、状态变化和过期信息。主动寻找替代入口、搜索、上下文说明、用户已有知识和合法产品约束等反证，不从单张截图、一个组件或缺少一段代码推断完整体验。

按证据定级：

- **已确认：**真实任务观察、可复现行为、日志或用户反馈直接证明错误理解或路径后果，并已核实对应结构；
- **高可信推断：**必要线索确实缺失、关系只靠不可用的呈现表达，或完整内容与语义足以推出后果，但尚未观察目标用户；
- **待确认：**已有具体风险线索，但 actor、目标、内容、模态或产品 contract 仍可能改变结论。

根因按展示模型归并为：内容／对象缺失、关系缺失或错置、分类或命名不符合用户模型、顺序或层级错配、导航定向不足、无效收纳、冗余或低价值信息竞争、authority 或时效冲突。视觉、文案和组件问题只有在它们是最高根因时才单独保留。

**完成标准：**每个候选问题都已获得与措辞相称的证据或精确的待确认条件，并经反证后只保留一个最高根因。

## 6. 合并与定级

每个 finding 形成一条 finding chain：

**actor、情境与用户问题 → 判断所需信息 → 当前呈现 → 用户可得到的解释 → 已观察后果或证据支持的预期后果 → 根因 → 证据**。

按问题核心程度、错误判断的后果、影响范围和重新定位成本定级：

- **P0：**核心用户普遍无法作出必要判断，或信息会系统性诱导高后果、不可逆的错误判断，且没有可靠替代依据；
- **P1：**核心问题在可达状态下无法回答、被误导或只能通过高成本试探回答，明显阻断或扭曲主要任务；
- **P2：**次要或条件性问题增加查找、比较、记忆或核验成本，但有可发现且可靠的恢复路径。

相同根因和最终后果合并；同一展示模型在浏览、搜索、通知或详情等多个入口造成同一个未解问题时，只保留一条 finding，并把不同入口作为证据。只有根因或最终判断后果不同才拆分。不要按字段、组件或页面数量拆分。严重度不由点击次数、层级深度、隐藏内容数量、字数或信息单元数量机械决定，而由必要信号被遮蔽或误读后的后果决定。

**完成标准：**每个 finding 只有一个主要根因、一个严重度、一个证据等级，并能说明用户无法回答什么以及最终影响。

## 7. 明确要求设计、重构或实现时

1. 固定用户问题、所需信息、展示模型、findings 和验收标准；
2. 为现有信息单元确定保留、合并、压缩、延后或删除，再纠正关系、authority、分组、命名、顺序和各层职责；
3. 用展示类型或纯映射函数把源数据转换成用户语义，再选择列表、表格、树、tabs、折叠区或详情；
4. 用第 4、5 节的 invariant、真实内容和模态条件验证新结构；
5. 同时验证应该出现和不该出现的信息：核心含义在需要时可得，删除项不再占据注意力，合并项只有一个 authority，次要细节没有越级竞争；
6. 实现后用原用户问题回归，证明用户不靠额外记忆或试探即可得到正确判断。

组件库只提供呈现与交互能力，不决定产品的信息模型。不能为了迁就组件默认结构而改变已确认的信息单元和关系。

## 输出 contract

先给出 `信息清晰度存在问题 / 信息清晰度成立 / 证据不足`，并用一句话说明 actor、信息载体、当前状态和首要用户问题。

审查时按 P0 → P2 输出 findings。每项用一小段说明用户问题、判断所需信息、当前呈现、已观察后果或证据支持的预期后果、最高根因、严重度、证据与可信度；涉及噪声时，列出具体信息单元及其“删除／合并／压缩／延后／保留”处置和判断依据。默认保留最影响判断的 3–5 项，所有额外 P0／P1 仍需输出。

最后列出已复核的信息获取路径、替代入口、呈现模态和会改变结论的未知项。内容处置属于审查结论，不展开页面重设计；明确要求建议时，在全部 findings 后给出对应的展示模型调整和可验证 acceptance criteria。

设计或重构时交付：用户问题与内容清单、现有信息的保留／合并／压缩／延后／删除清单、展示模型及源数据映射、分组／命名／顺序／导航、默认层与详情层职责、证据缺口和验收标准。明确要求实现时再按第 7 节修改并回归。
