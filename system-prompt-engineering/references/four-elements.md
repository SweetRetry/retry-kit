## P — Persona 角色设定

为模型赋予明确身份，决定回复的口吻、深度和专业程度。

### 写作要点

- 用一句话定义角色的**专业领域 + 资历级别 + 行为风格**
- 角色越具体，输出越稳定："资深 Java 架构师，擅长高并发系统设计" 优于 "程序员"
- 可叠加行为约束："语气专业但不居高临下，善于用类比解释复杂概念"

### 好的 Persona vs 差的 Persona

| 质量 | 示例 |
|------|------|
| 差 | "你是一个助手" |
| 中 | "你是一位 Python 开发者" |
| 好 | "你是一位有 10 年经验的 Python 后端架构师，专注于高并发微服务设计，擅长用简洁的语言向初级开发者解释复杂的系统设计决策" |

### 反模式

- **角色过载**：一个 Persona 塞入太多不相关的能力（"你既是律师又是医生又是厨师"）
- **角色空泛**：没有具体领域锚定（"你是一个聪明的 AI"）
- **角色矛盾**：行为约束与角色身份冲突（"你是严谨的学术研究员，请用网络流行语回答"）

## T — Task 任务描述

明确模型要执行的具体动作，是 prompt 的核心驱动力。

### 写作要点

- 用**祈使句**开头，一句话说清核心动作："审核以下代码段并找出潜在的内存泄漏"
- 复杂任务拆解为**有序步骤**，每步一个明确动作
- 区分"分析"、"生成"、"转换"、"评估"等动作类型 — 动词选择决定输出方向
- 指定完成标准：模型怎么知道任务"做完了"？

### 反模式

- **任务模糊**："帮我看看这段代码" → 看什么？找 bug？优化性能？改风格？
- **步骤缺失**：复杂任务只给终点不给路径，模型容易跳步或遗漏
- **多任务混杂**：一个 prompt 塞入多个不相关任务，导致注意力分散

## C — Context 上下文背景

提供必要的约束条件、领域知识或背景数据，帮助模型理解"边界"在哪里。

### 写作要点

- 回答三个问题：**为什么做**（任务背景）、**给谁看**（目标受众）、**边界在哪**（领域约束）
- 用 `<context>` 标签包裹，与其他部分视觉分离
- 只提供模型无法自行推断的信息，避免重复常识
- 关键术语给出明确定义，消除歧义

### 反模式

- **上下文过载**：把整本文档塞进去，淹没核心信息
- **上下文缺失**：不提供领域背景，模型只能猜测
- **隐含假设**：默认模型知道你的业务术语（"按 Q3 标准处理" — 什么标准？）

## F — Format 输出格式

规定输出必须符合的结构，消除格式歧义。

### 写作要点

- 明确指定结构类型：JSON、Markdown 表格、带标题的列表、代码块等
- 提供一个**输出骨架**（skeleton），模型填充内容即可
- 对关键字段说明数据类型和约束（如 "score: 1-10 整数"）
- 格式要求放在 `<format>` 标签内，与内容指令分离

### 反模式

- **格式模糊**："输出要整齐一点" — 什么叫整齐？
- **格式过度**：简单问答也要求复杂 JSON，增加不必要的认知负担
- **格式与任务脱节**：要求表格输出但任务是写叙事文本

## 组装顺序与优先级

四个模块的推荐组装顺序：

```
Persona → Context → Task → Format
```

**原因**：模型先理解"我是谁"（Persona），再理解"背景是什么"（Context），然后执行"做什么"（Task），最后按"什么格式"（Format）输出。这个顺序符合人类认知的自然流程。

### 优先级权重

| 优先级 | 模块 | 说明 |
|--------|------|------|
| 最高 | Task | 任务不清晰，其他模块再好也白搭 |
| 高 | Context | 缺少上下文，模型只能猜测边界 |
| 中 | Format | 格式不对可以重新生成，但浪费 token |
| 基础 | Persona | 影响风格和深度，但不影响正确性 |

### 模块间协同

- Persona 决定 Task 的执行深度（初级 vs 资深视角）
- Context 约束 Task 的执行范围（不要越界）
- Format 服务于 Task 的输出需求（匹配消费场景）
- 四个模块互相印证，不应出现矛盾
