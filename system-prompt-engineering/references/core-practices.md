## 实践一：XML 标签结构化

结构化标记通常能减少模型在长对话中的"指令偏移（Instruction Drift）"。

### 核心标签集

| 标签 | 用途 | 使用场景 |
|------|------|----------|
| `<persona>` | 角色设定 | 定义模型身份 |
| `<context>` | 背景信息 | 领域知识、约束条件 |
| `<task>` | 任务描述 | 核心动作和步骤 |
| `<constraints>` | 硬性约束 | 必须/禁止的行为 |
| `<format>` | 输出格式 | 结构要求 |
| `<examples>` | 示例对 | Few-shot 样本 |
| `<rules>` | 规则集 | 业务逻辑规则 |

### 为什么有效

- 模型将标签视为**语义边界**，不同标签内的指令互不干扰
- 长对话中模型容易"忘记"纯文本指令，但标签结构提供持久的锚点
- 便于人类阅读和维护，修改某个模块不影响其他部分

### 嵌套规则

- 保持**一层嵌套**为主，避免超过两层
- 同级标签之间用空行分隔
- 标签名使用小写英文，语义清晰

## 实践二：正面指令优先

告诉模型"要做什么"，而不是"不要做什么"。在多数场景下，正面指令更稳定、更易执行。

### 转换对照表

| 负面指令（避免） | 正面指令（推荐） |
|------------------|------------------|
| "不要写太长的废话" | "回答保持简洁，每段不超过 3 句" |
| "不要使用技术术语" | "用日常语言解释，确保非技术人员能理解" |
| "不要编造数据" | "仅引用提供的数据源，无数据时明确说明" |
| "不要跑题" | "始终围绕用户提出的具体问题回答" |
| "不要输出代码" | "用自然语言描述解决方案的逻辑步骤" |

### 为什么有效

- 负面指令需要模型先理解"什么是不该做的"，再推断"该做什么" — 多了一步推理
- 正面指令直接给出行为目标，减少歧义空间
- 负面指令在长对话中更容易被遗忘（"不要"的记忆衰减快于"要"）

### 例外情况

安全相关的硬性禁止仍然使用负面指令，放在 `<constraints>` 标签内：
```xml
<constraints>
- 严禁：输出任何用户的个人身份信息（PII）
- 严禁：生成可执行的恶意代码
</constraints>
```

## 实践三：示例注入 Few-Shot

将 3-5 个理想的问答对直接放入 System Prompt，确保模型在整个会话中保持稳定的输出风格。

### 放置位置

示例放在 **System Prompt** 而非 User Prompt 中。原因：
- System 级示例在整个会话中持续生效，不会被后续对话冲淡
- User 级示例只影响当轮回复，下一轮可能风格漂移

### 示例结构

```xml
<examples>

<example>
<input>如何优化 React 组件的渲染性能？</input>
<output>
**问题诊断**：React 组件不必要的重渲染通常由三个原因导致...

**解决方案**：
1. 使用 `React.memo` 包裹纯展示组件...
2. 将状态下沉到最近的消费者...

**验证方法**：使用 React DevTools Profiler 对比优化前后的渲染次数。
</output>
</example>

<example>
<input>解释什么是数据库索引</input>
<output>
**一句话理解**：索引就像书的目录页...

**工作原理**：...

**何时使用**：...
</output>
</example>

</examples>
```

### 设计要点

- 示例数量：3-5 个覆盖典型场景，过多浪费 token
- 示例多样性：覆盖简单/复杂、不同类型的输入
- 示例一致性：所有示例的输出格式必须统一，这就是模型要学的"模板"
- 边界示例：至少包含一个"拒绝回答"的示例，教模型如何优雅地说不

## 实践四：链式思考引导 CoT

在系统层级植入推理指令，比单次对话中要求"Think step by step"更具强制性。

### System 级 vs User 级 CoT

| 维度 | System 级 CoT | User 级 CoT |
|------|---------------|-------------|
| 持久性 | 整个会话生效 | 仅当轮生效 |
| 强制性 | 高 — 模型视为"身份的一部分" | 低 — 可能被后续指令覆盖 |
| 适用场景 | 需要始终保持推理链的任务 | 偶尔需要深度推理的单次提问 |

### 植入模板

```xml
<task>
在回答任何问题前，先在内部完成以下推理步骤（推理过程不输出给用户）：
1. 识别问题的核心诉求
2. 列出 2-3 个可能的解决方向
3. 评估每个方向的优劣
4. 选择最优方案后再组织输出
</task>
```

### 变体

- **显式推理**：要求模型输出推理过程（适合教学场景）
- **隐式推理**：要求模型内部推理但只输出结论（适合生产场景）
- **分步验证**：每步推理后自我检查，发现矛盾则回溯修正

## 实践五：默认兜底策略

在 System Prompt 中规定模型遇到无法处理的问题时如何优雅地拒绝，防止幻觉。

### 兜底策略模板

```xml
<constraints>
当遇到以下情况时，按对应策略处理：

- 知识边界：如果问题超出你的知识范围，回答"该问题超出当前知识范围，建议咨询 [具体渠道]"
- 数据缺失：如果缺少必要数据才能给出准确答案，列出所需数据并请求用户补充
- 模糊意图：如果用户意图不明确，提出 1-2 个澄清问题后再回答
- 安全红线：如果请求涉及有害内容，直接拒绝并说明原因
</constraints>
```

### 设计要点

- 每种异常场景给出**具体的回复模板**，不要只说"拒绝回答"
- 兜底策略的语气应与 Persona 一致（专业角色用专业语气拒绝）
- 优先引导用户提供更多信息，而非直接拒绝
- 区分"不知道"（知识边界）和"不应该回答"（安全红线）
