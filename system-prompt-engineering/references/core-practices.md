# 五条核心实践详解

## 实践一：XML 标签结构化

减少长对话中的指令偏移（Instruction Drift）。

**核心标签集**

| 标签 | 用途 |
|------|------|
| `<persona>` | 角色设定 |
| `<context>` | 背景 / 领域知识 / 约束 |
| `<task>` | 核心动作和步骤 |
| `<constraints>` | 硬性行为约束 |
| `<format>` | 输出结构 |
| `<examples>` | Few-shot 样本 |
| `<rules>` | 业务规则 |

**为什么有效**
- 模型视标签为语义边界，指令互不干扰
- 长对话中标签比纯文本更持久
- 便于维护，改一处不影响其他

**嵌套规则**
- 保持一层嵌套为主，不超过两层
- 同级标签用空行分隔
- 小写英文，语义清晰

## 实践二：正面指令优先

告诉模型「要做什么」而非「不要做什么」。

**转换对照**

| 负面 | 正面 |
|------|------|
| 不要写太长 | 每段不超过 3 句 |
| 不要用术语 | 用日常语言解释 |
| 不要编造数据 | 仅引用提供的数据源，无数据时明确说明 |
| 不要跑题 | 始终围绕用户具体问题回答 |

**为什么有效**
- 负面指令需先理解「不该做」再推断「该做」，多一步推理
- 正面指令直接给行为目标，减少歧义
- 长对话中「不要」的记忆衰减快于「要」

**例外**：安全红线仍用负面指令，放在 `<constraints>`。

## 实践三：Few-Shot 示例注入

3-5 个理想问答对放入 System Prompt，锁定输出风格。

**放置位置**：System Prompt（贯穿整个会话），非 User Prompt（仅当轮生效）。

**设计要点**
- 数量：3-5 个覆盖典型场景
- 多样性：简单 / 复杂 / 不同类型输入
- 一致性：所有 output 格式统一
- 边界示例：至少包含一个「拒绝回答」样本

## 实践四：CoT 链式思考

在系统层级植入推理步骤，比单次「Think step by step」更持久。

**System vs User 级**

| 维度 | System 级 | User 级 |
|------|-----------|---------|
| 持久性 | 全会话 | 仅当轮 |
| 强制性 | 高 | 可被覆盖 |
| 场景 | 始终需要推理链 | 偶尔深度推理 |

**变体**
- 显式推理：输出推理过程（教学场景）
- 隐式推理：内部推理，只输出结论（生产场景）
- 分步验证：每步自检，矛盾则回溯

## 实践五：默认兜底策略

**四类兜底场景**
- **知识边界**：超出知识范围 → 建议咨询指定渠道
- **数据缺失**：缺必要数据 → 列出所需数据请求补充
- **模糊意图**：意图不明 → 提出 1-2 个澄清问题
- **安全红线**：涉及有害内容 → 直接拒绝并说明原因

**设计要点**
- 每种异常给出具体回复模板，不只说「拒绝回答」
- 语气与 Persona 一致
- 优先引导用户补充信息，而非直接拒绝
- 区分「不知道」和「不应该回答」
