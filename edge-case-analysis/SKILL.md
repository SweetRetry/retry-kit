# 边界情况发现

只回答一个问题：**在什么具体条件下，当前逻辑会进入未定义、未覆盖或违反既有约束的状态？**

保持只读分析。先检查真实代码、diff、测试、调用链或流程说明，再输出边界清单；不要用通用 checklist 代替证据。

## 分析流程

### 1. 锁定范围

- 按用户指定的代码、方案、流程或 diff 确定分析边界。
- 用户只说 `changes` 时，检查当前变更及其直接影响的调用路径，不自动扩展到整个仓库。
- 区分本次变更新增的边界、原有但被本次变更暴露的边界，以及与本次范围无关的问题；只报告前两类。

### 2. 还原正常路径与约束

从实现和上下文中提取：

- 输入前提；
- 关键状态及合法转换；
- 必须始终成立的 invariant；
- 成功、失败、取消和重试后的预期结果。

没有明确正常路径或 invariant 时，先标记信息缺口，不擅自把假设写成事实。

### 3. 推演相关边界

只选择与当前范围有关的维度：

- **输入**：空值、缺失值、极值、非法格式、重复、乱序、超大数据；
- **状态**：非法转换、过期状态、部分完成、重复进入、历史脏数据；
- **时间与生命周期**：超时、取消、重试、过期、重启、发布切换、中途退出；
- **并发与顺序**：重复提交、并发写、重复投递、乱序到达、竞态；
- **外部依赖**：慢响应、不可用、部分成功、返回契约变化、结果不一致；
- **身份与隔离**：登录过期、权限变化、资源归属、跨用户或跨租户访问；
- **数据一致性**：部分写入、缓存与源数据分歧、事务边界、读写延迟；
- **资源与环境**：容量上限、限流、内存或磁盘不足、时区、locale、编码和平台差异。

不要机械覆盖全部维度。无法形成具体触发链的候选项应删除。

### 4. 建立可验证的边界链

每个边界必须同时包含：

1. 可到达的触发条件；
2. 触发时所处的状态；
3. 被违反的 invariant 或未定义行为；
4. 对用户、数据或后续流程的具体影响；
5. 支撑判断的代码、diff、测试或契约证据。

缺少任一项时，不要把它列为已发现边界；将有当前证据指向的关键未知项放入“待确认”部分。不要罗列适用于任何系统的泛化未知项，例如在没有模块发布或动态调用迹象时猜测“可能存在外部消费者”。

### 5. 过滤噪声

不要报告：

- 没有特殊触发条件的普通 happy-path bug；
- 纯代码风格、可维护性或性能优化建议；
- 无可达路径支撑的“理论上可能失败”；
- 已被当前实现明确处理且有证据验证的情况；
- 同一根因的重复表述。

合并共享同一触发条件和后果的边界，按影响与可达性排序，但不要替用户做修复优先级或 ROI 决策。

## 证据等级

- **已确认**：代码、测试、日志或可复现路径直接证明边界存在，且成立所需的关键上下游约束均已核实。
- **高可信推断**：调用链和状态转换足以推出结果，但尚未运行验证。
- **待确认**：缺少关键运行时、数据或契约信息；只陈述缺口和需要确认的事实。

保持事实与推断分离。代码片段中没有展示某项保护，不等于系统中确认不存在该保护；外部约束可能推翻结论时，降为高可信推断或待确认。

## 输出方式

使用自然语言，直接从最重要的发现讲起。不要套固定模板、表格、字段清单或重复的小标题。

每个边界用一小段连贯说明讲清楚：它会在什么条件下发生，当时系统处于什么状态，哪条约束会被打破，以及会造成什么具体影响。证据和可信度自然地融入叙述；只有不确定性会实质改变结论时，才补充一句还需要确认什么。

合并原因和结果相同的发现，避免把一次状态失控拆成多条近似问题。只报告有信息量的内容。范围内没有成立的边界时，用一句自然语言明确说明“未发现有证据支持的边界情况”，不要为了凑结构而编造问题。

## 职责边界

- 不修改代码或配置。
- 不提供修复方案、落地代码、架构选型、Strong Practice、ROI 分析或实施计划。
- 不把测试建议混入边界发现；用户另行要求测试设计时再处理。
- 用户同时明确要求修复时，先完成本 skill 的边界清单，再将后续修复视为独立的普通编码任务。
