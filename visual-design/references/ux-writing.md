# UX 文案

## 按钮标签：动词 + 宾语

**永远不要用 "OK"、"Submit"、"Yes/No"。**

| 差 | 好 | 原因 |
|---|---|------|
| OK | 保存更改 | 说明会发生什么 |
| Submit | 创建账户 | 以结果为导向 |
| Yes | 删除消息 | 确认具体动作 |
| Cancel | 继续编辑 | 明确"取消"的含义 |

**破坏性操作**命名具体的破坏："删除"（永久）而不是"移除"（可恢复）。"删除 5 个项目"而不是"删除所选"。

---

## 错误信息：发生了什么 + 为什么 + 怎么修

| 场景 | 模板 |
|------|------|
| 格式错误 | "[字段] 需要是 [格式]。例如：[示例]" |
| 必填缺失 | "请输入 [缺少的内容]" |
| 权限不足 | "你没有 [东西] 的访问权限。[替代操作]" |
| 网络错误 | "无法连接到 [服务]。检查网络连接并 [操作]" |
| 服务器错误 | "我们这边出了问题。正在处理中。[替代操作]" |

不要指责用户："请输入 MM/DD/YYYY 格式" 而不是 "你输入了无效日期"。

---

## 空状态

空状态是入门时刻：简短承认 → 解释价值 → 提供行动。

"还没有项目。创建第一个来开始吧。" 而不是 "没有数据"。

---

## Voice vs Tone

Voice 是品牌个性（处处一致），Tone 适应场景：

| 时刻 | 语气 |
|------|-----|
| 成功 | 简短庆祝："完成！更改已上线。" |
| 错误 | 共情帮助："没能成功。试试这个…" |
| 加载 | 安心具体："正在保存草稿…"（不是"加载中…"） |
| 破坏性确认 | 严肃清晰："删除这个项目？此操作不可撤销。" |

**永远不要对错误用幽默。**

---

## 确认对话框：少用

大多数确认对话框是设计失败——考虑用 undo 代替。必须确认时：命名操作、解释后果、用具体标签（"删除项目"/"保留项目"，不是"是"/"否"）。

---

## 无障碍文案

- 链接文字有独立含义："查看定价方案" 不是 "点击这里"
- Alt 文字描述信息："Q4 收入增长 40%" 不是 "图表"。装饰性图片用 `alt=""`
- 图标按钮需要 `aria-label`

---

## 术语一致性

选一个词，坚持用。删除/移除/清除 → 统一用"删除"。设置/偏好/选项 → 统一用"设置"。多样性制造困惑。

---

## 多语言提示

为文本膨胀预留空间（德语 +30%、法语 +20%）。数字独立于句子结构。避免缩写。

---

**避免**：指责用户、模糊错误（"出了点问题"）、为多样性变换术语、对错误用幽默、冗余复述（标题已说的不要介绍语再说）。
