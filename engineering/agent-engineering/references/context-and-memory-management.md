# 上下文与记忆

上下文承载当前决策所需的信息。先减少无关输入，再决定压缩或持久化；上下文变长本身不证明需要自建记忆系统。

## 按需取得证据

- 初次检索返回相关摘要和定位信息；需要判断时再读取原文。文件路径、日志位置或记录 ID 应可回查。
- 工具在输出边界控制体积。截断保留关键错误、完整性标记和分页入口；不能只保留尾部就声称证据完整。
- 重复读取先判断来源是否变化。只有资源版本与权限范围可确认未变时才复用结果。

[Anthropic — Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) 将上下文视为有限资源，支持按需检索、压缩和结构化笔记。选择依据是实际任务表现，而非固定历史轮数。

## 压缩与状态延续

先查宿主是否已有 session、compaction 或持久状态机制。自建机制只补已测得的缺口。

压缩后仍须能恢复：当前目标、已确认约束、授权范围、关键证据及来源、实际变更、验证结果、未完成项、等待中的工具或批准。

- 任务事实与执行状态各有明确来源。摘要可以索引来源，不能把模型推断升级成已验证事实。
- 持久笔记保留当前有用状态及证据位置，按变化更新。它不必每轮全量注入高优先级提示词。
- 剪枝保留协议要求的工具调用、结果及推理项。依据项目 SDK 和模型接口核对，不能任意拼接或删除消息。
- 会话状态选定一种主导延续方式。混用完整历史重放与服务端会话时，须明确去重与一致性规则。
- 压缩或进程恢复后检查约束、未完成操作和证据入口；用长任务回放验证，不只检查摘要读起来是否通顺。

OpenAI 的 [Running agents](https://developers.openai.com/api/docs/guides/agents/running-agents) 列出历史重放、session 与服务端延续方式，并提醒混用可能重复上下文。具体压缩接口查 [Compaction](https://developers.openai.com/api/docs/guides/compaction)。

## 缓存与成本

提示词缓存复用输入前缀，不替代任务记忆，也不保证重复请求输出一致。

供应商支持前缀缓存时，保持可复用内容稳定，将动态内容置后；同时核对模型、断点、保留策略和接口要求。仅调整内容顺序不保证命中。

用缓存命中、总输入成本、延迟和任务正确率判断收益。压缩可能降低命中，却仍降低总成本；不要为缓存保留无关历史或过期事实。

机制依据：[OpenAI — Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)。
