# 子代理与委托

委托解决可独立分担的实际瓶颈；主控仍负责整体结果。先判断需要几个 Agent，再决定拓扑。

## 委托准入

在宿主和任务允许委托时，判断以下条件：子任务能独立交付，输入与权限可界定，结果可核验，预期收益超过协调和上下文成本。

依赖密集、共享状态多、拆分后仍须反复交换细节的任务通常更适合单 Agent。上下文过多可先缩小读取或压缩已完成工作；不能按跨文件或固定步骤数强制委托。

[Anthropic — Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) 展示了并行探索的收益和协调成本；研究任务的经验不能直接推导所有编码任务都需多 Agent。

## 按所有权选拓扑

| 情况 | 选择 |
| --- | --- |
| 主控需要汇总多个独立结果并保持回复责任 | manager 调用子代理作为工具 |
| 专家应接管当前交互和后续处理 | handoff，明确移交状态与责任 |
| 工作项已知且互不依赖 | 代码并行调度，不必让模型动态分工 |

OpenAI 的 [Orchestration and handoffs](https://developers.openai.com/api/docs/guides/agents/orchestration) 区分主控持有责任和专家接管。handoff 不等于并行，也不自动获得额外权限。

## 输入、权限与写入

- 委托说明目标、必要上下文、资源范围、交付条件与停止条件。发送足够判断的材料，不默认复制全部父代历史。
- 权限由执行层按调用身份实施。只读角色须覆盖 shell 等间接写入入口；模型和权限选择保留宿主配置与用户决定。
- 并行写入分配明确的资源所有权；无法隔离时串行修改或由主控整合。共享可变状态的更新须由明确所有者负责。
- 子任务独立配置预算和取消传播；等待、失败与取消均保持可见。无增量的交接往返应停止并诊断。

## 交接与整合

子代理返回结论、证据位置、实际变更、验证结果与未解决项；原始轨迹按需回查，不默认回灌全部历史。

主控检查证据和交付条件，并验证整合后的结果。子代理的“完成”或“通过”是待核对声明，不能直接成为整体任务的完成证据。
