# Simplify Code

复杂度分两种。**本质复杂度**来自问题本身：要存哪些数据、要守哪些规则、要和哪些外部系统打交道。**偶然复杂度**来自实现：多出来的层、重复的状态、绕远的流程、同一概念的几个名字。简化只删偶然复杂度。

在现有结构里逐行找问题，每一行都显得合理，找到的只会是局部毛病。所以先不看现有结构，只从行为推出问题需要的**理想形状**，再拿现状去对照。对不上的部分才是候选，而且会按偏离了形状的哪一项自然成组，那一项就是根因。

默认只交付审查；用户明确授权后才改代码。

## 0. 定范围

- 审用户指定的文件、目录、diff 或入口。用户说 `changes` 时，审当前改动；都没有时，先问。
- **推演单元**取包住范围的最小闭合功能，从入口一直到存储与外部调用。范围是一段 diff 时，单元是这段 diff 所属的功能。
- 读可以越出范围，包括调用方、接口另一端、类型定义和仓库已有的工具。改动只落在范围内与受影响的调用方。

## 1. 写行为契约

列出单元的每一类**观察者**以及他们看到的东西。简化前后，每个观察者看到的必须完全一样：

- 终端用户：每个界面状态下的渲染内容、可达性树、焦点与键盘行为、动画、URL 与浏览器存储。
- 接口调用方：路径、请求与响应的字段和类型、状态码、错误格式。
- 模块调用方：公共函数与组件的签名、返回值、抛出的错误。
- 存储：写入的数据、事务边界、并发语义。
- 外部系统：发出的请求与消息的次数、顺序和内容。
- 运维：日志、指标、埋点。

契约从入口、出口和副作用读出，同时记下现有的数据 schema 与外部接口。

**完成标准：**单元内每个副作用、每个对外输出，都能归到某个观察者的某一条。

## 2. 推出理想形状

只依据契约、数据 schema 和外部接口，写出今天从零实现这个单元时的形状。先写完，再去看现有的模块划分，防止照着现状画。

形状只含四项：

- **状态**：最少需要几份状态；每份只有一个所有者（数据库表、服务端缓存、URL、组件 state 等）；类型只允许合法取值；能算出来的都不存。
- **边界**：外部输入在哪里解析成内部类型，内部类型在哪里格式化成输出，信任、事务和部署的边界在哪。转换与校验只发生在边界上。
- **概念**：最少几个名词，每个只有一个名字。
- **流程**：每个入口从输入到输出走几步，每步做一件契约要求的事。

**完成标准：**契约的每一条都由形状的某一部分产生，形状的每一部分都至少对应契约的一条。

## 3. 对照现状

把单元内每个现存元素（文件、模块、类、组件、hook、类型、字段、状态、配置、层）映射到理想形状。映射不上的元素就是偶然复杂度，写明它偏离了形状的哪项决定，例如“状态：订单状态有两个所有者”。偏离同一项决定的元素归为一组，这项决定就是该组的根因。

对照时用 [references/signatures.md](references/signatures.md) 识别常见的偏离。

每组写出代价的证据：读者多跳了几层；改一次需求要多改几处，从 `git log` 取真实改动来数；或者要同时记住几种状态组合。

**完成标准：**每个现存元素要么映射到形状，要么归进某个偏离组。

## 4. 查栅栏

对每个偏离组，先查它为什么存在（Chesterton's fence）：注释、`git log` 与 `git blame`、测试替身、依赖注入的注册、外部引用、反射或序列化、性能测量、无障碍与兼容性要求、服务端渲染与水合约束。

查到成立的理由，说明形状漏了一条约束。把约束补进形状，重新对照受影响的元素。理由不成立或查不到时，写明查过哪些地方。

**完成标准：**每组结论为“保留”并附理由，或为“可简化”并附查过的地方；所有成立的理由都已补进形状。

## 5. 按杠杆排序

杠杆等于改掉后消失的偶然复杂度，乘以这块代码的改动频率（取 `git log` 的热点）。很少有人改的冷代码，即使写得绕，也排在后面。

把“可简化”的组排成一串步骤：

- 每一步单独保持行为不变，可以单独提交、单独验证；
- 能解锁后续的步骤排前面，例如先收紧类型，再删掉依赖宽类型的防御代码；
- 只有改契约才能消除的差异（例如接口字段）不排进步骤，单独列为“需改契约的提议”。

**完成标准：**每个“可简化”组都落在某一步或某条提议里，每一步都写明验证方式。

## 6. 实施

仅在用户授权后执行：

1. 先搭等价检查，用同一组输入在改动前后比对观察者看到的东西。
   - 前端：对每个受影响的界面状态截图、导出 DOM 与可达性树快照、记录网络请求。
   - 后端：重放同一组请求，比对响应、写入的数据与外部调用记录。
   - 现有测试没覆盖到的分支与转换，先补特征测试（characterization test），确认它在改动前通过。
2. 按顺序逐步实施，每步跑全部检查。出现差异就撤回该步，并记录原因。
3. 某一步没有检查能证明行为不变时，标为“未验证”，并写出缺少什么检查。

**完成标准：**每一步都标为“已验证”“未验证”或“已撤回”。

## 交付

1. **理想形状**：状态、边界、概念、流程，每项几行。
2. **步骤**：按杠杆排序，每步一段。

   ```text
   [1] 根因：订单状态有两个所有者（服务端与 ordersStore）
       症状：web/orders/useOrders.ts:12 把响应拷进 store；web/orders/OrderRow.tsx:30 用 effect 同步本地状态
       代价：最近 3 次订单显示相关改动，平均每次改 5 个文件
       改法：前端直接读请求缓存，删除 ordersStore.orders 与同步 effect
       验证：订单列表在加载、空、错误、有数据四种状态下截图，并比对请求记录
   ```

3. **保留**：查过但保留的复杂度，每条一行，附理由，免得下次重审。
4. **需改契约的提议**与**转交的 bug**：每条一行。简化保留原有 bug。
5. 实施后：每一步的检查命令、结果与验证状态，以及新增的特征测试与基线。

没有可简化项时，交付理想形状，并说明现状已经贴合它。
