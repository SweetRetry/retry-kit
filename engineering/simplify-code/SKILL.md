# Simplify Code

本 Skill 的核心是系统性判断：**当前复杂度是否在解决真实问题，若是表达或预支复杂度，如何进行最小化安全重构。**

## Quick start

### 输入代码示例：
```go
// user.go
type UserFetcher interface {
    FetchUser(id string) (*User, error)
}

type UserFetcherImpl struct {
    db *sql.DB
}

func (u *UserFetcherImpl) FetchUser(id string) (*User, error) {
    return u.db.QueryRow("SELECT ...", id)
}

func GetUserByID(fetcher UserFetcher, id string) (*User, error) {
    return fetcher.FetchUser(id)
}
```

### 审查输出示例：
```md
- [High] user.go:2: UserFetcher 接口目前仅有一个生产实现且无 Mock/测试替身需求 → 删除 UserFetcher 接口并内联
- [High] user.go:14: GetUserByID 函数只做了一层无参数转调的薄 wrapper 转发 → 删除 GetUserByID，让调用方直接调用 fetcher.FetchUser(id)
```

## Workflows

### 代码简化审查工作流

当触发本 Skill 时，按以下步骤执行审查：

1. **定位流程与边界确认**
   - [ ] 梳理核心业务动作的始末，区分哪些层在做业务决策，哪些层仅在转发/改名或搬运参数。
   - [ ] 确认当前语言与框架上下文。
   - [ ] 检查审查范围（单文件、单模块还是 PR）与重构半径限制（不擅自修改公共 API、对外契约、并发/事务机制、异常语义，涉及跨模块改动前与用户对齐）。

2. **统计复杂度度量值**
   - [ ] 统计读懂一个完整流程所需的函数跳转次数（若超过 4 次则标记为高跳转）。
   - [ ] 统计该行为涉及的角色数量及文件层级。
   - [ ] 检查重复代码的出现次数及演进方向是否一致。

3. **过滤必要非功能复杂度（排除以下场景）**
   - [ ] 确认是否为经过 Benchmark 验证的性能特化路径（位运算、无锁设计、对象复用等）。
   - [ ] 确认是否为纵深防御所需的冗余安全校验与入参清洗。
   - [ ] 确认是否为防止领域泄漏的解耦映射层（如 BO/DTO/Entity 转换）。
   - [ ] 确认是否为显式错误处理与资源清理逻辑（如 Go 的 `if err != nil`、`defer` 释放）。

4. **输出结论与严重级判定**
   - [ ] 判定严重级：阻碍排障且有低风险简化路径的标记为 `High`；失衡但修改取决于变更频率的标记为 `Medium`；仅有改进空间但无实质负担的标记为 `Low`（不因偏好风格判定为 Low）。
   - [ ] 将 findings 转化为具体的简化动作（删除、内联、合并、扁平化、去配置化、去泛化）。
   - [ ] 默认以单行简洁格式输出结果（格式为 `- [严重度] <位置>: <问题说明> → <具体简化动作>`，不输出思考过程和总结词，若无发现仅输出“未发现明确的 simplify findings”）。

## Advanced features

### 核心判定原则与信号对照表

#### 1. 核心判断原则
- **理解路径优先**：简单不等于行数少，而是理解路径更短。若缩短代码行数会导致控制流变绕或引入隐式状态，则不视为简化。
- **服务当前变化**：怀疑一切为假想未来预留的扩展点。当前无第 2 种真实变化时，保持单路径实现。
- **区分合理重复/单实现**：重复稳定出现 3 次以上且演进方向一致才可抽象；保护合理的灰度/环境双轨机制，以及符合框架规约/测试 Mock 的单实现 Interface。

#### 2. 复杂度信号对照表

| 信号分类 | 复杂度症状 (High Value Signal) | 合理例外 (Exclusion / Low Value) |
| :--- | :--- | :--- |
| **无效抽象** | 单实现 interface/strategy；纯转发的 provider/resolver/service。 | 用作 Mock 测试、SDK 扩展点、或框架 DI 注入约束；支持动态注册的策略模式。 |
| **薄中间层** | 跨层级仅做参数转发，未吸收复杂度或缩小调用方职责。 | 遵循标准 DDD/分层架构（如 Controller-Service-Repo）且职责边界清晰的层。 |
| **错误抽象** | 泛型/抽象为了适配不同语义而堆砌 Flag、分支、枚举和未配置的配置项。 | 各处语义完全一致，通过精简分支能完美统一的抽象。 |
| **隐藏主流程** | 读懂一个行为需要跳转 4 次以上；核心步骤被 Setup/Adapter 噪音淹没。 | 线性且清楚的单函数长流程。 |
| **概念膨胀** | 文件数、类数与名词数量远超问题规模；职责边界不真实的重叠角色。 | 因业务边界真实独立、各层职责明确而存在的多文件。 |

#### 3. 审查红线（绝对禁止）
- **盲目合并**：禁止仅因相似就合并处于不同演进生命周期或演进方向的逻辑。
- **机械删除**：禁止看到单实现接口或分层转发就无视测试/规约/标准协议盲目要求删除。
- **破坏稳定性**：禁止简化为了性能特化、纵深防御或显式错误资源清理而设计的“必要复杂度”代码。
- **层级耦合**：禁止强行合并领域防腐层（如 DTO 与 Entity 合并）导致结构耦合。
- **越界重构**：禁止在未经用户授权的前提下直接规划大规模架构重组或破坏向后兼容。
