# Simplify Code

让下一个读代码的人更快看懂、更快定位问题，同时**行为完全不变**。

衡量方法：从入口读到真正干活的那行代码，要跳几个文件、经过几层函数、记住几个概念。这几个数变少才算简化；行数变少但更绕，不算。

默认只给审查结论；用户明确授权后才改代码。

## 范围

- 只审用户指定的文件、目录、diff 或入口。用户说 `changes` 时，审当前改动；用户没指定时，先问。
- **行为不变**指以下各项都不变：返回值、抛出的错误类型、副作用的次数与顺序（写库、发请求、发消息、日志与埋点）、写入的数据、并发与事务行为、公共函数签名。
- 要改上面任何一项，就不是简化。确有必要时，先问用户。
- 发现 bug 时，记为转交项：特殊条件下才出现的失效交给 `find-edgecases`，普通 bug 交给代码审查。简化改动保留原有 bug，修复另开改动。
- 范围外的结构问题和跨模块的大重组，只记一行。

## 1. 从入口读到干活的地方

从每个入口（路由 handler、导出函数、命令）一路跳到真正做事的代码。记下经过的每一层，并用一句话写这层做了什么：算了什么、校验了什么、转换了什么格式、隔离了什么依赖，或者“只是把参数往下传”。

```text
POST /users → UserController.create → UserService.create → UserManager.create → UserRepo.insert
              只转发                   只转发               校验邮箱唯一           写库
```

连续几层“只转发”是重点。

**完成标准：**每个入口的调用链都写完，每层都有一句话。

## 2. 判定可简化前，先查它为什么存在

判定一层可简化前，先查它存在的理由（Chesterton's fence）：注释、`git log` 或 `git blame`、测试里的 mock、依赖注入的注册、是否导出给外部使用、有没有性能基准。

以下复杂度有证据时保留：

- 有基准数据支撑的性能优化；
- 系统边界上的安全校验；
- 外部协议与内部模型之间的转换；
- 语言要求的错误处理与资源释放。

**完成标准：**每层的结论是“保留”并写明理由，或是“可简化”并写明查过哪些地方。

## 3. 选最小的改法

对每个“可简化”的层，按下表选改法：

| 看到的情况 | 改法 | 遇到这种情况就保留 |
| --- | --- | --- |
| 接口只有一个实现；工厂只被调用一次 | 直接调用具体实现 | 测试 mock、SDK 扩展或依赖注入要用这个接口 |
| 函数只把参数原样传给下一层 | 删掉这一层 | 这层隔离了外部依赖或做了格式转换 |
| 同一校验、转换或空值检查在调用链上做了多次 | 只留在最先接触外部输入的那一层 | 该层还有别的调用入口，或各层抛的错误不同 |
| 一个函数靠 flag 分支做几件不同的事 | 按用途拆成几个函数 | 只是同一件事的参数微调 |
| 主流程被拆成很多小方法和临时变量 | 合回一段从上往下读的流程 | 某段计算独立且复杂 |
| 两处代码长得像，但改动原因不同 | 拆开，允许各写一份 | 两处确实总是一起改 |
| 文件、类、概念比问题本身多得多 | 合并总是一起改的部分 | 它们属于真正独立的业务 |
| 代码、参数、配置或 flag 没有调用方，或所有调用方都传同一个值 | 删除，或改为常量 | 被反射、动态调用、序列化或外部使用 |
| 存了一个能从别的状态算出来的值 | 改为现算 | 有性能数据，或需要保存某一时刻的快照 |

**完成标准：**每个“可简化”的层都对应一种改法，或因符合保留条件改回“保留”。

## 4. 实施

仅在用户授权后执行：

1. 列出能检查这段行为的现有手段：测试、typecheck、lint 与 build。
2. 某项改动涉及分支或数据转换，且现有测试没有覆盖时，先写特征测试（characterization test，记录当前输出的测试），确认它在改动前通过。
3. 逐项修改，同时修改受影响的调用方。
4. 每项改完，运行相关检查。
5. 检查失败时，撤回该项并记录原因。
6. 没有检查能证明行为不变时，把该项标为“未验证”，并写出缺少的检查。

**完成标准：**每项都标为“已验证”“未验证”或“已撤回”。

## 交付

每项一行，格式为 `[等级] 文件:行号: 读者付出的代价 → 改法`：

```text
[High] src/user/manager.ts:12: Service 与 Manager 两层只转发，读者跳 3 个文件才看到邮箱校验 → 删除 UserManager，校验移入 UserService
```

等级：

- `High`：明显拖慢阅读，且改起来风险低；
- `Medium`：值不值得改，取决于这段代码改动的频率；
- `Low`：负担小但确实存在。

“读者付出的代价”要具体：多跳了几层、多跟了几个分支、多记了几个概念。只是写法偏好的问题不列。

问题列表之后，列出范围外的问题与转交项，每条一行。没有发现时输出 `未发现明确的 simplify findings`。实施后，为每项写出检查命令、结果与验证状态，并列出新增的特征测试。
