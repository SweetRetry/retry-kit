# 多层边界分析

发现当前设计在非常规但可到达的条件下，何时进入未定义、未覆盖、彼此矛盾或违反 invariant 的状态。

先画出**边界地图**，再从每一层构造**边界链**，最后用反证排除猜测。广度来自逐层检查，深度来自跨层组合和恢复路径，可信度来自真实证据。

本 skill 的交付止于只读的边界发现：输出边界、证据与必要的不确定性。代码修改、测试设计、修复方案、架构选择、ROI 和实施计划属于后续独立任务；用户同时要求修复时，先交付边界发现，再处理后续任务。

## 1. 锁定范围与证据

从用户指定的代码、方案、流程或 diff 开始，检查真实实现、调用者与被调用者、测试、schema、配置、接口契约和运行证据。用户只说 `changes` 时，以当前变更为起点，沿数据、状态和副作用的传播路径向外追踪，直到遇到稳定 contract、明确隔离边界或与变更无因果关系的区域。

区分本次范围新引入的边界、被本次范围触发或放大的原有边界，以及无因果关系的问题。前两类进入分析，第三类留在范围外。

完成本步时，应明确入口、出口、直接与间接消费者、状态权威、外部依赖和可用证据；无法确认的部分记录为信息缺口，不用假设补齐。

## 2. 建立边界地图

还原正常路径、失败路径、恢复路径和生命周期。标出输入与 actor、状态权威、合法转换、持久化点、缓存、跨进程 handoff、不可逆副作用、权限边界、人工介入点，以及成功、失败、取消、重试后的预期结果。

逐层判断当前范围是否存在独立的边界面：

- **值与表示层**：缺失、空值、极值、非法格式、精度、编码、序列化、默认值；
- **局部逻辑层**：分支组合、错误路径、清理逻辑、重复进入、返回值与异常语义；
- **领域与状态层**：invariant、非法转换、部分完成、终态重入、删除、归档、恢复；
- **数据与持久化层**：唯一性、事务边界、部分写入、读写延迟、缓存分歧、历史脏数据；
- **接口与契约层**：调用方与提供方的假设、兼容性、错误映射、分页、批量、幂等语义；
- **并发与时间层**：竞态、重复、乱序、延迟、超时、时钟、时区、过期、调度交错；
- **分布式与依赖层**：部分成功、结果不确定、消息投递、重试放大、降级、第三方契约漂移；
- **身份与隔离层**：认证过期、权限中途变化、资源归属、跨用户或跨租户访问、委托关系；
- **资源与运行层**：容量上限、限流、背压、内存或磁盘不足、启动、关闭、崩溃、重启；
- **部署与演进层**：滚动发布、旧客户端、旧数据、schema 或配置漂移、feature flag、回滚；
- **业务与人工层**：额度、计费、结算、取消、退款、审批、人工重放、对账和不可逆业务后果。

并非所有层都适用，但每一层都要经过适用性判断。完成本步时，所有适用层、跨层 handoff 和核心 invariant 都应出现在边界地图中。

## 3. 对每层施加扰动

围绕真实状态和 contract 推演能改变结果的最小扰动：

- 值从正常区间跨到缺失、临界、溢出或表示不一致；
- 一次事件变成零次、重复、多次、并发或乱序；
- 操作在开始前、执行中、提交后或响应前被取消、超时、崩溃或重试；
- 数据、缓存、权限、配置或时钟在一次流程中途发生变化；
- 依赖从明确成功或失败变成慢响应、部分成功或结果不确定；
- 正常规模扩大到容量、速率、批量或资源边界；
- 当前版本与旧客户端、旧数据、相邻版本或回滚状态共同运行。

从扰动后的可达状态继续向下游追踪，不在首次报错处停止。检查副作用是否已经发生、状态是否能恢复、重试会读到什么、下游如何解释结果，以及用户或业务最终看到什么。

完成本步时，每个适用层都应经过与其 contract 相关的扰动；每个候选项都应能说明从正常路径分叉的准确位置。

## 4. 深挖跨层组合

系统级 edge case 常由两个单独可处理的条件组合产生。对边界地图中的每个 handoff 和不可逆副作用检查：

- 上游认为成功，而下游失败、超时或只完成一部分；
- 数据已提交但响应丢失，调用方随后重试、取消或切换身份；
- 恢复、补偿、清理或 retry 本身再次失败或被重复执行；
- 并发、资源压力或权限变化发生在迁移、发布、过期或人工操作期间；
- 两个不同 actor、租户、设备、worker 或版本同时操作同一逻辑实体；
- 单个保护各自成立，但组合后出现顺序缺口、状态缝隙或责任真空；
- 局部失败被吞掉或错误映射为成功，直到更远的层才显现数据或业务后果。

沿传播方向追踪候选项，直到系统回到明确稳定状态、产生不可逆后果，或证据边界使后续只能待确认；然后反向检查恢复与重入是否会再次触发同一链条。

完成本步时，每个跨层 handoff 都应检查部分失败、结果不确定和 replay；每个候选边界都应覆盖初次失效与后续恢复路径。

## 5. 建立可验证的边界链

边界链包含：**可到达的触发条件 → 分叉前状态 → 跨过的层与 handoff → 被违反的 invariant 或未定义行为 → 系统最终状态 → 用户、数据或业务影响 → 证据**。

按证据定级：

- **已确认**：代码、测试、日志、数据或复现路径直接证明边界存在，关键上下游约束均已核实；
- **高可信推断**：实现、调用链和状态转换足以推出结果，但尚未运行验证；
- **待确认**：现有证据指向具体风险，但缺少会改变结论的运行时、数据或契约事实。

代码片段中未出现保护，不足以证明系统中不存在保护。缺少完整链条的候选项只能进入待确认，而且要指出缺失的具体事实；适用于任何系统的泛化未知项不形成发现。

完成本步时，每个保留项都应具备完整边界链，或具备由现有证据指向的明确缺口。

## 6. 反证与覆盖收口

逐条尝试推翻候选边界：检查保护逻辑、上游约束、下游 contract、数据库约束、运行配置、测试和实际可达性。实现已明确处理、无法到达，或没有特殊触发条件的普通 happy-path bug，从结果中移除。

收口前复核：

- 每个适用层都已检查，没有只停留在函数或 diff 表面；
- 每个核心 invariant 都至少经历一次能威胁它的扰动；
- 每个状态转换都检查了中断、重复和恢复后的重入；
- 每个跨层 handoff 和不可逆副作用都检查了部分成功与结果不确定；
- 并发、时间、权限、资源和版本条件已在相关位置参与组合，而非孤立罗列；
- 同一根因与最终后果只保留一次，可信度与证据一致。

完成本步时，所有适用层均有结论，所有输出项均经受过反证，所有信息缺口都具体到可能改变哪条结论。

## 输出

使用自然语言，从影响最大的发现讲起。每个边界用一小段连贯文字讲清触发条件、状态如何跨层传播、哪条约束被打破、最终影响、证据与可信度；只有未知事实会实质改变结论时，才说明待确认内容。

按根因和影响合并发现，不套固定表格或字段模板。范围内没有成立的边界时，直接说明“未发现有证据支持的边界情况”，并确保这一结论来自完整的多层复核，而非只检查 happy path。
