# Task Execution Contract

配置任务包中的派发、审查、集成与恢复规则时读取。这里描述任务执行契约，不自动启动当前会话的子 Agent 或开发工作。

### 1.3 两级审查机制与 5 条硬红线 (Two-Tier Review)
- **局部完成前收敛复杂度**：实现前确定已有语义归属与复用点；提交前检查本次新增的重复规则/状态、无当前用途的扩展点、无职责的转发层、应移除的旧路径与临时代码。证据明确且范围内可低风险消除的就地处理，保留有实际职责的抽象；纯风格偏好不挂单，跨范围治理记录收益与代价后另行裁决。
- **第 1 级：子任务日常审查 (Phase Reviewer)**：相关检查通过并形成语义完整的 Commit 后异步审查，记录 base/head 与覆盖范围，结合调用方核对改动及 5 条硬红线。局部复杂度未收敛则退回最小修复；非阻塞且有明确价值的后续工作才记入 `issues.md`，避免积累尾部 simplify 清单。
- **第 2 级：集成后最终验收 (Final Sign-off Reviewer)**：核验合并后的业务行为、跨任务交互、共享状态和目标遗漏。运行项目要求及与风险相称的回归，复用仍有效的局部审查证据；不机械重审未受影响代码。未运行或失败的必需检查不能算通过，既有失败需基线证据。`SIGN_OFF` 表示任务验收通过，不授予发布权限。
- **审查 5 条硬红线（一票否决 BLOCKER）**：
  1. **保护验收依据**：为通过检查弱化断言、跳过必需测试、吞掉必须暴露的错误，或用假数据冒充真实实现；需求变更导致的测试更新由验收责任人按新契约同步并复核，不把正常测试 fixture 当作弊；
  2. **防违规**：破坏 `00-overview.md` 中约定的核心业务规则（Invariants）；
  3. **防慢查询**：在大表上写无索引关联、无条件 `LATERAL JOIN`、全表扫描、循环查库 (N+1) 或无分页一次性全量加载数据；
  4. **防严重缺陷**：真实可达的空指针、并发竞态或死锁；
  5. **核对历史包袱处置**：以历史包袱为由引入本可在当前范围低风险消除的重复规则、无效层或绕过业务约束的补丁。
- **核对数据库索引，不盲信单测**：
  - 涉及 DB/ORM 改动时，Reviewer **必须使用检索工具查阅仓库中的 Schema、Migration 或 DDL 定义**，核验查询命中的具体索引名；无匹配索引且未补迁移脚本直接打回；
  - 单元测试通常仅有少量 mock 数据，单测通过对性能判定为零置信度。

### 1.4 物理隔离与节奏控制 (Isolation & Control)
- **Git Worktree 物理隔离**：并发子任务分配独立的 `.worktrees/phase-X`，避免文件覆盖与 Git 锁冲突。
- **共享资源边界**：端口、测试数据库、迁移和外部环境也需分配所有权或串行访问；Worktree 不隔离这些资源。主控汇总执行状态与全局台账，子任务只回传局部记录。
- **预算与诊断**：按任务不确定性设置执行预算。同一失败、同一假设且无新证据的重复尝试触发诊断或换路；同一修补思路无增量失败两次即停止该思路。有新证据的调试可在预算内继续。预算耗尽、环境故障和需求缺失分别记录续接条件，独立任务继续推进。
- **能力画像与迟绑定（Late Binding）**：切分子任务时只评估抽象能力画像（Profile），禁止在任务文档中硬编码具体厂商的具体模型版本号，避免模型升级后任务包失效：
  - **低复杂度** (`tier: fast`, `effort: off`)：机械样板、文档配置、简单单测或严格遵循现有模式的增量；
  - **中复杂度** (`tier: standard`, `effort: low~medium`)：标准业务逻辑、多分支组件、具明确契约的接口与常规重构；
  - **高复杂度** (`tier: reasoning`, `effort: high`)：核心算法、并发竞态、跨模块复杂状态机、底层协议架构或高不确定性排障。
- **运行时动态映射**：具体模型名与推理控制参数由执行宿主（Harness / CLI / 环境配置别名）在派发时动态解析（如宿主别名 `fast → 最新轻量模型`，`reasoning → 当前最新高推理模型`）。拆解物保持厂商中立，模型换代仅需升级宿主别名，任务文档零修改。硬限制由运行时实施，不支持时标为执行约定。
- **状态与证据门禁**：任务状态依次为 `Todo → Implementing → Verifying → Reviewing → Ready → Integrated`；未完成任务可进入 `Blocked`，解决后回到实际步骤。`Ready` 必须有绑定代码版本的验证通过与明确审查通过，`Pending`、未知或“没有 BLOCKER”均不足以放行；`Integrated` 还需合并后相关检查通过。交付切片完成另需对应业务行为验收通过。
- **限制未确认依赖扩散**：异步审查期间继续独立工作；依赖尚未通过门禁的契约或行为的任务等待。修复、rebase 或契约变化后重新判断证据覆盖，只使受影响的验证/审查失效并补查。集成责任人合并 `Ready` 任务，验证后再推进相关依赖。
- **断点与恢复**：在总览的恢复断点记录分支、base/head、未提交改动位置、证据、进行中的操作及下一步；有外部副作用时记录操作标识与完成证据。中断恢复先核对 Git 和实际运行现场，再修正看板，不盲目重放迁移或外部操作。确认提交已集成、必要证据已保留且无未提交工作后清理 Worktree。
