# Task Breakdown

把已确认的需求、RFC 或接口契约，拆解为结构清晰、可独立执行且适合多 Agent 并行协作的工程任务文档包（保存在 `docs/tasks/{taskfolder}/**`）。

## 1. 核心质量门槛 (Quality Levers)

### 1.1 充分提供上下文 (Context First)
- **总览锚定业务全局 (`00-overview.md`)**：写清业务目标、核心实体结构、不可破坏的业务规则（Invariants）与关键技术决策；涉及数据访问时补充生产数据量级与性能基准。
- **子任务自含局部上下文 (`0X-phase-*.md`)**：每个执行任务包含场景意图、上游契约、下游交付物与调用方、适用的仓库参考实现；涉及数据访问时补充数据规模与索引约束。
- **当前规格是执行依据**：公共规则和契约只保留一个权威来源；子任务摘录必要约束并注明来源版本，避免复制整份总览。数据规模、性能目标与参考实现应有来源，未知项明确标记，不套用模板数值。

### 1.2 交付切片与执行任务 (Delivery & Ownership)
- **按业务行为组织交付**：交付切片描述触发条件、可观察结果、业务规则与相关失败状态；只有合并后的行为验收通过才完成。纵向指验收覆盖真实调用链，不要求每个 Agent 贯穿全栈修改代码。
- **按语义归属拆分执行任务**：一个交付切片可由多个 Phase 协作完成。每个 Phase 明确独占写入范围与上下游契约，模块实现和专属测试放在同一任务内；频繁互改同一规则或依赖对方内部实现的任务应合并或串行。
- **公共文件唯一责任人**：共享类型、入口注册、迁移、依赖清单及锁文件由指定任务集中修改，消费者提交变更需求。Worktree 隔离不允许多个任务并发修改同一语义来源。
- **先验证不确定边界，再扩大并行**：跨模块契约尚未验证时，先以一个代表性最小场景跑通真实链路，可由单个串行任务或多个有依赖的任务完成；已有稳定链路可直接复用。直接写明前置任务、启动条件与可并行任务，已就绪任务持续集成，不把接线与联调全部留到末尾。
- **任务粒度与渐进细化**：任务与文件数量随依赖、责任边界和验收范围动态调整，不设固定数量或行数配额。近期任务写清步骤和验证命令，远期保留目标、依赖与验收条件，执行前再细化。

### 1.3 执行契约

为任务包配置派发、审查、集成或恢复时，读取 [execution-contract.md](references/execution-contract.md)，将适用规则写入任务文档。它包含复杂度收敛、两级审查、索引核验、Worktree 与共享资源所有权、能力迟绑定、证据门禁和恢复断点；这些约束不等于自动启动执行。

### 1.4 老代码处置与变更追踪 (Legacy & Changes)
- **按必要性处置老代码**：与当前行为有关且低风险时就地修正；只有确实需要隔离外部协议或不稳定实现时增加适配层。必要的临时兼容记录到 `legacy-burdens.md`，注明代价、移除条件与后续责任，不默认扩张重构范围或承诺未经确认的还款日期。
- **当前规格与历史分离**：需求或契约变化时，同步更新总览及受影响任务，使其始终反映当前有效要求；在 `changes.md` 追加旧要求、新要求、原因、依据和影响范围，保留历史而不让执行者重放历史推导现状。
- **中途改契约的同步步骤**：定位受影响任务并暂停相关依赖，由契约责任人在指定集成分支提交变更，更新规格与验收依据；相关分支按仓库策略同步，复核受影响证据后恢复。无需暂停无关任务或强制操作主干、打 Tag。

### 1.5 面向人的进度看板 (Human Kanban)
- 复制 [assets/kanban.html](assets/kanban.html) 到任务目录，主控根据执行汇报更新其中 `board-data` JSON；无需独立状态文件、构建或服务。Markdown 保存需求、契约及恢复上下文，看板保存当前展示进度，不从 Markdown 推断状态。
- 任务启动、状态或阻塞变化、审查裁决与集成验收后更新数据及时间；主控核对汇报的任务与代码版本，按证据门禁采纳，旧汇报不得覆盖新状态。子 Agent 只汇报，不直接改看板。
- 保留交付进度、状态分布、任务卡片与依赖图；业务已验收和任务已集成分别计数，阻塞与待决事项直出，技术证据按需展开。只更新数据区，不随任务重写界面。
- 数据字段见模板内注释；写入时将 JSON 字符串中的 `<` 编码为 `\u003c`。交付前打开看板核对计数、依赖与状态；它是汇报后的快照，刷新查看更新。

## 2. 任务包结构规范 (Task Package Structure)

所有文件写入 `docs/tasks/{taskfolder}/`（模板见 [references/templates.md](references/templates.md)）：

| 文件名 | 作用 | 包含核心内容 |
| :--- | :--- | :--- |
| **`00-overview.md`** | Agent 全局知识与计划 | 当前规格、交付切片及验收、任务复杂度与依赖、规则与数据规模、状态入口、DoD 与最终验收提示词 |
| **`kanban.html`** | Human 可视化看板 | 验收进度、状态分布、任务卡片、依赖图、阻塞与待决事项、按需展开的详情 |
| **`0X-phase-*.md`** | 独立执行子任务 | 所属交付切片、任务复杂度与推荐配置、任务上下文、写入边界、复杂度取舍、派发与审查配置、步骤与版本绑定的验证证据 |
| **`issues.md`** | 问题追踪账本 | 需求未明确细节、外部依赖故障、Reviewer 提出的改进建议 |
| **`legacy-burdens.md`** | 老代码记录表 | 遇到的历史代码坑、当前处理方式（顺手改/加防腐层/临时兼容）与后续还款计划 |
| **`changes.md`** | 需求变更表 | 追加记录中途发生的需求变更、接口调整与分支同步情况 |

## 3. 拆解步骤与完成标准 (Breakdown Steps)

当用户调用 `$task-breakdown` 时，按以下顺序执行拆解，每一步达成完成标准后再进行下一步：

1. **提炼全局契约与规则**
   - 梳理业务现状、范围（In-Scope / Non-Goals）、核心实体、业务规则（Invariants）、生产数据量级预估与技术选型 ADR；
   - 定义交付切片及业务验收，识别需先验证的契约边界，安排最小闭环或引用已有链路证据；
   - **完成标准**：创建 `docs/tasks/{taskfolder}/00-overview.md`，包含上述完整内容与最终验收 Reviewer Payload。
2. **按责任边界切分执行任务**
   - 建立交付切片到 Phase 的映射，按依赖和所有权安排串并行，为近期任务创建 `0X-phase-{slug}.md`；
   - 评估各 Phase 复杂度（低/中/高），据此标注推荐模型层级与推理强度；
   - 注入自含任务上下文（场景、上游契约、下游消费、参考代码范式、数据量级约束），限定修改范围（Exclusive Write）与只读范围，配置派发与审查 Payload；
   - **完成标准**：每个交付切片都有实现及集成验收责任人，公共写入无并发重叠；子任务均标注复杂度与模型/推理配置；近期任务具备可执行验证，远期任务标明细化条件，未解决前置条件不标为可派发。
3. **初始化辅助台账**
   - 创建 `issues.md`、`legacy-burdens.md` 和 `changes.md`；
   - 复制 HTML 模板并填入初始计划，尚未执行的任务标为待办、证据标为未运行；总览链接看板并记录初始恢复断点；
   - **完成标准**：台账及初始状态建立，看板可打开且任务数量、依赖、状态与初始化计划一致。
4. **交付拆解汇报**
   - 向用户汇报拆解结论；
   - **完成标准**：优先给出 HTML 看板入口，再汇报文档路径、交付切片与执行任务映射、核心规则与数据规模约束、第一批可启动任务及未决条件。拆解交付不等于自动启动开发，执行范围沿用用户授权。
