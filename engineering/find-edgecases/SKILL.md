# Find Edgecases

找这类问题：正常情况下没事，但在某个**真实可能发生**的条件下，系统进入错误且无法自己恢复的状态。常见后果有重复扣款、两份数据不一致、任务永远卡在 `processing`。

默认只报告问题。用户要建议时，在问题列表后按根因给方向。用户要修改时，先用测试复现，再只改已确认问题涉及的代码，改完重跑该测试。

## 范围

- 只审用户指定的代码、diff、设计或调用路径。用户说 `changes` 时，审当前改动；用户没指定时，先问。
- 审设计文档时，用章节或流程节点代替 `文件:行号`。
- 范围外的代码可以读，但只为回答两个问题：这个触发条件真能发生吗？上下游有没有兜住？
- 根因在范围外的问题，只在结尾记一行。
- 正常输入就会出错的普通 bug 交给代码审查，复杂度问题交给 `simplify-code`，交互问题交给 UI 审查。这些只在结尾记一行。

## 合格的 finding

> `order/pay.ts:42` 调用支付接口后、把订单写成 `paid` 前，如果进程重启：钱已扣，订单仍是 `pending`。`jobs/retry.ts:18` 会重新发起扣款，且请求不带幂等键，用户被扣两次。证据：`pay.ts:40-48` 先调支付再写库；支付调用没有传 `idempotencyKey`。等级：高可信推断，未复现。

每个 finding 都要写清：

1. 触发条件；
2. 在哪一行走上岔路；
3. 已经发生了什么撤不回的事；
4. 系统最后停在什么状态；
5. 影响谁；
6. 证据与等级（见第 4 步）。

缺任何一项，就继续查或丢弃。

## 1. 找出“出错就麻烦”的位置

在范围内找两类位置，每条标 `文件:行号`：

- **撤不回的动作**（不可逆副作用）：写库、调外部接口、发消息、扣款、发通知、删文件。
- **必须成立的规则**（invariant）：例如“一个订单只扣一次款”“库存不为负”“状态只能 `pending → paid → shipped`”“缓存与数据库一致”。

**完成标准：**两类位置都已列出；每个撤不回的动作都标出它可能破坏的规则。

## 2. 把相关路径走一遍

从每个位置出发，顺着代码回答：谁调用它？它调用谁？成功怎么走，失败怎么走？

重点看跨边界的交接：调用外部服务、写库后发消息、任务入队、新旧版本读同一份数据。每个交接处回答两个问题：

1. 交接前的状态是什么？
2. 失败时，调用方以为发生了什么，实际发生了什么？

**完成标准：**每个写操作都能说出最后由谁读取它的结果，以及失败或进程重启后由谁重试、由谁接着做。

## 3. 逐个问“如果……会怎样”

从撤不回的动作开始问，只问会改变结果的问题：

- 同一请求或消息来两次？两个同时来？顺序反了？
- 做到一半进程挂了？写库成功但响应没回去，调用方又重试？
- 依赖超时或请求被取消：是没做，还是做了但没回？
- 执行途中，权限、配置、缓存或当前用户被改了？锁、令牌或缓存过期了？
- 输入为空、`null`、超长、边界值，或涉及时区、精度、旧版本格式？
- 数据量放大 100 倍、队列积压、新旧版本同时运行、回滚？
- 重试、补偿或清理本身失败，或与正常流程同时运行？

风险最高的位置，再把两个相关条件叠加着问，例如“超时之后又重试”。

每个问题都追到系统最终停下的状态：数据最后是什么样？会不会自己修好？抛异常、返回错误、打日志都不是终点，要继续看是谁接住了它。

**完成标准：**每个撤不回的动作都问过上面每一类问题；每个候选都能说出最终状态，或说出缺哪项信息才能判断。

## 4. 尝试推翻每个候选

对每个候选找反证：上游是否已经校验？数据库有没有唯一约束？框架或队列是否自带去重？部署方式是否让触发条件不可能出现？有没有测试覆盖？一个函数里没有保护，不代表整个系统没有保护。

高严重度的候选能用现有测试框架或一段脚本复现时，先复现再定级。只报告时，复现用的临时文件放在仓库外，或跑完删除。

按证据标等级：

- **已确认**：代码、测试、日志、数据或复现过程直接证明，上下游约束已核实；
- **高可信推断**：调用链足以推出后果，但没有实际运行；
- **待确认**：有具体线索，但缺一项会改变结论的事实，例如线上配置、部署拓扑或真实数据。

**完成标准：**留下的每条都经过反证；待确认项写明缺哪项事实；同一根因只留一条。

## 5. 输出

按严重度从高到低排：数据错误与安全 → 撤不回的业务损失 → 服务不可用 → 其他。每条按上面示例的格式写一段。

问题列表之后依次写：

1. **审查范围**：审了哪些代码，哪些高风险路径没覆盖到；
2. **范围外线索**：每条一行，写位置与怀疑原因；
3. **转交项**：每条一行，写位置与该交给谁。

没有成立的问题时，写“未发现有证据支持的系统 edge case”，再写审查范围与可能改变结论的未知项。
