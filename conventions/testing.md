# Testing

测试编写与覆盖规范。能机械判定的禁令由 [scripts/check-tests.mjs](scripts/check-tests.mjs) 执行，其余条款靠评审。

## 目标与基本原则

测试以合理成本保护真实业务行为、数据正确性、对外契约和高风险边界。测试数量与覆盖率只用于发现遗漏，不等于正确性。

不要求每个文件、函数、类、Hook 或组件都有测试。新增测试必须有独立的错误捕获价值，不能仅以提高覆盖率或编写成本低为理由；但“必须有测试的情形”一节列出的场景不受此限。

新增或保留一个测试前，应能回答：

1. 它保护哪条业务规则、数据约束或对外契约？
2. 哪种合理且可能发生的错误会使它失败？
3. 现有测试是否已覆盖相同风险？
4. 仅重构内部实现、行为不变时，它是否仍会通过？

答不出第 1、2 条的测试，应删除、合并或改写。

## 术语

| 术语 | 含义 | 不包括 |
| --- | --- | --- |
| 普通 UI 测试 | 验证渲染结果、布局、样式、文案、DOM 结构、独立点击与表单交互的测试，包括组件测试、视觉回归、截图对比、DOM 快照 | 与渲染无关的纯逻辑，即使它写在 Hook 或组件文件里 |
| UI 层纯逻辑 | 位于前端但不依赖渲染的计算、校验、格式化、状态转换，如折扣计算 Hook、表单校验函数 | 依赖 DOM、渲染生命周期或事件派发才能运行的代码 |
| 关键模块 | 涉及资金、权限、数据持久化、对外 API 契约或曾发生线上事故的模块；项目可在仓库内维护清单 | 仅因代码复杂而被认为“重要”的模块 |
| 受影响测试 | 覆盖本次改动文件及其直接调用方的测试 | 全量测试套件 |
| 允许范围内的验证 | 项目文档、CI 配置或任务说明明确允许运行的命令；未说明时只运行受影响测试和项目默认检查 | 需要外部账号、生产数据或付费资源的验证 |

## 必须有测试的情形

以下情形必须有对应的测试变更。确实无法编写时，必须在完成说明中写明原因和替代验证方式。

1. **修复缺陷**：必须有能复现原问题、并在修复后通过的回归测试。已有测试可扩展时优先扩展，不为同一缺陷重复建例。
2. **业务规则或对外契约变化**：计算、判断、状态转换、API 请求与响应、事件格式发生变化时，必须新增或修改断言来反映新行为。
3. **新增权限、资金或数据写入逻辑**：必须至少覆盖一条正常路径和一条拒绝路径，并断言拒绝时未产生副作用。

## 应覆盖的测试类型

按风险和场景选择，不要求每个函数机械覆盖全部类别：

- **核心业务规则**：计算、判断、状态转换、优先级和约束，包括 UI 层纯逻辑。
- **关键业务链路**：通过服务、API 和集成测试验证业务任务、结果和持久化状态。
- **有效边界**：空集合、临界值、上限、时间边界等会改变结果的输入。
- **失败与恢复**：超时、依赖异常、取消、重试、回滚及失败后的可恢复状态。
- **权限与隔离**：身份、角色、资源归属和租户边界。
- **并发与幂等**：重复请求、乱序事件、竞争更新和重复消费。
- **系统集成**：请求与序列化、数据库约束、事务、事件及模块连接。
- **明确的非功能要求**：性能、资源释放等有明确验收标准的行为；可访问性有合规或合同要求时也属此类。

## UI 与浏览器端到端测试

**普通 UI 测试一律不做**：不编写、不运行组件测试、视觉回归、截图对比和 DOM 快照，不为布局、样式、文案、独立点击、表单交互建立用例。UI 层纯逻辑不属于此类，应抽成不依赖渲染的函数，按普通单元测试处理。

**可访问性检查**默认不建测试。产品有合规或合同要求时，按“明确的非功能要求”处理，并在项目内注明依据。

**浏览器端到端测试**只在同时满足以下条件时采用：

- 链路属于关键模块，如登录、支付、下单、权限变更；
- 错误只会出现在真实浏览器中，例如前端组装请求、跨页面状态传递、浏览器存储或重定向，服务与 API 测试无法捕获；
- 预期收益高于编写、运行、维护和误报排查成本。

AI Agent 新增浏览器端到端测试前，必须先说明满足上述哪些条件，并取得人工确认。

端到端测试聚焦少量关键任务是否真正完成、结果是否正确，可包含必要的点击、输入和界面结果断言。不逐页覆盖、不穷举 UI 状态，不重复低层已覆盖的业务分支，也不以端到端名义恢复普通 UI 测试。按钮可见、页面打开、点击成功不等于业务完成，必须断言任务的实际结果。

## 不应存在的测试

以下 10 类测试不得新增，发现已有的应按工作流程处理。普通 UI 测试见上一节。

1. **预期值无独立依据**：用被测函数、复制的生产算法或同一有缺陷的工具生成预期值；把当前输出直接抄成预期值；大型、易变或未经审查的快照。小而稳定、可审阅的非 UI 输出快照除外。
2. **只验证 Mock 配置**：Mock 掉被测能力或整个业务链路后，只证明假数据按设定流转。
3. **只证明代码执行**：只断言不抛异常、返回值存在或 HTTP 200，不验证结果、状态变化或必要副作用。“不抛异常”本身就是完整契约时除外。
4. **绑定内部实现**：无业务理由地断言私有方法、内部变量或调用顺序，导致行为不变的重构也要大面积改测试。
5. **重复验证依赖或静态检查**：测试语言、框架、第三方库本身，或编译器、类型检查、Lint 已保证的事项。自身的配置、适配和外部输入的运行时校验仍按风险覆盖。
6. **无新增价值的重复与配套**：只替换普通输入；多个层级重复枚举同一批分支；仅因新增文件或函数而配套测试；测试没有独立规则的 getter、setter、包装和参数转发。
7. **为不存在的需求造测试**：为凑覆盖率强行触发不可达状态或制造不合理输入；为未经确认的兼容、降级或未来能力建立约束。
8. **不可靠或掩盖失败**：吞掉异常、遗漏异步等待、跳过关键断言，或靠反复重试偶尔通过。
9. **源码字符串检查**：搜索函数名、关键字或代码片段来证明功能正确。明确的架构约束或代码生成输出检查除外。
10. **临时诊断与成本失衡**：一次性排查脚本、环境检查或调试辅助代码留在套件中；为简单行为引入大量 Mock、Fixture 或辅助框架，维护成本超过保护价值。

## 预期值与断言

预期结果必须有独立依据：业务规则、外部协议、明确不变量或独立可信的参考实现。优先使用固定预期值，例如“余额 100 扣除 30 后为 70”，不在测试中重复计算。

编解码往返测试可以使用，但不能作为唯一证据，因为编码和解码可能以相互抵消的错误同时通过。

优先断言：

- 返回值和错误；
- 持久化状态；
- 对外事件及必要副作用；
- 失败时不应发生的副作用，如拒绝后未扣费、未写入、未越权泄露。

对外调用本身是契约时，可断言目标、参数和必要次数；不约束无关的内部调用过程。

## 测试层级与 Mock

按目标错误和成本选择层级，各层分别保护规则、连接和完整流程，不重复枚举同一风险。

| 层级 | 保护对象 | 典型目标错误 |
| --- | --- | --- |
| 单元测试 | 计算、判断、解析、状态转换，含 UI 层纯逻辑 | 规则写错、边界遗漏 |
| 集成测试 | 模块连接、数据库约束、事务、权限、事件处理 | 约束未生效、事务未回滚、越权 |
| API 与服务链路测试 | 请求与响应契约、跨服务流程、最终持久化结果 | 契约破坏、流程中断、状态不一致 |
| 浏览器端到端测试 | 关键任务在真实浏览器中的完整链路，条件见上文 | 只在浏览器中出现的集成错误 |

数据库事务和约束不能仅靠 Mock 证明。

保留被测范围内的真实业务逻辑，只在网络、时钟、随机数等边界按需使用替身。Mock 的数据和错误行为必须符合真实契约；第三方兼容性通过契约测试或受控集成测试补充。

## 测试数据与不稳定测试

**数据隔离**：每个涉及数据库或外部状态的测试必须自行准备数据并在结束后恢复。优先顺序为事务回滚、独立测试库或 Schema、测试结束后显式清理。不得依赖其他测试写入的数据，不得使用生产数据或真实用户信息，Fixture 中不得包含真实密钥。

**不稳定测试**：同一代码下结果时好时坏的测试，按以下顺序处理：

1. 先定位原因，常见为遗漏异步等待、依赖执行顺序、共享状态、未控制时间或随机数；
2. 能在本次任务内修复的，直接修复；
3. 不能立即修复的，标记为隔离并记录原因、负责人和期限，不得用增加重试次数或放宽断言来掩盖；
4. 被隔离测试保护的风险，在完成说明中列为覆盖缺口。

## 测试质量要求

- 测试名称描述“条件 → 行为 → 结果”，例如“余额不足时扣款 → 拒绝 → 余额不变”。
- 一个测试聚焦一个场景，可包含多个相关断言。
- 使用最小必要数据；共享工具不得隐藏关键动作和预期。
- 测试可独立运行，不依赖执行顺序或遗留状态。
- 控制时间、随机数和外部状态；随机或属性测试必须固定种子、可复现。
- 异步测试等待明确事件或状态，不使用固定休眠猜测完成时间。
- 不为方便测试随意暴露私有实现、加入测试专用判断，或引入没有业务价值的生产代码抽象。将 UI 层纯逻辑抽成独立函数不属于此限。
- LLM/Agent 系统分开验证：参数、权限、状态等确定性契约精确断言；开放式回答用明确标准评测。

## 工作流程

1. **评估**：明确变更涉及的行为、风险和现有覆盖。先对照“必须有测试的情形”；不属于其中且已有覆盖充分时，不新增测试。优先扩展已有测试。
2. **编写**：修复缺陷时先写能复现问题的失败测试，再修复并确认通过。
3. **反向检查**：删除关键逻辑、反转条件或破坏结果时，测试是否会失败。关键模块必要时使用变异测试。
4. **处理失败**：测试失败时先判断是实现错误、需求变化还是测试过时。修改预期值、删除断言或更新快照必须有需求或契约依据，不得仅为通过而放宽条件或增加重试。
5. **清理**：过时、重复或不稳定的测试可修复、合并或删除，并说明原因及原风险如何继续被保护。清理范围仅限本次改动直接涉及的测试；超出范围的批量删除或移出（包括已有普通 UI 测试）单独提交，AI Agent 须先取得人工确认。
6. **验证**：先运行受影响测试，再按风险在允许范围内扩大验证。受影响行为已充分验证、适用检查已通过即停止，不反复全量运行，不继续补充相似用例。
7. **说明**：按下方模板写完成说明。

## 完成说明模板

每次涉及测试的改动，完成后按以下格式说明，每项一两行即可；某项无内容时写“无”。

```markdown
**行为覆盖变化**：新增/修改/删除了哪些测试，分别保护什么行为。
**未新增测试的理由**：（仅当属于“必须有测试的情形”却未新增时填写）原因及替代验证方式。
**已运行的验证**：运行了哪些命令，结果如何。
**清理与隔离**：删除、合并或隔离了哪些测试，原风险由什么继续保护。
**剩余覆盖缺口**：已知但未覆盖的风险，及建议的后续处理。
```
